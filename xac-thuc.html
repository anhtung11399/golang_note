Xác thực và phân quyền

Băm mật khẩu, session và JWT, cookie an toàn, đăng nhập bằng Google (OAuth), phân quyền theo vai trò và chủ sở hữu.

Học xong bài này bạn sẽ:
  • Lưu mật khẩu đúng chuẩn
  • Chọn session hay JWT có lý do
  • Kiểm quyền ở mọi endpoint

#Hai câu hỏi khác nhau

Phần lớn sự cố rò rỉ dữ liệu qua API không phải do đăng nhập yếu, mà do quên kiểm quyền ở một endpoint nào đó. Bài này đi qua cả hai, phân quyền được nhấn mạnh hơn.

#Lưu mật khẩu: băm chậm, có muối

Không bao giờ lưu mật khẩu, kể cả đã mã hoá (mã hoá thì giải mã được). Lưu giá trị băm bằng thuật toán chuyên cho mật khẩu: cố tình chậm và tốn bộ nhớ, để kẻ trộm database không thể thử hàng tỷ mật khẩu mỗi giây.

Thuật toánDùng cho mật khẩu?
MD5, SHA-1, SHA-256 (trần)Không. Quá nhanh: card đồ hoạ thử được hàng tỷ lần mỗi giây
Argon2idCó. OWASP khuyến nghị dùng đầu tiên
bcryptCó. Rất phổ biến, đơn giản. Chỉ dùng 72 byte đầu của mật khẩu
scrypt, PBKDF2Chấp nhận được (PBKDF2 khi cần chuẩn FIPS)
Go
import "golang.org/x/crypto/bcrypt"

func HashPassword(pw string) (string, error) {
    if len(pw) < 8 || len(pw) > 72 { // bcrypt chỉ nhận tối đa 72 byte
        return "", &ValidationError{Field: "password", Message: "Mật khẩu từ 8 đến 72 ký tự"}
    }
    b, err := bcrypt.GenerateFromPassword([]byte(pw), 12) // cost 12: mỗi lần băm cỡ vài trăm ms
    return string(b), err
}

func CheckPassword(hash, pw string) bool {
    return bcrypt.CompareHashAndPassword([]byte(hash), []byte(pw)) == nil
}

Chuỗi băm bcrypt đã chứa sẵn muối (salt) ngẫu nhiên và cost: $2a$12$R9h/cIPz0gi.URNNX3kh2O.... Hai người cùng mật khẩu 123456 vẫn có hai chuỗi băm khác nhau.

Đăng nhập phải trả cùng một thông báo cho "sai email" và "sai mật khẩu" ("Email hoặc mật khẩu không đúng"), nếu không kẻ tấn công dò được email nào đã đăng ký. Và nhớ giới hạn tần suất đăng nhập (bài 17): băm chậm không cứu được mật khẩu 12345678 nếu kẻ tấn công được thử không giới hạn.

Nhiều vụ rò rỉ lớn bị khuếch đại vì mật khẩu được băm bằng thuật toán nhanh. Vụ LinkedIn năm 2012 là ví dụ hay được nhắc: mật khẩu băm SHA-1 không muối, sau đó phần lớn bị bẻ khoá. Ngày nay, nhiều sản phẩm chọn không tự lưu mật khẩu nữa mà cho đăng nhập bằng Google / Apple, magic link qua email, hoặc passkey.

#Phiên đăng nhập (session)

Sau khi xác thực xong, server cần "nhớ" người dùng cho các request sau. Cách truyền thống và vẫn rất tốt cho web: session token ngẫu nhiên trong cookie.

Go
func NewSessionToken() (token string, hash []byte, err error) {
    b := make([]byte, 32)
    if _, err := rand.Read(b); err != nil { // crypto/rand, KHÔNG phải math/rand
        return "", nil, err
    }
    token = base64.RawURLEncoding.EncodeToString(b)
    h := sha256.Sum256([]byte(token))
    return token, h[:], nil // gửi token cho client, chỉ lưu hash vào database
}

func SetSessionCookie(w http.ResponseWriter, token string, ttl time.Duration) {
    http.SetCookie(w, &http.Cookie{
        Name:     "__Host-session", // tiền tố __Host-: bắt buộc Secure, Path=/, không Domain
        Value:    token,
        Path:     "/",
        MaxAge:   int(ttl.Seconds()),
        HttpOnly: true,                 // JavaScript không đọc được → XSS không lấy được token
        Secure:   true,                 // chỉ gửi qua HTTPS
        SameSite: http.SameSiteLaxMode, // hạn chế gửi kèm request từ trang khác (CSRF)
    })
}

Vì sao lưu băm của token? Nếu database bị lộ (bản sao lưu, log), kẻ tấn công cũng không dùng được các phiên đang hoạt động.

  • Đăng xuất: xoá dòng phiên trong database. Hiệu lực ngay.
  • Đổi mật khẩu: xoá mọi phiên khác của người đó.
  • Hạn phiên: ví dụ 30 ngày, gia hạn khi người dùng còn hoạt động.

Lưu token trong localStorage rất tiện ở frontend, nhưng bất kỳ đoạn script nào chạy được trên trang (một thư viện bị chiếm quyền, một lỗi XSS) đều đọc được nó. Cookie HttpOnly thì JavaScript không đọc được. Với ứng dụng web cùng tên miền với API, cookie là lựa chọn an toàn hơn.

Middleware xác thực

Go
type ctxUserKey struct{}

func (a *Auth) Middleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        c, err := r.Cookie("__Host-session")
        if err == nil {
            if u, err := a.store.UserBySession(r.Context(), sha256Of(c.Value)); err == nil {
                r = r.WithContext(context.WithValue(r.Context(), ctxUserKey{}, u))
            }
        }
        next.ServeHTTP(w, r) // chưa đăng nhập vẫn đi tiếp: route nào cần thì tự chặn
    })
}

func RequireUser(next http.HandlerFunc) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        if _, ok := r.Context().Value(ctxUserKey{}).(User); !ok {
            WriteJSON(w, http.StatusUnauthorized, errBody("UNAUTHENTICATED", "Vui lòng đăng nhập"))
            return
        }
        next(w, r)
    }
}

#JWT: khi nào nên, khi nào không

JWT (JSON Web Token) là một chuỗi gồm 3 phần header.payload.signature. Payload chứa thông tin (user id, vai trò, hạn), chữ ký chứng minh server đã tạo ra nó. Server kiểm chữ ký là tin payload, không cần tra database.

Session trong databaseJWT
Đăng xuất / thu hồi ngayDễ: xoá dòngKhó: token vẫn hợp lệ tới khi hết hạn, trừ khi có danh sách chặn (lại phải tra database)
Mỗi request tra databaseCó (cache được bằng Redis)Không
Đổi quyền có hiệu lựcNgayKhi token cũ hết hạn
Hợp vớiWeb app thông thườngGiao tiếp giữa các dịch vụ, token ngắn hạn, hệ thống nhiều bên (OAuth, OIDC)

Lỗi JWT hay gặp: chấp nhận thuật toán none hoặc để token tự chọn thuật toán; khoá ký yếu; hạn quá dài (vài tháng); nhét dữ liệu nhạy cảm vào payload (payload chỉ được mã hoá base64, ai cũng đọc được, không phải mã hoá bí mật). Nếu dùng JWT: thư viện uy tín (golang-jwt/jwt/v5), cố định thuật toán khi kiểm, hạn ngắn (5 đến 15 phút) kèm refresh token lưu ở server.

#Đăng nhập bằng Google (OAuth 2.0 / OpenID Connect)

Ứng dụng hiện đại thường để Google / Apple xác thực, bạn khỏi lưu mật khẩu. Luồng an toàn cho web là Authorization Code + PKCE, chạy ở phía server:

Package golang.org/x/oauth2 lo phần lớn luồng này (có hỗ trợ PKCE). Định danh người dùng là trường sub của Google (không đổi), không phải email (người dùng có thể đổi email).

#Phân quyền: kiểm ở mọi nơi

Theo vai trò (RBAC)

Go
func RequireRole(role string, next http.HandlerFunc) http.HandlerFunc {
    return RequireUser(func(w http.ResponseWriter, r *http.Request) {
        if UserFrom(r.Context()).Role != role {
            WriteJSON(w, http.StatusForbidden, errBody("FORBIDDEN", "Bạn không có quyền"))
            return
        }
        next(w, r)
    })
}

mux.HandleFunc("POST /v1/classes", RequireRole("teacher", h.createClass))

Theo quyền sở hữu: nơi lỗ hổng hay nằm

Vai trò "giáo viên" cho phép sửa lớp, nhưng chỉ lớp của mình. Kiểm tra này không làm ở middleware được vì phụ thuộc dữ liệu. Cách an toàn nhất: đưa người dùng hiện tại vào mọi câu truy vấn.

GoSai / nguy hiểm
// Kiểm vai trò rồi tin id trong URL: giáo viên A sửa được lớp của giáo viên B
func (h *Handler) updateClass(w http.ResponseWriter, r *http.Request) {
    id := pathID(r)
    h.db.Exec(ctx, `UPDATE classes SET name = $1 WHERE id = $2`, name, id)
}

func (h *Handler) updateClass(w http.ResponseWriter, r *http.Request) {
    me := UserFrom(r.Context())
    tag, err := h.db.Exec(ctx,
        `UPDATE classes SET name = $1 WHERE id = $2 AND teacher_id = $3`, name, pathID(r), me.ID)
    // ... tag.RowsAffected() == 0 → 404

Mỗi quy tắc phân quyền cần một test: tạo hai người dùng, người A tạo dữ liệu, người B thử đọc / sửa / xoá dữ liệu đó qua mọi endpoint, phải nhận 403/404. Nhiều đội gom các test này thành một bộ riêng và chạy ở mọi lần thay đổi.

Một mẫu giúp không quên: hàm tầng store đều nhận người gọi làm tham số, như ClassOf(ctx, teacherID, classID) thay vì Class(ctx, classID). Không có hàm nào lấy dữ liệu theo id trần để người viết handler vô tình dùng.

#CSRF khi dùng cookie

Trình duyệt tự gửi cookie kèm request, kể cả request do một trang web khác tạo ra (form ẩn tự submit). Đó là tấn công CSRF.

  • SameSite=Lax: cookie không đi kèm POST / PUT / DELETE xuất phát từ trang khác. Đã chặn được phần lớn.
  • Kiểm header Origin (hoặc Sec-Fetch-Site) của mọi request thay đổi dữ liệu: phải là tên miền của bạn.
  • Từ Go 1.25, net/http có sẵn http.CrossOriginProtection làm việc này dựa trên Sec-Fetch-Site và Origin.
  • API chỉ nhận Content-Type: application/json cũng khó bị tạo từ form HTML thường.

Câu hỏi nhanh. Phụ huynh đăng nhập gọi GET /v1/children/123/grades. Middleware đã xác nhận người này có vai trò phụ huynh. Còn cần kiểm tra gì?

Vai trò không thay thế được quyền sở hữu. Đổi 123 thành 124 là xem được điểm con nhà khác nếu thiếu kiểm tra này: lỗi BOLA, bài 19.

#Bài tập

Đăng ký, đăng nhập, đăng xuất

Thêm vào API ghi chú: bảng users, sessions(token_hash, user_id, expires_at). Endpoint POST /register, POST /login (5 lần sai / 15 phút / email thì 429), POST /logout, GET /me. Ghi chú thuộc về người tạo, mọi endpoint ghi chú chỉ thấy ghi chú của mình.

Danh sách kiểm tra
  • Email chuẩn hoá chữ thường, UNIQUE trong database, trùng trả 409.
  • Mật khẩu băm bcrypt / argon2id, không bao giờ trả ra JSON hay ghi log.
  • Sai email và sai mật khẩu cùng một thông báo, cùng status 401.
  • Token 32 byte từ crypto/rand, database lưu SHA-256 của token.
  • Cookie HttpOnly, Secure, SameSite=Lax.
  • Đăng xuất xoá dòng session, gọi /me bằng cookie cũ phải nhận 401.
  • Test: người B gọi GET/PATCH/DELETE /notes/{id của A} nhận 404.
