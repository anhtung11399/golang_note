Bảo mật API: các lỗ hổng hay gặp nhất

OWASP API Top 10 bằng ví dụ Go: truy cập dữ liệu người khác, SQL injection, gán trường bừa, SSRF, lộ bí mật, CORS.

Học xong bài này bạn sẽ:
  • Nhận ra lỗi BOLA / IDOR trong code
  • Chống tiêu tốn tài nguyên không giới hạn
  • Có checklist bảo mật trước khi lên production

BOLA (còn gọi là IDOR) là nguyên nhân của rất nhiều vụ lộ dữ liệu lớn qua API: đổi số trong URL là xem được đơn hàng, hồ sơ, hoá đơn của người khác. Vụ rò rỉ dữ liệu khách hàng của nhà mạng Úc Optus năm 2022 được báo chí mô tả là xuất phát từ một API không yêu cầu xác thực và có định danh khách hàng tăng dần. Lỗi này không cần kỹ thuật cao: chỉ cần một vòng lặp đổi id.

#SQL injection và các loại injection khác

Đã gặp ở bài 17: luôn dùng tham số $1. Những chỗ vẫn hay sót:

  • Tên cột sắp xếp, chiều sắp xếp lấy từ query string → dùng danh sách cho phép.
  • LIKE với dữ liệu người dùng: tham số vẫn an toàn, nhưng ký tự % và _ trong từ khoá sẽ là ký tự đại diện. Thoát chúng nếu muốn tìm đúng chữ.
  • Chạy lệnh hệ thống: không bao giờ exec.Command("sh", "-c", "convert " + filename). Truyền tham số riêng: exec.Command("convert", filename, out).
  • Đường dẫn file từ người dùng: ../../etc/passwd. Từ Go 1.24 có os.Root để giới hạn thao tác file trong một thư mục.

#API7: SSRF

Tính năng "nhập URL ảnh đại diện", "nhập URL webhook", "xem trước link": server tải URL do người dùng đưa. Kẻ tấn công đưa http://169.254.169.254/latest/meta-data/ (địa chỉ dịch vụ metadata trên AWS, nơi có thể chứa thông tin đăng nhập tạm của máy chủ) hoặc http://localhost:6379.

Go · trích đoạn
// Chặn ở tầng kết nối: kiểm IP THẬT sau khi phân giải DNS (chống đổi DNS giữa lúc kiểm và lúc gọi)
dialer := &net.Dialer{
    Timeout: 5 * time.Second,
    Control: func(network, address string, _ syscall.RawConn) error {
        host, _, err := net.SplitHostPort(address)
        if err != nil {
            return err
        }
        ip, err := netip.ParseAddr(host)
        if err != nil {
            return err
        }
        if ip.IsLoopback() || ip.IsPrivate() || ip.IsLinkLocalUnicast() || ip.IsUnspecified() || ip.IsMulticast() {
            return fmt.Errorf("địa chỉ bị chặn: %s", ip)
        }
        return nil
    },
}
safeClient := &http.Client{
    Timeout:   10 * time.Second,
    Transport: &http.Transport{DialContext: dialer.DialContext},
}

Vụ Capital One năm 2019 (thông tin của khoảng 100 triệu khách hàng bị lộ) liên quan tới SSRF: kẻ tấn công khiến một máy chủ gọi tới dịch vụ metadata của AWS và lấy được thông tin đăng nhập tạm. Sau đó AWS đẩy mạnh IMDSv2, phiên bản yêu cầu token, để khó khai thác kiểu này hơn.

#API8: cấu hình sai

CORS

CORS là cơ chế trình duyệt hỏi server "trang ở tên miền X có được đọc response của bạn không". Nó bảo vệ người dùng khỏi trang độc, không bảo vệ API khỏi curl.

Go · trích đoạnSai / nguy hiểm
// Phản chiếu mọi Origin + cho gửi cookie: trang web bất kỳ đọc được dữ liệu của người dùng đang đăng nhập
w.Header().Set("Access-Control-Allow-Origin", r.Header.Get("Origin"))
w.Header().Set("Access-Control-Allow-Credentials", "true")
Go · trích đoạnĐúng / nên làm
var allowed = map[string]bool{"https://sobaitap.vn": true, "https://admin.sobaitap.vn": true}

if o := r.Header.Get("Origin"); allowed[o] {
    w.Header().Set("Access-Control-Allow-Origin", o)
    w.Header().Set("Access-Control-Allow-Credentials", "true")
    w.Header().Add("Vary", "Origin") // để cache không trả nhầm header cho Origin khác
}

Bạn chắc đã từng gặp lỗi CORS ở frontend và cách "sửa nhanh" là bật * ở backend. Giờ bạn ở phía bên kia: chỉ liệt kê đúng tên miền của mình. Nếu frontend và API cùng tên miền (API ở /api), bạn không cần CORS.

Header bảo mật và thông tin lỗi

Go · trích đoạn
func SecurityHeaders(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        h := w.Header()
        h.Set("X-Content-Type-Options", "nosniff")
        h.Set("Referrer-Policy", "strict-origin-when-cross-origin")
        h.Set("Strict-Transport-Security", "max-age=31536000; includeSubDomains")
        h.Set("X-Frame-Options", "DENY")
        next.ServeHTTP(w, r)
    })
}
  • Không trả stack trace, câu SQL, chuỗi lỗi nội bộ cho client (bài 7).
  • Tắt các endpoint gỡ lỗi (/debug/pprof) trên cổng công khai, đặt chúng ở cổng nội bộ.
  • Không để bản dev (DEV_FAKE_LOGIN=1, dữ liệu mẫu) chạy được trên production. Kiểm tra lúc khởi động và từ chối chạy.

#Phân quyền ở một chỗ: lớp policy

BOLA xảy ra vì kiểm tra quyền nằm rải rác, mỗi handler tự nhớ (hoặc quên) kiểm tra. Khi số endpoint lên tới vài trăm, cách bền vững là gom luật phân quyền vào một package, và mọi đường đọc / ghi đều đi qua nó.

internal/authz/authz.go
package authz

import (
    "context"
    "errors"
)

var ErrForbidden = errors.New("không có quyền")

type Action string

const (
    ViewSubmission  Action = "submission.view"
    GradeSubmission Action = "submission.grade"
    DeleteClass     Action = "class.delete"
)

type User struct {
    ID      int64
    IsAdmin bool
}

// Relations: các câu hỏi về quan hệ, trả lời bằng truy vấn database
type Relations interface {
    TeachesClassOfSubmission(ctx context.Context, teacherID, submissionID int64) (bool, error)
    IsGuardianOfSubmission(ctx context.Context, parentID, submissionID int64) (bool, error)
    OwnsClass(ctx context.Context, teacherID, classID int64) (bool, error)
}

type Authorizer struct{ rel Relations }

func (a *Authorizer) Can(ctx context.Context, u User, act Action, resourceID int64) error {
    var ok bool
    var err error
    switch act {
    case ViewSubmission:
        // giáo viên của lớp, HOẶC phụ huynh của bé
        ok, err = a.rel.TeachesClassOfSubmission(ctx, u.ID, resourceID)
        if err == nil && !ok {
            ok, err = a.rel.IsGuardianOfSubmission(ctx, u.ID, resourceID)
        }
    case GradeSubmission:
        ok, err = a.rel.TeachesClassOfSubmission(ctx, u.ID, resourceID) // chỉ giáo viên
    case DeleteClass:
        ok, err = a.rel.OwnsClass(ctx, u.ID, resourceID)
    default:
        return ErrForbidden // hành động lạ: TỪ CHỐI, không bao giờ mặc định cho phép
    }
    if err != nil {
        return err
    }
    if !ok {
        return ErrForbidden
    }
    return nil
}
Go · trích đoạn
func (h *H) grade(w http.ResponseWriter, r *http.Request) {
    u := authz.UserFrom(r.Context())
    id, _ := strconv.ParseInt(r.PathValue("id"), 10, 64)
    if err := h.authz.Can(r.Context(), u, authz.GradeSubmission, id); err != nil {
        writeErr(w, err) // ErrForbidden → 404 (không lộ là bài có tồn tại)
        return
    }
    // ...
}

Lợi ích: một bảng luật duy nhất để review, viết test cho từng ô (giáo viên lớp khác, phụ huynh bé khác, người lạ), và thêm vai trò mới chỉ sửa một chỗ. Với hệ thống lớn, có thư viện / dịch vụ chuyên cho việc này: Casbin, OPA, OpenFGA (mô hình quan hệ kiểu Google Zanzibar).

Một lớp bảo vệ thứ hai: lọc theo người dùng ngay trong câu SQL (WHERE c.teacher_id = $me). Quên gọi Can thì câu SQL vẫn không trả dữ liệu của người khác. Hai lớp cùng lúc thì một lần quên không thành lỗ hổng.

#API2: những lỗi xác thực hay gặp ở API

Bài 21 dạy cách làm đúng. Đây là danh sách lỗi để rà lại:

  • Đăng nhập, quên mật khẩu, xác minh OTP không giới hạn số lần thử: OTP 6 số chỉ có 1 triệu khả năng.
  • Token đặt lại mật khẩu không hết hạn, dùng lại được nhiều lần, hoặc so sánh bằng == (dùng subtle.ConstantTimeCompare).
  • JWT: chấp nhận thuật toán none, không kiểm tra exp / aud / iss, khoá ký yếu. Dùng thư viện chuẩn (golang-jwt/jwt/v5) và chỉ định rõ thuật toán được chấp nhận.
  • Đổi email / mật khẩu không hỏi lại mật khẩu cũ, không gửi thông báo về email cũ.
  • Đăng xuất không huỷ phiên phía server. Đổi mật khẩu không huỷ các phiên khác.
  • Thông báo lỗi khác nhau cho "email không tồn tại" và "sai mật khẩu": kẻ xấu dò được ai có tài khoản.

#API9: biết mình đang có những API nào

  • Bản /v1 cũ vẫn chạy với luật kiểm tra lỏng hơn /v2. Kẻ tấn công gọi bản cũ.
  • Môi trường staging dùng dữ liệu thật nhưng bảo vệ kém, có tên miền đoán được (staging-api.).
  • Endpoint gỡ lỗi (/debug, /test-email) quên tắt.

Phòng: danh sách API từ OpenAPI spec (bài 15) là nguồn sự thật. Test tự động so danh sách route thật của server với spec: route có mà spec không có thì báo lỗi CI. Đặt ngày ngừng hỗ trợ cho bản cũ và trả header Deprecation / Sunset.

Go · trích đoạn
// Liệt kê mọi route đã đăng ký: in lúc khởi động hoặc so với spec trong test
for _, p := range registeredPatterns { // tự giữ danh sách khi gọi mux.HandleFunc
    fmt.Println(p)
}

#API10: không tin dữ liệu từ API bên thứ ba

Dữ liệu từ ngân hàng, cổng thanh toán, AI, đối tác cũng là đầu vào không tin cậy, như dữ liệu người dùng:

  • Webhook: kiểm tra chữ ký (HMAC) và thời gian, đối chiếu lại số tiền với đơn trong database (bài 23). Đừng tin trường amount trong webhook là số tiền của đơn.
  • Giới hạn khi gọi ra ngoài: timeout, kích thước body đọc về (io.LimitReader), số lần redirect.
  • Validate response như validate request: kiểu, độ dài, giá trị cho phép, trước khi ghi vào database hay hiện cho người dùng.
  • Nội dung AI sinh ra có thể chứa HTML / script / link lạ: escape khi hiển thị, không bao giờ chạy như lệnh hay câu SQL.
Go · trích đoạn
resp, err := client.Do(req) // client có Timeout
if err != nil {
    return err
}
defer resp.Body.Close()
body := io.LimitReader(resp.Body, 1<<20) // tối đa 1MB, đối tác trả 2GB cũng không làm hết RAM
var out PartnerResp
if err := json.NewDecoder(body).Decode(&out); err != nil {
    return fmt.Errorf("đối tác trả dữ liệu hỏng: %w", err)
}
if out.Status != "paid" && out.Status != "pending" { // chỉ nhận giá trị đã biết
    return fmt.Errorf("trạng thái lạ: %q", out.Status)
}

#Audit log: ai đã làm gì

Log ứng dụng để gỡ lỗi, có thể bị xoay vòng và xoá. Audit log là bản ghi lâu dài các hành động nhạy cảm, để trả lời "ai đã xoá lớp này", "ai đã xem hồ sơ bé này", phục vụ điều tra sự cố và yêu cầu pháp lý.

SQL
CREATE TABLE audit_events (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    at         timestamptz NOT NULL DEFAULT now(),
    actor_id   bigint,                 -- ai làm (NULL: hệ thống)
    action     text NOT NULL,          -- 'class.delete', 'login.failed', 'role.grant'
    target     text,                   -- 'class:42'
    ip         inet,
    detail     jsonb                   -- không chứa mật khẩu, token
);
CREATE INDEX ON audit_events (target, at);

Ghi audit trong cùng transaction với hành động (xoá lớp thất bại thì không có dòng audit). Ứng dụng chỉ được INSERT vào bảng này, không có quyền UPDATE / DELETE (cấp quyền riêng trong Postgres), để kẻ chiếm được ứng dụng không xoá được dấu vết.

#Mô hình hoá mối đe doạ trong 30 phút

Trước khi làm một tính năng có rủi ro (thanh toán, upload, chia sẻ dữ liệu), cả đội ngồi vẽ luồng dữ liệu và đi qua sáu câu hỏi STRIDE:

ChữMối đe doạCâu hỏi cho tính năng
SSpoofing: giả danhcó ai giả làm người khác / giả làm ngân hàng gửi webhook được không?
TTampering: sửa dữ liệuclient sửa giá, sửa điểm, sửa id được không?
RRepudiation: chối bỏcó bằng chứng ai đã làm hành động này không (audit log)?
IInformation disclosure: lộ thông tinresponse, log, URL, thông báo lỗi có lộ gì không?
DDenial of service: làm sậpgửi file 2GB, 10.000 request, câu tìm kiếm nặng thì sao?
EElevation of privilege: leo quyềnphụ huynh làm được việc của giáo viên, giáo viên làm được việc của quản trị không?

Kết quả là một danh sách việc cụ thể (thêm giới hạn, thêm test phân quyền), đưa vào kế hoạch như mọi việc khác.

#Bí mật (secrets)

  • Không commit khoá API, mật khẩu database, khoá ký vào git, kể cả repo riêng tư. Lỡ commit thì coi như đã lộ: đổi khoá, xoá khỏi lịch sử git không đủ.
  • Đưa vào qua biến môi trường hoặc trình quản lý bí mật (AWS Secrets Manager, GCP Secret Manager, Vault, secrets của nền tảng deploy).
  • Bật tính năng quét bí mật của GitHub (secret scanning, push protection) cho repo.
  • So sánh token, chữ ký bằng subtle.ConstantTimeCompare hoặc hmac.Equal để không lộ thông tin qua thời gian so sánh.

#Upload file

  • Giới hạn kích thước trước khi đọc hết vào bộ nhớ.
  • Không tin phần mở rộng hay Content-Type client gửi. Đọc vài byte đầu: http.DetectContentType.
  • Tên file lưu trữ do server tạo (id ngẫu nhiên), không dùng tên người dùng đặt.
  • Lưu ở dịch vụ lưu trữ đối tượng (S3, R2, GCS), phục vụ file qua tên miền khác với ứng dụng, hoặc kèm Content-Disposition: attachment, để file HTML / SVG độc không chạy được trong tên miền của bạn.
  • Kiểm quyền khi tải file về, giống mọi tài nguyên khác (BOLA với file là cực kỳ phổ biến).

#Bài tập

Tấn công thử API của chính bạn

Chạy API có đăng nhập ở lời giải bài 21 (hoặc bản Docker ở bài 29). Đóng vai kẻ tấn công, dùng curl thử 6 cách dưới đây. Với mỗi cách, đoán trước API sẽ trả gì, rồi mới chạy để kiểm tra.

  1. BOLA: người B đọc, xoá ghi chú của người A bằng cách đổi id trên URL.
  2. SQL injection: gửi email là ' OR '1'='1 khi đăng nhập.
  3. Body khổng lồ: gửi một ghi chú 100 KB.
  4. Mass assignment: đăng ký kèm trường lạ "id": 1, "role": "admin".
  5. Không đăng nhập: gọi /notes không có cookie, hoặc với cookie bịa ra.
  6. Lộ lỗi: gửi JSON hỏng, xem response có lộ chi tiết bên trong không.
Xem lời giải
Terminal
J='Content-Type: application/json'
curl -s -c a.txt -X POST localhost:8080/register -H "$J" -d '{"email":"a@x.vn","password":"matkhau123"}'
curl -s -c b.txt -X POST localhost:8080/register -H "$J" -d '{"email":"b@x.vn","password":"matkhau123"}'
curl -s -b a.txt -X POST localhost:8080/notes -H "$J" -d '{"text":"bí mật của A"}'
Terminal — kết quả khi chạy
{"id":1,"email":"a@x.vn"}
{"id":2,"email":"b@x.vn"}
{"id":1,"text":"bí mật của A","createdAt":"2026-11-03T09:20:00.1+00:00"}

1. BOLA: B thử ghi chú số 1 của A.

Terminal — kết quả khi chạy
$ curl -s -b b.txt localhost:8080/notes/1
{"error":"Không tìm thấy"}
$ curl -s -o /dev/null -w '%{http_code}\n' -b b.txt -X DELETE localhost:8080/notes/1
404

Chặn được vì mọi câu SQL có AND user_id = $2. Trả 404 chứ không phải 403, nên B không biết ghi chú số 1 có tồn tại hay không.

2. SQL injection:

Terminal — kết quả khi chạy
$ curl -s -X POST localhost:8080/login -H "$J" -d $'{"email":"\' OR \'1\'=\'1","password":"x"}'
{"error":"Email hoặc mật khẩu không đúng"}

Chặn được vì câu SQL dùng tham số $1: chuỗi ' OR '1'='1 được coi là một email (lạ), không phải code SQL. ($'...' là cách bash cho phép viết dấu nháy đơn bên trong chuỗi.)

3. Body khổng lồ: tạo chuỗi 100.000 chữ a bằng Python rồi gửi:

Terminal — kết quả khi chạy
$ BIG=$(python3 -c 'print("a" * 100000)')
$ curl -s -b a.txt -X POST localhost:8080/notes -H "$J" -d "{\"text\":\"$BIG\"}"
{"error":"JSON không hợp lệ"}

Chặn được nhờ http.MaxBytesReader (64 KB) trong hàm decode: server ngừng đọc khi vượt giới hạn, không nạp cả khối vào RAM. Câu báo lỗi chưa thật chính xác: muốn báo "Dữ liệu quá lớn" thì kiểm *http.MaxBytesError như hàm DecodeJSON ở bài 12.

4. Mass assignment:

Terminal — kết quả khi chạy
$ curl -s -X POST localhost:8080/register -H "$J" -d '{"email":"c@x.vn","password":"matkhau123","id":1,"role":"admin"}'
{"id":3,"email":"c@x.vn"}

Không làm gì được: struct credentials chỉ có hai trường Email, Password, nên id và role bị bỏ qua, id do database tự đánh. Nếu bạn lỡ decode thẳng vào struct User có trường Role, kẻ tấn công tự phong admin được. Đó là lý do mỗi request có struct riêng.

5. Không đăng nhập / cookie bịa:

Terminal — kết quả khi chạy
$ curl -s localhost:8080/notes
{"error":"Vui lòng đăng nhập"}
$ curl -s -H 'Cookie: __Host-session=toi-tu-bia-ra' localhost:8080/notes
{"error":"Vui lòng đăng nhập"}

Token bịa không có bản băm tương ứng trong bảng sessions. Token thật là 32 byte ngẫu nhiên, đoán trúng là chuyện không thể.

6. Lộ lỗi:

Terminal — kết quả khi chạy
$ curl -s -b a.txt -X POST localhost:8080/notes -H "$J" -d '{"text":'
{"error":"JSON không hợp lệ"}

Response chỉ có câu chung chung. Chi tiết như unexpected EOF, tên bảng, câu SQL không lọt ra ngoài.

Kết luận: cả 6 cách đều bị chặn, và mỗi cái chặn được nhờ một dòng code cụ thể bạn đã viết. Thử bỏ AND user_id = $2 trong getNote rồi chạy lại cách 1: B đọc được bí mật của A. Đó chính là lỗi API số một của OWASP.

#Checklist trước khi lên production

Tự rà API của bạn theo danh sách này
  • Mọi endpoint (trừ vài endpoint công khai có chủ đích) yêu cầu đăng nhập.
  • Mọi truy vấn theo id có điều kiện quyền sở hữu, và có test người B truy cập dữ liệu người A.
  • Struct request / database / response tách riêng. Không trả hash mật khẩu, token, email của người khác.
  • Body, file, chuỗi, phân trang, tần suất đều có giới hạn.
  • Truy vấn SQL chỉ dùng tham số, tên cột động chọn từ danh sách cho phép.
  • Cookie HttpOnly, Secure, SameSite. Kiểm Origin cho request thay đổi dữ liệu. CORS chỉ mở cho tên miền của mình.
  • http.Server và http.Client có timeout. Gọi URL do người dùng nhập thì có chặn SSRF.
  • Lỗi 500 không lộ chi tiết. Log không chứa mật khẩu, token.
  • Bí mật không nằm trong git. govulncheck, gosec chạy trong CI.
  • Endpoint quản trị tách riêng, có xác thực hai lớp.
