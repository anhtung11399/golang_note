Theo dõi hệ thống: log, metrics, tracing

Ba trụ cột quan sát hệ thống, health check, Prometheus, OpenTelemetry, pprof, SLO và cảnh báo.

Học xong bài này bạn sẽ:
  • Biết hệ thống đang khoẻ hay ốm
  • Lần ra request chậm ở đâu
  • Đặt cảnh báo có ý nghĩa

#Ba trụ cột quan sát

Ở frontend, khi có lỗi bạn mở DevTools trên chính máy mình. Trên production không có DevTools: server chạy ở đâu đó, phục vụ hàng nghìn người, và lỗi xảy ra lúc bạn đang ngủ. Bạn chỉ biết chuyện gì xảy ra qua những gì hệ thống tự ghi lại.

#Logs: đã học ở bài 13

  • Log có cấu trúc (JSON), mỗi dòng có request_id, user_id khi có.
  • Mức log: ERROR cho thứ cần người xem, WARN cho bất thường tự phục hồi được, INFO cho sự kiện nghiệp vụ quan trọng, DEBUG tắt trên production.
  • Ghi log ra stdout, để nền tảng thu gom. Không tự ghi vào file trên server.
  • Không log dữ liệu nhạy cảm.

#Metrics với Prometheus

Prometheus (ra đời ở SoundCloud, nay là dự án của CNCF) định kỳ gọi endpoint /metrics của server để lấy các con số, lưu theo thời gian. Grafana vẽ biểu đồ từ đó.

Go · trích đoạn
import (
    "github.com/prometheus/client_golang/prometheus"
    "github.com/prometheus/client_golang/prometheus/promauto"
    "github.com/prometheus/client_golang/prometheus/promhttp"
)

var (
    httpRequests = promauto.NewCounterVec(prometheus.CounterOpts{
        Name: "http_requests_total",
        Help: "Số request HTTP",
    }, []string{"method", "route", "status"})

    httpDuration = promauto.NewHistogramVec(prometheus.HistogramOpts{
        Name:    "http_request_duration_seconds",
        Help:    "Thời gian xử lý request",
        Buckets: prometheus.DefBuckets,
    }, []string{"method", "route"})
)

// Trong middleware Logger (bài 13), sau next.ServeHTTP:
route := r.Pattern // Go 1.23+: mẫu route đã khớp, ví dụ "GET /classes/{id}"
httpRequests.WithLabelValues(r.Method, route, strconv.Itoa(rec.status)).Inc()
httpDuration.WithLabelValues(r.Method, route).Observe(time.Since(start).Seconds())

// Mở /metrics ở cổng NỘI BỘ, không công khai
internal := http.NewServeMux()
internal.Handle("GET /metrics", promhttp.Handler())
go http.ListenAndServe("127.0.0.1:9090", internal)

Nhãn (label) của metric phải có số giá trị hữu hạn. Dùng mẫu route /classes/{id}, không dùng đường dẫn thật /classes/12345, không dùng user id. Mỗi tổ hợp nhãn là một chuỗi số liệu riêng, nhãn vô hạn sẽ làm Prometheus hết bộ nhớ.

Đo cái gì: phương pháp RED

Với mỗi dịch vụ, theo dõi ba con số:

  • Rate: số request mỗi giây.
  • Errors: tỉ lệ request lỗi (5xx).
  • Duration: thời gian xử lý, xem theo phân vị (p50, p95, p99), không xem trung bình.

Vì sao không dùng trung bình? 99 request mất 10ms và 1 request mất 5 giây có trung bình 60ms, trông ổn. Nhưng p99 là 5 giây: cứ 100 người thì 1 người chờ 5 giây. Người dùng nhiều thao tác nhất (giáo viên chấm bài cả lớp) gần như chắc chắn gặp request chậm đó.

Với tài nguyên (CPU, bộ nhớ, pool kết nối database, hàng đợi), dùng phương pháp USE: Utilization (đang dùng bao nhiêu phần trăm), Saturation (bao nhiêu thứ đang phải xếp hàng chờ), Errors.

#Traces: request chậm ở đâu

OpenTelemetry là chuẩn mở (cũng thuộc CNCF) để tạo và gửi trace, metrics, logs, được hầu hết các nhà cung cấp hỗ trợ. Trong Go, các thư viện bọc sẵn cho net/http, pgx, go-redis tự tạo span. Trace id được truyền giữa các dịch vụ qua header chuẩn traceparent (W3C Trace Context), và qua ctx bên trong một dịch vụ: thêm một lý do để truyền ctx đi mọi nơi.

#Health check

Go · trích đoạn
// Liveness: tiến trình còn sống không? Không kiểm database (database chết thì khởi động lại server cũng vô ích)
mux.HandleFunc("GET /livez", func(w http.ResponseWriter, r *http.Request) {
    w.WriteHeader(http.StatusOK)
})

// Readiness: sẵn sàng nhận request chưa? Kiểm những thứ bắt buộc phải có
mux.HandleFunc("GET /readyz", func(w http.ResponseWriter, r *http.Request) {
    ctx, cancel := context.WithTimeout(r.Context(), time.Second)
    defer cancel()
    if err := db.Ping(ctx); err != nil {
        http.Error(w, "database", http.StatusServiceUnavailable)
        return
    }
    w.WriteHeader(http.StatusOK)
})

Load balancer và Kubernetes gọi các endpoint này: bản nào không "ready" thì không nhận request mới, bản nào không "live" thì bị khởi động lại. Lúc graceful shutdown (bài 13), cho /readyz trả 503 trước để load balancer ngừng gửi request mới tới.

#pprof: xem bên trong chương trình đang chạy

Go có sẵn công cụ profiling cực mạnh. Bật nó ở cổng nội bộ:

Go · trích đoạn
import _ "net/http/pprof" // đăng ký /debug/pprof/* vào http.DefaultServeMux

go http.ListenAndServe("127.0.0.1:6060", nil) // chỉ nghe ở localhost
Terminal
go tool pprof -http=:8000 http://localhost:6060/debug/pprof/profile?seconds=30  # CPU: hàm nào tốn nhiều nhất
go tool pprof -http=:8000 http://localhost:6060/debug/pprof/heap                # bộ nhớ: ai cấp phát nhiều
curl "http://localhost:6060/debug/pprof/goroutine?debug=1"                        # đang có bao nhiêu goroutine, kẹt ở đâu

Lệnh đầu mở giao diện web có biểu đồ flame graph: hàm nào càng rộng càng tốn thời gian. Số goroutine tăng mãi theo thời gian là dấu hiệu rò rỉ goroutine (bài 09).

Không bao giờ để /debug/pprof mở ra Internet: nó lộ thông tin bên trong và có thể bị dùng để làm chậm server. Chỉ nghe ở 127.0.0.1 hoặc cổng nội bộ, truy cập qua SSH / VPN.

#SLO và cảnh báo

Hệ thống không cần "không bao giờ lỗi", mà cần đủ tốt theo một mục tiêu rõ ràng. Cách làm phổ biến từ sách Site Reliability Engineering của Google:

  • SLI (chỉ số): tỉ lệ request thành công và nhanh hơn 300ms.
  • SLO (mục tiêu): 99,5% request trong 30 ngày đạt chỉ số trên.
  • Error budget: 0,5% còn lại là "ngân sách lỗi". Còn ngân sách thì cứ deploy tính năng mới, sắp hết thì tập trung sửa độ ổn định.

99,9% nghe rất cao nhưng vẫn là khoảng 43 phút sự cố mỗi tháng. Mỗi số 9 thêm vào đắt hơn rất nhiều.

Đặt cảnh báo theo triệu chứng người dùng thấy (tỉ lệ lỗi tăng, p99 tăng, hàng đợi ứ đọng quá 10 phút), không theo nguyên nhân (CPU 80%). CPU 80% mà người dùng không bị ảnh hưởng thì không đáng đánh thức ai lúc 3 giờ sáng. Mỗi cảnh báo phải dẫn tới một hành động cụ thể, nếu không mọi người sẽ quen bỏ qua cảnh báo.

Câu hỏi nhanh. Độ trễ trung bình của API là 80ms, p99 là 4 giây. Kết luận nào đúng?

Một trang gọi 10 API thì xác suất ít nhất một API rơi vào nhóm 1% chậm nhất là khoảng 10%. Đuôi phân phối mới là thứ người dùng cảm nhận.

#Bài tập

Thêm khả năng quan sát cho một API

Viết một API nhỏ có hai endpoint giả (GET /notes/{id} nhanh, GET /report chậm và thỉnh thoảng lỗi), rồi thêm:

  • /livez và /readyz (kiểm database, ở đây giả lập được bật / tắt).
  • middleware đo RED, xuất ở 127.0.0.1:9090/metrics.
  • pprof cũng ở cổng nội bộ 127.0.0.1:9090.

Tạo tải, đọc metrics, và (tuỳ chọn) xem bằng Prometheus + Grafana.

Gợi ý từng bước

  1. Middleware đo: giống Logger ở bài 13 (bọc ResponseWriter để nhớ status), nhưng thay vì ghi log thì tăng counter và ghi histogram.
  2. Nhãn route lấy từ r.Pattern (Go 1.23+): sau khi mux khớp, nó là mẫu như "GET /notes/{id}", không phải đường dẫn thật.
  3. Hai server trong một chương trình: server chính ở :8080 chạy ở main, server nội bộ chạy trong một goroutine (bài 09).
  4. Tạo tải: một vòng for trong terminal gọi curl chạy nền là đủ, hoặc cài hey: go install github.com/rakyll/hey@latest.

main.go
package main

import (
    "context"
    "errors"
    "log"
    "math/rand/v2"
    "net/http"
    _ "net/http/pprof" // đăng ký /debug/pprof/* vào http.DefaultServeMux
    "strconv"
    "sync/atomic"
    "time"

    "github.com/prometheus/client_golang/prometheus"
    "github.com/prometheus/client_golang/prometheus/promauto"
    "github.com/prometheus/client_golang/prometheus/promhttp"
)

var (
    httpRequests = promauto.NewCounterVec(prometheus.CounterOpts{
        Name: "http_requests_total",
        Help: "Số request HTTP",
    }, []string{"method", "route", "status"})

    httpDuration = promauto.NewHistogramVec(prometheus.HistogramOpts{
        Name:    "http_request_duration_seconds",
        Help:    "Thời gian xử lý request",
        Buckets: prometheus.DefBuckets, // các mốc 5ms, 10ms, 25ms, ... 10s
    }, []string{"method", "route"})
)

type statusRecorder struct {
    http.ResponseWriter
    status int
}

func (s *statusRecorder) WriteHeader(code int) {
    s.status = code
    s.ResponseWriter.WriteHeader(code)
}

// metrics: middleware đo RED (Rate, Errors, Duration) cho mọi request
func metrics(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        rec := &statusRecorder{ResponseWriter: w, status: http.StatusOK}
        next.ServeHTTP(rec, r)
        route := r.Pattern // mẫu route đã khớp, ví dụ "GET /notes/{id}". Không dùng r.URL.Path (vô hạn giá trị)
        if route == "" {
            route = "không khớp"
        }
        httpRequests.WithLabelValues(r.Method, route, strconv.Itoa(rec.status)).Inc()
        httpDuration.WithLabelValues(r.Method, route).Observe(time.Since(start).Seconds())
    })
}

// Giả lập database: lúc khoẻ lúc không, để thử /readyz
var dbDown atomic.Bool

func pingDB(ctx context.Context) error {
    if dbDown.Load() {
        return errors.New("database không trả lời")
    }
    return nil
}

func main() {
    mux := http.NewServeMux()

    // Hai API giả: /notes nhanh, /report chậm và thỉnh thoảng lỗi
    mux.HandleFunc("GET /notes/{id}", func(w http.ResponseWriter, r *http.Request) {
        time.Sleep(time.Duration(2+rand.IntN(8)) * time.Millisecond) // 2-10ms
        w.Write([]byte(`{"id":` + r.PathValue("id") + `}`))
    })
    mux.HandleFunc("GET /report", func(w http.ResponseWriter, r *http.Request) {
        time.Sleep(time.Duration(100+rand.IntN(400)) * time.Millisecond) // 100-500ms
        if rand.IntN(10) == 0 {                                           // 10% lỗi
            http.Error(w, "lỗi", http.StatusInternalServerError)
            return
        }
        w.Write([]byte(`{"ok":true}`))
    })

    // Liveness: tiến trình còn sống. Không kiểm database
    mux.HandleFunc("GET /livez", func(w http.ResponseWriter, r *http.Request) {
        w.Write([]byte("ok"))
    })
    // Readiness: sẵn sàng nhận request chưa. Kiểm những thứ bắt buộc
    mux.HandleFunc("GET /readyz", func(w http.ResponseWriter, r *http.Request) {
        ctx, cancel := context.WithTimeout(r.Context(), time.Second)
        defer cancel()
        if err := pingDB(ctx); err != nil {
            http.Error(w, "chưa sẵn sàng: "+err.Error(), http.StatusServiceUnavailable)
            return
        }
        w.Write([]byte("ok"))
    })
    // Chỉ để thử: bật / tắt database giả
    mux.HandleFunc("POST /debug/db-down", func(w http.ResponseWriter, r *http.Request) {
        dbDown.Store(!dbDown.Load())
        w.Write([]byte("dbDown=" + strconv.FormatBool(dbDown.Load()) + "\n"))
    })

    // Cổng NỘI BỘ: metrics và pprof, chỉ nghe ở 127.0.0.1, không mở ra Internet
    go func() {
        internal := http.NewServeMux()
        internal.Handle("GET /metrics", promhttp.Handler())
        internal.Handle("/debug/pprof/", http.DefaultServeMux) // pprof đã tự đăng ký vào DefaultServeMux
        log.Println("nội bộ: http://127.0.0.1:9090/metrics và /debug/pprof/")
        log.Fatal(http.ListenAndServe("127.0.0.1:9090", internal))
    }()

    srv := &http.Server{Addr: ":8080", Handler: metrics(mux), ReadHeaderTimeout: 5 * time.Second}
    log.Println("API: http://localhost:8080")
    log.Fatal(srv.ListenAndServe())
}

Đọc metrics:

  • 200 request tới /notes/1, /notes/2... đều nằm chung một dòng route="GET /notes/{id}", không phải 200 dòng. Đó là lý do dùng r.Pattern.
  • /report: 28 thành công, 2 lỗi 500, tỉ lệ lỗi khoảng 7% (code giả lập 10%, ngẫu nhiên nên mỗi lần chạy mỗi khác).
  • Histogram đếm tích luỹ: le="0.25" là 9 nghĩa là 9 request xong trong 0,25 giây, le="0.5" là 30 nghĩa là cả 30 xong trong 0,5 giây. Trung bình = sum / count = 10,04 / 30 ≈ 0,33 giây. Prometheus tính p95 từ các bucket này.
  • Gọi /metrics qua cổng công khai 8080 ra 404: metrics chỉ có ở cổng nội bộ, đúng ý muốn.

Chạy docker compose up, mở Grafana, thêm data source Prometheus với địa chỉ http://prometheus:9090, rồi tạo biểu đồ với các truy vấn:

PromQL
