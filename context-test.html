Context và kiểm thử

context để huỷ / đặt thời hạn cho công việc, viết test dạng bảng, test HTTP, đo hiệu năng.

Học xong bài này bạn sẽ:
  • Truyền context xuyên suốt một request
  • Viết test dạng bảng (table-driven)
  • Chạy test với -race và đo coverage

#context: huỷ và hạn chót cho cả một chuỗi việc

Người dùng mở trang, request đi vào server, server gọi database và một API bên ngoài. Giữa chừng người dùng đóng tab. Mọi việc phía sau có nên tiếp tục không? Không: tốn tài nguyên cho một response không ai nhận.

context.Context là cách Go truyền tín hiệu huỷ, hạn chót và một ít dữ liệu đi theo request xuyên qua mọi tầng.

Giống AbortController: bạn tạo controller.signal, truyền vào fetch(url, { signal }), gọi controller.abort() để huỷ. Trong Go, ctx đóng vai signal và được truyền vào mọi hàm có I/O.

Quy ước bắt buộc

  • ctx context.Context là tham số đầu tiên của mọi hàm có gọi mạng, database, hoặc chạy lâu.
  • Không lưu ctx vào trong struct. Truyền nó qua tham số.
  • Trong HTTP handler, lấy ctx từ r.Context(): nó tự bị huỷ khi client ngắt kết nối.
  • Chỉ dùng context.Background() ở điểm khởi đầu: hàm main, test, việc nền.

Context hoạt động thế nào

Một ctx có method Done() trả về một channel. Channel đó bị đóng khi ctx bị huỷ (do ai đó gọi cancel(), hoặc hết giờ). Hàm làm việc lâu chỉ cần select (bài 9) giữa "việc xong" và "ctx.Done()". Chạy thử:

Go
package main

import (
    "context"
    "fmt"
    "time"
)

// Giả lập gọi dịch vụ tỷ giá: cần `d` thời gian mới có kết quả
func fetchRate(ctx context.Context, d time.Duration) (int, error) {
    select {
    case <-time.After(d): // làm xong
        return 25_400, nil
    case <-ctx.Done(): // bị huỷ hoặc hết giờ TRƯỚC khi làm xong
        return 0, ctx.Err() // ctx.Err() cho biết lý do
    }
}

func main() {
    // Tạo ctx tự hết hạn sau 1 giây. context.Background() là ctx gốc, không bao giờ hết hạn
    ctx, cancel := context.WithTimeout(context.Background(), time.Second)
    defer cancel() // LUÔN gọi cancel khi xong việc, để dọn bộ đếm giờ

    rate, err := fetchRate(ctx, 200*time.Millisecond) // nhanh: kịp trước hạn
    fmt.Println("lần 1:", rate, err)

    rate, err = fetchRate(ctx, 3*time.Second) // chậm: hết 1 giây là bị cắt
    fmt.Println("lần 2:", rate, err)

    // Huỷ bằng tay: giống controller.abort() của AbortController
    ctx2, cancel2 := context.WithCancel(context.Background())
    go func() {
        time.Sleep(100 * time.Millisecond)
        cancel2() // một nơi khác quyết định huỷ
    }()
    rate, err = fetchRate(ctx2, 3*time.Second)
    fmt.Println("lần 3:", rate, err)
}
Terminal — kết quả khi chạy
lần 1: 25400 <nil>
lần 2: 0 context deadline exceeded
lần 3: 0 context canceled

Hai lỗi có sẵn: context.DeadlineExceeded (in ra "context deadline exceeded": hết giờ) và context.Canceled ("context canceled": bị huỷ). Kiểm tra bằng errors.Is(err, context.DeadlineExceeded). Mọi thư viện mạng, database của Go đều làm giống fetchRate ở trên: nhận ctx, dừng khi ctx bị huỷ.

Đặt thời hạn cho một bước

Cách dùng thật trong service (trích đoạn): request còn bao nhiêu thời gian không biết, nhưng bước gọi dịch vụ tỷ giá thì không được quá 2 giây.

Go · trích đoạn
func (s *Service) Quote(ctx context.Context, id int64) (Price, error) {
    // ctx con: hết hạn sau 2 giây, HOẶC khi ctx cha (của request) bị huỷ, cái nào đến trước
    ctx, cancel := context.WithTimeout(ctx, 2*time.Second)
    defer cancel()

    rate, err := s.fx.Rate(ctx, "USD", "VND") // truyền ctx con xuống
    if err != nil {
        if errors.Is(err, context.DeadlineExceeded) {
            return Price{}, fmt.Errorf("dịch vụ tỷ giá quá chậm: %w", err)
        }
        return Price{}, err
    }
    // ...
}

Hạn chót lồng nhau: nếu request gốc còn 1 giây mà bạn đặt WithTimeout(ctx, 2*time.Second), ctx con vẫn hết hạn sau 1 giây. Context con không bao giờ sống lâu hơn context cha.

Tự kiểm tra ctx trong việc chạy lâu

Vòng lặp xử lý hàng triệu dòng không tự dừng khi ctx bị huỷ. Thỉnh thoảng hỏi ctx.Err(): trả nil là còn được chạy (trích đoạn):

Go · trích đoạn
func exportCSV(ctx context.Context, w io.Writer, rows []Row) error {
    for i, r := range rows {
        if i%1000 == 0 { // thỉnh thoảng kiểm tra xem đã bị huỷ chưa
            if err := ctx.Err(); err != nil {
                return err
            }
        }
        writeRow(w, r)
    }
    return nil
}

Giá trị đi theo request

Context còn mang theo được vài giá trị, ví dụ mã của request để mọi dòng log của cùng một request có chung một mã (bài 27):

Go
package main

import (
    "context"
    "fmt"
)

type ctxKey string // kiểu riêng, tránh trùng khoá với package khác

const requestIDKey ctxKey = "request_id"

// Trả về ctx MỚI có thêm giá trị. ctx cũ không bị sửa
func WithRequestID(ctx context.Context, id string) context.Context {
    return context.WithValue(ctx, requestIDKey, id)
}

func RequestID(ctx context.Context) string {
    id, _ := ctx.Value(requestIDKey).(string) // Value trả về any, đổi sang string (bài 06)
    return id
}

// Hàm ở tầng sâu bên trong: không cần tham số requestID riêng, lấy từ ctx
func saveToDB(ctx context.Context) {
    fmt.Println("[" + RequestID(ctx) + "] lưu vào database")
}

func main() {
    ctx := WithRequestID(context.Background(), "req-7f3a")
    saveToDB(ctx)
}
Terminal — kết quả khi chạy
[req-7f3a] lưu vào database

Chỉ đặt vào context những thứ thuộc về request: request id, thông tin người dùng đã xác thực, trace id. Không dùng context để truyền tham số tuỳ chọn hay phụ thuộc (database, logger cấu hình): như vậy hàm có tham số ẩn, rất khó đọc và test.

#Kiểm thử: có sẵn trong Go

Không cần cài Jest. Quy tắc:

  • File test nằm cạnh file code, cùng thư mục, tên kết thúc bằng _test.go.
  • Hàm test tên bắt đầu bằng Test, nhận một tham số t *testing.T.
  • Go không có expect(...).toBe(...). Bạn tự so sánh bằng if, sai thì gọi t.Errorf.

Dùng lại dự án sobaitap ở bài 8 (có grade/grade.go với hàm Classify). Tạo thêm file grade/grade_test.go:

grade/grade_test.go
package grade

import "testing"

func TestClassify(t *testing.T) {
    got := Classify(8.5)
    if got != "Giỏi" {
        t.Errorf("Classify(8.5) = %q, muốn %q", got, "Giỏi")
    }
}

Test dạng bảng: phong cách chuẩn của Go

Thay vì viết 10 hàm test gần giống nhau, liệt kê các trường hợp trong một bảng (một slice struct) rồi chạy vòng lặp. Thay toàn bộ grade/grade_test.go bằng:

grade/grade_test.go
package grade

import "testing"

func TestClassify(t *testing.T) {
    // Bảng: mỗi dòng là một trường hợp, gồm tên, đầu vào, kết quả mong muốn
    tests := []struct {
        name  string
        score float64
        want  string
    }{
        {"giỏi", 8.5, "Giỏi"},
        {"vừa đủ giỏi", 8, "Giỏi"},
        {"đạt", 6, "Đạt"},
        {"biên dưới đạt", 5, "Đạt"},
        {"chưa đạt", 4.9, "Chưa đạt"},
        {"điểm 0", 0, "Chưa đạt"},
    }
    for _, tc := range tests {
        // t.Run tạo một test con mang tên tc.name, giống it("...") trong Jest
        t.Run(tc.name, func(t *testing.T) {
            if got := Classify(tc.score); got != tc.want {
                t.Errorf("Classify(%v) = %q, muốn %q", tc.score, got, tc.want)
            }
        })
    }
}

Test có database thật

Fake (bài 6) phù hợp để test nghiệp vụ. Nhưng câu SQL thì phải test với database thật: fake không biết câu SQL của bạn sai cú pháp hay thiếu index. Hai cách phổ biến:

  • Chạy Postgres bằng Docker trong CI, mỗi test tạo schema riêng hoặc bọc trong một transaction rồi rollback.
  • Thư viện testcontainers-go: test tự bật container Postgres, xong tự tắt.

Nhiều đội chạy toàn bộ test API với database thật, mỗi test một database sạch. Chậm hơn fake, nhưng bắt được những lỗi chỉ database thật mới có: ràng buộc UNIQUE, khoá ngoại, trigger.

#Bài tập

Test bảng cho hàm phân trang

Viết test dạng bảng cho hàm pageOf ở bài tập bài 4 (phân trang trên slice). Các trường hợp: trang đầu, trang giữa, trang cuối thiếu phần tử, trang vượt quá, page = 0, size âm, danh sách rỗng. Chạy với -cover để xem bao nhiêu phần trăm code được test chạy qua.

Gợi ý từng bước

  1. Tạo dự án mới: mkdir paging && cd paging && go mod init paging.
  2. Tạo paging.go (package main cũng được, test được hàm trong package main) chứa hàm pageOf từ bài 4 và một hàm main rỗng.
  3. Tạo paging_test.go cùng thư mục, cùng package main. Viết bảng như TestClassify ở trên, mỗi dòng có page, size, và want []string.
  4. So sánh hai slice bằng slices.Equal(got, want) (không dùng == được với slice).
  5. Chạy go test -v -cover .
Xem lời giải
paging.go
package main

func pageOf(items []string, page, size int) []string {
    if page < 1 || size < 1 {
        return []string{}
    }
    start := (page - 1) * size
    if start >= len(items) {
        return []string{}
    }
    end := min(start+size, len(items))
    return items[start:end]
}

func main() {}
paging_test.go
package main

import (
    "slices"
    "testing"
)

func TestPageOf(t *testing.T) {
    items := []string{"a", "b", "c", "d", "e"}
    tests := []struct {
        name       string
        items      []string
        page, size int
        want       []string
    }{
        {"trang đầu", items, 1, 2, []string{"a", "b"}},
        {"trang giữa", items, 2, 2, []string{"c", "d"}},
        {"trang cuối thiếu", items, 3, 2, []string{"e"}},
        {"vượt quá", items, 4, 2, []string{}},
        {"page 0", items, 0, 2, []string{}},
        {"size âm", items, 1, -1, []string{}},
        {"rỗng", nil, 1, 10, []string{}},
    }
    for _, tc := range tests {
        t.Run(tc.name, func(t *testing.T) {
            got := pageOf(tc.items, tc.page, tc.size)
            if !slices.Equal(got, tc.want) {
                t.Errorf("pageOf(page=%d, size=%d) = %v, muốn %v", tc.page, tc.size, got, tc.want)
            }
        })
    }
}

$ go test -cover .
ok  	paging	0.004s	coverage: 100.0% of statements

Giải thích: 100% nghĩa là mọi câu lệnh của pageOf đều được ít nhất một trường hợp chạy qua. Thử xoá dòng "vượt quá" khỏi bảng rồi chạy lại: độ phủ giảm, vì nhánh start >= len(items) không còn ai chạy tới. Xem từng dòng nào chưa được test chạy tới: go test -coverprofile=c.out . && go tool cover -html=c.out (mở trình duyệt, dòng đỏ là chưa chạy).

Hàm có hạn chót

Viết slowSquare(ctx context.Context, n int) (int, error): bình thường mất 1 giây mới trả về n * n, nhưng nếu ctx bị huỷ trước thì dừng ngay và trả lỗi của ctx. Viết test chứng minh: với timeout 100ms, hàm trả về context.DeadlineExceeded trong chưa tới 200ms.

Gợi ý từng bước

  1. Thân hàm giống hệt fetchRate ở đầu bài: select giữa time.After(time.Second) và ctx.Done().
  2. Trong test: tạo ctx bằng context.WithTimeout(context.Background(), 100*time.Millisecond), ghi start := time.Now(), gọi hàm.
  3. Kiểm tra hai điều: lỗi đúng loại (errors.Is), và time.Since(start) nhỏ hơn 200ms.
Xem lời giải
square.go
package main

import (
    "context"
    "time"
)

func slowSquare(ctx context.Context, n int) (int, error) {
    select {
    case <-time.After(time.Second): // làm đủ 1 giây
        return n * n, nil
    case <-ctx.Done(): // bị huỷ trước
        return 0, ctx.Err()
    }
}

func main() {}
square_test.go
package main

import (
    "context"
    "errors"
    "testing"
    "time"
)

func TestSlowSquareTimeout(t *testing.T) {
    ctx, cancel := context.WithTimeout(context.Background(), 100*time.Millisecond)
    defer cancel()

    start := time.Now()
    _, err := slowSquare(ctx, 3)

    if !errors.Is(err, context.DeadlineExceeded) {
        t.Fatalf("err = %v, muốn DeadlineExceeded", err) // Fatalf: dừng test, các dòng sau vô nghĩa
    }
    if d := time.Since(start); d > 200*time.Millisecond {
        t.Errorf("mất %v, quá lâu", d)
    }
}

func TestSlowSquareOK(t *testing.T) {
    got, err := slowSquare(context.Background(), 3) // không có hạn: chạy đủ 1 giây
    if err != nil || got != 9 {
        t.Errorf("slowSquare(3) = %d, %v; muốn 9, nil", got, err)
    }
}
