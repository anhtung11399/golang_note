Cache và Redis

Khi nào cần cache, cache-aside, TTL, xoá cache, cache stampede, giới hạn tần suất bằng Redis.

Học xong bài này bạn sẽ:
  • Áp dụng cache-aside với Redis
  • Biết các cách cache làm sai dữ liệu
  • Chặn hàng nghìn request trùng bằng singleflight

#Khi nào cần cache

Cache là giữ sẵn kết quả của một việc tốn kém để lần sau trả ngay. Nhưng cache cũng là nguồn gốc của rất nhiều lỗi "dữ liệu cũ". Câu đùa nổi tiếng của Phil Karlton: "Chỉ có hai việc khó trong khoa học máy tính: xoá cache cho đúng và đặt tên."

Chỉ cache khi đo được là cần:

  • Dữ liệu được đọc nhiều hơn ghi rất nhiều (cấu hình, danh mục, trang chủ, hồ sơ công khai).
  • Tính toán đắt (báo cáo tổng hợp, gọi API bên ngoài có tính phí hoặc chậm).
  • Chấp nhận được việc dữ liệu cũ đi vài giây / vài phút.

Trước khi thêm cache, hãy thử thêm index hoặc sửa N+1 (bài 16). Một truy vấn 0,1ms có index thì không cần cache. Cache che đi một truy vấn chậm, nhưng không sửa được nó.

#Các tầng cache trong một hệ thống

Bạn đã quen với tầng đầu: Cache-Control: max-age=31536000, immutable cho file JS có hash trong tên, và React Query / SWR giữ dữ liệu API trong bộ nhớ của tab. Backend thêm các tầng phía sau.

#Redis

Redis là một kho key-value chạy trong RAM, mỗi lệnh thường mất dưới 1ms. Ngoài làm cache, nó còn được dùng cho: phiên đăng nhập, đếm giới hạn tần suất, khoá phân tán, hàng đợi đơn giản, bảng xếp hạng.

Terminal
docker run -d --name redis -p 6379:6379 redis:7
docker exec -it redis redis-cli
redis-cli
SET user:42:name "Lan" EX 60     # lưu, hết hạn sau 60 giây
GET user:42:name                  # "Lan"
TTL user:42:name                  # còn bao nhiêu giây
INCR rl:login:1.2.3.4             # tăng bộ đếm (nguyên tử), trả về giá trị mới
DEL user:42:name
Go
import "github.com/redis/go-redis/v9"

rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
// Hoặc từ URL: opt, _ := redis.ParseURL(os.Getenv("REDIS_URL")); rdb := redis.NewClient(opt)

err := rdb.Set(ctx, "user:42:name", "Lan", time.Minute).Err()
name, err := rdb.Get(ctx, "user:42:name").Result()
if errors.Is(err, redis.Nil) { // khoá không tồn tại
    // ...
}

#Cache-aside: mẫu dùng nhiều nhất

Go
func (s *Service) ClassSummary(ctx context.Context, classID int64) (Summary, error) {
    key := fmt.Sprintf("class:%d:summary:v1", classID)

    if b, err := s.rdb.Get(ctx, key).Bytes(); err == nil {
        var sum Summary
        if json.Unmarshal(b, &sum) == nil {
            return sum, nil // hit
        }
    } else if !errors.Is(err, redis.Nil) {
        // Redis lỗi: ghi log rồi đi tiếp vào database, KHÔNG làm hỏng request
        slog.WarnContext(ctx, "redis get", "err", err)
    }

    sum, err := s.store.ComputeSummary(ctx, classID)
    if err != nil {
        return Summary{}, err
    }
    if b, err := json.Marshal(sum); err == nil {
        s.rdb.Set(ctx, key, b, 5*time.Minute) // lỗi ghi cache cũng không làm hỏng request
    }
    return sum, nil
}

Cache phải là thứ có cũng được, mất cũng được. Redis sập thì hệ thống chậm đi, không được chết theo. Và luôn có TTL: dù bạn quên xoá cache ở đâu đó, dữ liệu sai cũng chỉ tồn tại tối đa bằng TTL.

Hậu tố :v1 trong khoá: khi đổi cấu trúc Summary, tăng lên v2, bản code mới không đọc nhầm dữ liệu cache dạng cũ.

#Xoá cache khi dữ liệu đổi

Go
func (s *Service) Submit(ctx context.Context, sub Submission) error {
    if err := s.store.Submit(ctx, sub); err != nil { // 1. ghi database trước
        return err
    }
    s.rdb.Del(ctx, fmt.Sprintf("class:%d:summary:v1", sub.ClassID)) // 2. rồi xoá cache
    return nil
}

Vì sao xoá thay vì ghi giá trị mới vào cache? Vì hai request cập nhật cùng lúc có thể ghi cache theo thứ tự ngược với database, để lại giá trị cũ trong cache. Xoá thì lần đọc sau tự lấy giá trị đúng từ database.

Vẫn còn một khe hở nhỏ: một request đọc lấy giá trị cũ từ database, request khác ghi và xoá cache, rồi request đọc kia mới ghi giá trị cũ vào cache. TTL giới hạn thời gian sai. Với dữ liệu tuyệt đối không được sai (số dư, tồn kho, quyền truy cập), đừng cache, hoặc chỉ dùng cache để hiển thị, còn quyết định thì luôn đọc từ database.

#Cache stampede: hàng nghìn request cùng tính lại

Trang chủ được cache 60 giây, 2.000 request mỗi giây. Đúng lúc cache hết hạn, 2.000 request cùng thấy "miss" và cùng chạy truy vấn nặng. Database quá tải, chậm lại, nhiều request hơn bị miss... Đây gọi là cache stampede (hay thundering herd).

Cách chặn trong một tiến trình: singleflight. Các lời gọi cùng khoá đang chạy thì chờ và dùng chung kết quả của lời gọi đầu tiên.

Go
import "golang.org/x/sync/singleflight"

type Service struct {
    group singleflight.Group
    // ...
}

func (s *Service) HomeFeed(ctx context.Context) (Feed, error) {
    v, err, _ := s.group.Do("home-feed", func() (any, error) {
        return s.loadHomeFeed(ctx) // chỉ MỘT goroutine chạy, những cái khác chờ kết quả này
    })
    if err != nil {
        return Feed{}, err
    }
    return v.(Feed), nil
}

Các cách khác: thêm ngẫu nhiên vào TTL (5 phút ± 30 giây) để các khoá không hết hạn cùng lúc, và làm mới cache ở nền trước khi hết hạn.

Package singleflight vốn nằm trong mã nguồn của groupcache, thư viện cache do Brad Fitzpatrick viết khi ở Google, dùng cho dl.google.com. Nó gom các yêu cầu trùng nhau để chỉ một yêu cầu thật sự đi tới nguồn.

#Cache trong bộ nhớ của server

Với dữ liệu nhỏ, rất nóng, ít đổi (cấu hình, danh sách môn học mặc định), map trong bộ nhớ có mutex nhanh hơn Redis nhiều (không qua mạng). Nhược điểm: mỗi bản server có bản riêng, không xoá đồng loạt được. Chỉ dùng với TTL ngắn và dữ liệu chấp nhận lệch giữa các máy.

#Giới hạn tần suất (rate limit)

Chặn dò mật khẩu, spam gửi OTP / email, một người dùng ngốn hết tài nguyên. Hai cách:

Trong một tiến trình: token bucket

Go
import "golang.org/x/time/rate"

// Mỗi giây thêm 5 "vé", tối đa dồn 10 vé: cho phép bùng 10 request rồi 5 request mỗi giây
lim := rate.NewLimiter(5, 10)
if !lim.Allow() {
    w.Header().Set("Retry-After", "1")
    http.Error(w, "Quá nhiều yêu cầu", http.StatusTooManyRequests)
    return
}

Dùng chung nhiều server: đếm trong Redis

Go
// Cửa sổ cố định: tối đa 5 lần đăng nhập sai mỗi 15 phút cho mỗi email
func (s *Service) allowLogin(ctx context.Context, email string) (bool, error) {
    key := "rl:login:" + email
    n, err := s.rdb.Incr(ctx, key).Result() // INCR là nguyên tử
    if err != nil {
        return true, err // Redis lỗi: tuỳ chính sách, ở đây cho qua và ghi log
    }
    if n == 1 {
        s.rdb.Expire(ctx, key, 15*time.Minute) // lần đầu trong cửa sổ thì đặt hạn
    }
    return n <= 5, nil
}

Đoạn trên có điểm yếu nhỏ: nếu server chết giữa INCR và EXPIRE, khoá không bao giờ hết hạn và người đó bị khoá mãi. Cách chắc chắn là gộp hai lệnh vào một script Lua hoặc một MULTI/EXEC pipeline để Redis chạy nguyên khối. Đây chính là loại lỗi "hai bước rời nhau" bạn đã gặp ở database.

Các dịch vụ lớn trả về header cho client biết giới hạn: GitHub API dùng X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset. Có một bản nháp chuẩn IETF cho header RateLimit đang được nhiều nơi áp dụng.

#Cache HTTP cho client

Go
// Dữ liệu công khai, ít đổi: cho CDN và trình duyệt cache 5 phút
w.Header().Set("Cache-Control", "public, max-age=300")

// Dữ liệu riêng của người dùng: CDN không được cache
w.Header().Set("Cache-Control", "private, no-store")

Một lỗi nghiêm trọng có thật: CDN cache nhầm response chứa dữ liệu cá nhân (vì thiếu private / no-store), và người dùng khác truy cập cùng URL nhận được trang của người khác. Mọi response cần đăng nhập nên mặc định Cache-Control: no-store.

Câu hỏi nhanh. Redis bị sập 5 phút. Với mẫu cache-aside viết đúng, chuyện gì xảy ra?

Cache lỗi thì bỏ qua và đọc nguồn sự thật. Đó là lý do cần theo dõi tải database và có rate limit, phòng khi cache biến mất đột ngột.

#Bài tập

Cache có singleflight và TTL lệch ngẫu nhiên

Viết hàm generic GetOrLoad[T any](ctx, rdb, group, key, ttl, load func(ctx) (T, error)) (T, error): thử Redis, miss thì dùng singleflight gọi load, ghi vào Redis với TTL cộng thêm ngẫu nhiên tối đa 10%. Redis lỗi thì vẫn trả được kết quả từ load.

Xem lời giải
Go
func GetOrLoad[T any](ctx context.Context, rdb *redis.Client, g *singleflight.Group,
    key string, ttl time.Duration, load func(context.Context) (T, error)) (T, error) {

    var zero T
    if b, err := rdb.Get(ctx, key).Bytes(); err == nil {
        var v T
        if json.Unmarshal(b, &v) == nil {
            return v, nil
        }
    }
    v, err, _ := g.Do(key, func() (any, error) {
        val, err := load(ctx)
        if err != nil {
            return nil, err
        }
        if b, err := json.Marshal(val); err == nil {
            jitter := time.Duration(rand.Int64N(int64(ttl / 10))) // math/rand/v2
            rdb.Set(ctx, key, b, ttl+jitter)
        }
        return val, nil
    })
    if err != nil {
        return zero, err
    }
    return v.(T), nil
}

Lưu ý: hàm load chạy với ctx của request đầu tiên. Nếu request đó bị huỷ, các request đang chờ cũng nhận lỗi theo. Ở hệ thống thật người ta dùng context.WithoutCancel(ctx) (Go 1.21+) kèm timeout riêng cho việc tải chung.
