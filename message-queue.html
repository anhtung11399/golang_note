Message queue: Kafka, NATS, RabbitMQ

Queue và log, topic / partition / consumer group, at-least-once, thứ tự, retry và DLQ, viết producer / consumer bằng Go, chọn công cụ.

Học xong bài này bạn sẽ:
  • Hiểu Kafka hoạt động thế nào
  • Viết consumer Go xử lý đúng khi lỗi
  • Chọn hàng đợi phù hợp

#Khi nào hàng đợi bằng Postgres không còn đủ

Bài 23 làm hàng đợi bằng một bảng jobs với FOR UPDATE SKIP LOCKED. Cách đó đủ cho rất nhiều hệ thống: vài trăm việc mỗi giây, một nhóm worker. Bạn cần một message broker riêng khi:

  • Nhiều dịch vụ cùng nghe một sự kiện. "Bài đã nộp" → dịch vụ thông báo gửi push, dịch vụ thống kê cập nhật biểu đồ, dịch vụ AI xếp hàng chấm thử. Mỗi bên đọc theo tốc độ riêng, thêm bên thứ tư không cần sửa bên gửi.
  • Lượng lớn: hàng chục nghìn sự kiện mỗi giây (log, click, vị trí xe).
  • Cần đọc lại quá khứ: dịch vụ mới muốn xử lý lại toàn bộ sự kiện 7 ngày qua.
  • Giữ thứ tự theo từng đối tượng: mọi sự kiện của một đơn hàng phải xử lý đúng thứ tự.

#Kafka hoạt động thế nào

Năm khái niệm, hiểu là đọc được mọi tài liệu Kafka:

  • Topic: một dòng sự kiện có tên, ví dụ submissions.
  • Partition: topic được chia thành N phần. Mỗi partition là một file chỉ ghi thêm vào cuối, mỗi tin có số thứ tự gọi là offset. Thứ tự chỉ được bảo đảm trong một partition.
  • Key: tin nhắn có key (ví dụ student_id) luôn vào cùng một partition (băm key). Vì vậy mọi sự kiện của một học sinh được xử lý đúng thứ tự.
  • Consumer group: một nhóm consumer cùng tên chia nhau các partition. Mỗi partition chỉ được một consumer trong nhóm đọc. Nhóm khác đọc độc lập.
  • Commit offset: consumer báo "tôi đã xử lý tới offset 1042". Khởi động lại thì đọc tiếp từ đó.

Số partition là giới hạn trên của số consumer chạy song song trong một nhóm. Đặt từ đầu nhiều hơn mức cần (ví dụ 12 hoặc 24), vì tăng partition sau này làm thay đổi partition của các key (mất thứ tự trong lúc chuyển).

Producer bằng Go

Hai thư viện phổ biến: github.com/twmb/franz-go (nhanh, đầy đủ, nhiều đội mới chọn) và github.com/segmentio/kafka-go (API đơn giản). Bài này dùng franz-go.

Terminal

producer/main.go
package main

import (
    "context"
    "encoding/json"
    "fmt"
    "log"
    "strconv"
    "time"

    "github.com/twmb/franz-go/pkg/kgo"
)

type SubmissionEvent struct {
    EventID      string    `json:"eventId"` // để consumer chống xử lý trùng
    StudentID    int64     `json:"studentId"`
    AssignmentID int64     `json:"assignmentId"`
    At           time.Time `json:"at"`
}

func main() {
    cl, err := kgo.NewClient(
        kgo.SeedBrokers("localhost:9092"),
        kgo.DefaultProduceTopic("submissions"),
        kgo.RequiredAcks(kgo.AllISRAcks()), // chỉ coi là gửi xong khi mọi bản sao đã nhận
        // idempotent producer bật sẵn: gửi lại do lỗi mạng không tạo tin trùng
    )
    if err != nil {
        log.Fatal(err)
    }
    defer cl.Close()

    ctx := context.Background()
    for i := 1; i <= 6; i++ {
        ev := SubmissionEvent{
            EventID:      fmt.Sprintf("sub-%d", i),
            StudentID:    int64(i%3 + 1), // 3 học sinh
            AssignmentID: 9,
            At:           time.Now(),
        }
        b, _ := json.Marshal(ev)
        rec := &kgo.Record{Key: []byte(strconv.FormatInt(ev.StudentID, 10)), Value: b}

        // ProduceSync: chờ broker xác nhận. Bản thật thường dùng Produce (bất đồng bộ, có callback) để nhanh hơn
        res := cl.ProduceSync(ctx, rec)
        if err := res.FirstErr(); err != nil {
            log.Fatal(err)
        }
        r := res[0].Record
        fmt.Printf("gửi %s học sinh %d → partition %d offset %d\n", ev.EventID, ev.StudentID, r.Partition, r.Offset)
    }
}

Consumer bằng Go

consumer/main.go
package main

import (
    "context"
    "encoding/json"
    "log/slog"
    "os/signal"
    "syscall"

    "github.com/twmb/franz-go/pkg/kgo"
)

type SubmissionEvent struct {
    EventID   string `json:"eventId"`
    StudentID int64  `json:"studentId"`
}

func main() {
    ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
    defer stop()

    cl, err := kgo.NewClient(
        kgo.SeedBrokers("localhost:9092"),
        kgo.ConsumerGroup("notify"),
        kgo.ConsumeTopics("submissions"),
        kgo.DisableAutoCommit(), // TỰ commit sau khi xử lý xong, không để thư viện commit trước
    )
    if err != nil {
        panic(err)
    }
    defer cl.Close()

    for {
        fetches := cl.PollFetches(ctx)
        if fetches.IsClientClosed() || ctx.Err() != nil {
            return
        }
        fetches.EachError(func(t string, p int32, err error) {
            slog.Error("fetch", "topic", t, "partition", p, "err", err)
        })

        fetches.EachRecord(func(r *kgo.Record) {
            var ev SubmissionEvent
            if err := json.Unmarshal(r.Value, &ev); err != nil {
                slog.Error("tin hỏng, bỏ qua", "offset", r.Offset, "err", err) // không để 1 tin hỏng chặn cả partition
                return
            }
            if err := handle(ctx, ev); err != nil {
                // xem phần "Lỗi và thử lại" bên dưới
                slog.Error("xử lý lỗi", "event", ev.EventID, "err", err)
            }
            slog.Info("đã xử lý", "event", ev.EventID, "partition", r.Partition, "offset", r.Offset)
        })

        // Xử lý xong cả lô mới commit. Sập giữa chừng → lần sau đọc lại từ offset cũ
        if err := cl.CommitUncommittedOffsets(ctx); err != nil {
            slog.Error("commit", "err", err)
        }
    }
}

func handle(ctx context.Context, ev SubmissionEvent) error { return nil }

#Giao ít nhất một lần, và cái giá của nó

Consumer xử lý xong tin, chuẩn bị commit thì sập. Lần sau nó đọc lại tin đó. Đây là at-least-once: không mất tin, nhưng có thể nhận trùng. Ba mức giao nhận:

MứcCách đạtHậu quả
At-most-oncecommit trước, xử lý sausập giữa chừng → mất tin
At-least-oncexử lý trước, commit sausập giữa chừng → xử lý trùng. Dùng cái này, và làm xử lý idempotent
Exactly-onceKafka transaction (đọc - ghi Kafka - commit trong một transaction)chỉ đúng khi cả đầu vào và đầu ra đều là Kafka. Ghi ra database / gửi email thì vẫn cần idempotent

Làm xử lý idempotent: ghi event_id đã xử lý vào database trong cùng transaction với việc chính.

Go · trích đoạn
func handle(ctx context.Context, pool *pgxpool.Pool, ev SubmissionEvent) error {
    tx, err := pool.Begin(ctx)
    if err != nil {
        return err
    }
    defer tx.Rollback(ctx)

    tag, err := tx.Exec(ctx,
        `INSERT INTO processed_events (consumer, event_id) VALUES ('stats', $1) ON CONFLICT DO NOTHING`, ev.EventID)
    if err != nil {
        return err
    }
    if tag.RowsAffected() == 0 {
        return nil // đã xử lý rồi (tin trùng) → bỏ qua
    }
    if _, err := tx.Exec(ctx,
        `UPDATE class_stats SET submitted = submitted + 1 WHERE assignment_id = $1`, ev.AssignmentID); err != nil {
        return err
    }
    return tx.Commit(ctx)
}

Với việc ra bên ngoài (gửi email, gọi API thanh toán), không có "cùng transaction". Dùng idempotency key của bên kia nếu có (nhiều API thanh toán nhận Idempotency-Key), hoặc ghi "đang gửi" trước, gửi, rồi ghi "đã gửi", chấp nhận hiếm khi bị gửi trùng.

#Lỗi và thử lại: retry, DLQ

Tin xử lý lỗi thì làm gì? Không commit thì cả partition bị kẹt ở tin đó (vì offset là một con số, không bỏ qua được một tin ở giữa). Cách làm chuẩn:

Go · trích đoạn
type permanent struct{ error } // lỗi không thể sửa bằng thử lại: dữ liệu sai, bài không tồn tại

func process(ctx context.Context, cl *kgo.Client, r *kgo.Record) {
    var err error
    for attempt := 1; attempt <= 3; attempt++ {
        err = handleRecord(ctx, r)
        var p permanent
        if err == nil || errors.As(err, &p) {
            break
        }
        time.Sleep(time.Duration(attempt*attempt) * 100 * time.Millisecond) // 100ms, 400ms, 900ms
    }
    if err == nil {
        return
    }
    // Không chặn partition: chuyển tin sang topic khác kèm lý do, rồi coi như đã xử lý
    out := &kgo.Record{
        Topic: "submissions.dlq",
        Key:   r.Key,
        Value: r.Value,
        Headers: []kgo.RecordHeader{
            {Key: "error", Value: []byte(err.Error())},
            {Key: "source-offset", Value: []byte(strconv.FormatInt(r.Offset, 10))},
        },
    }
    if e := cl.ProduceSync(ctx, out).FirstErr(); e != nil {
        panic(e) // không ghi được DLQ thì KHÔNG được commit: dừng lại, để lần sau xử lý lại
    }
}

Đặt cảnh báo khi DLQ có tin mới. DLQ mà không ai xem thì chỉ là thùng rác có tên đẹp. Có công cụ để đẩy tin trong DLQ quay lại topic chính sau khi sửa lỗi code.

#Thiết kế sự kiện

  • Tên ở thì quá khứ: submission.created, payment.succeeded. Sự kiện là điều đã xảy ra, không phải mệnh lệnh.
  • Luôn có: eventId (duy nhất, để chống trùng), type, occurredAt, phiên bản lược đồ.
  • Mang đủ dữ liệu hay chỉ id? Chỉ id (submissionId: 42) thì consumer phải gọi lại API để lấy dữ liệu, dễ bị dữ liệu đã đổi. Mang đủ dữ liệu (ảnh chụp lúc xảy ra) thì consumer độc lập hơn. Thường mang đủ dữ liệu mà consumer cần, không mang dữ liệu nhạy cảm.
  • Chỉ thêm trường, không xoá / đổi nghĩa, giống REST API. Consumer cũ phải đọc được tin mới. Đội lớn dùng schema registry với Protobuf / Avro để kiểm tra điều này tự động.
  • Gửi sự kiện cùng lúc ghi database thế nào cho không mất? Outbox (bài 23): ghi sự kiện vào bảng outbox cùng transaction, một tiến trình khác đọc outbox và đẩy lên Kafka.

#NATS: nhẹ và nhanh

NATS là một file chạy viết bằng Go, khởi động trong mili giây, dùng ít RAM. Có hai lớp: Core NATS (bắn và quên, không lưu, cực nhanh) và JetStream (lưu lại, có consumer, giống Kafka nhưng đơn giản hơn).

Terminal
docker run -d --name nats -p 4222:4222 nats:2 -js   # -js: bật JetStream
go get github.com/nats-io/nats.go
main.go
package main

import (
    "context"
    "fmt"
    "log"
    "time"

    "github.com/nats-io/nats.go"
    "github.com/nats-io/nats.go/jetstream"
)

func main() {
    nc, err := nats.Connect(nats.DefaultURL)
    if err != nil {
        log.Fatal(err)
    }
    defer nc.Drain()

    js, _ := jetstream.New(nc)
    ctx := context.Background()

    // Stream: lưu mọi tin có subject bắt đầu bằng "submissions."
    js.CreateOrUpdateStream(ctx, jetstream.StreamConfig{
        Name:     "SUBMISSIONS",
        Subjects: []string{"submissions.>"},
        MaxAge:   7 * 24 * time.Hour,
    })

    // Consumer bền (durable): nhớ đã đọc tới đâu, nhiều bản cùng tên chia nhau việc
    cons, _ := js.CreateOrUpdateConsumer(ctx, "SUBMISSIONS", jetstream.ConsumerConfig{
        Durable:    "notify",
        AckPolicy:  jetstream.AckExplicitPolicy,
        MaxDeliver: 5,                // giao tối đa 5 lần
        AckWait:    30 * time.Second, // không ack trong 30 giây → giao lại
    })
    cc, _ := cons.Consume(func(m jetstream.Msg) {
        fmt.Printf("nhận %s: %s\n", m.Subject(), m.Data())
        m.Ack() // lỗi tạm thời thì m.NakWithDelay(time.Minute) để giao lại sau
    })
    defer cc.Stop()

    // Gửi: Publish chờ JetStream xác nhận đã lưu
    js.Publish(ctx, "submissions.class42", []byte(`{"studentId":7,"assignmentId":9}`))
    js.Publish(ctx, "submissions.class43", []byte(`{"studentId":8,"assignmentId":11}`))
    time.Sleep(200 * time.Millisecond)
}

#RabbitMQ: khi cần định tuyến

RabbitMQ mạnh ở định tuyến: producer gửi tới một exchange với một routing key, exchange chuyển tin tới các queue khớp. Hay gặp ở hệ thống cũ, hệ thống ngân hàng, và các việc cần ưu tiên, độ trễ, TTL từng tin.

Go · trích đoạn
import amqp "github.com/rabbitmq/amqp091-go"

conn, _ := amqp.Dial("amqp://guest:guest@localhost:5672/")
ch, _ := conn.Channel()
ch.ExchangeDeclare("events", "topic", true, false, false, false, nil)
q, _ := ch.QueueDeclare("email-jobs", true, false, false, false, nil)    // durable: sống sót khi khởi động lại
ch.QueueBind(q.Name, "submission.*", "events", false, nil)                 // nhận mọi sự kiện submission.*
ch.Qos(10, 0, false)                                                       // mỗi consumer giữ tối đa 10 tin chưa ack

msgs, _ := ch.Consume(q.Name, "", false /* autoAck */, false, false, false, nil)
for m := range msgs {
    if err := sendEmail(m.Body); err != nil {
        m.Nack(false, true) // trả lại queue để thử lại
        continue
    }
    m.Ack(false)
}

Grab, Uber, Shopee đều dùng Kafka làm "xương sống" sự kiện: mỗi chuyến xe, mỗi đơn hàng sinh ra hàng chục sự kiện, hàng trăm dịch vụ cùng đọc. Nhưng ở những công ty đó cũng có đội riêng chỉ để vận hành Kafka. Với sản phẩm nhỏ, chọn thứ đơn giản nhất đủ dùng.

Câu hỏi nhanh. Topic có 6 partition. Nhóm consumer chạy 10 bản. Bao nhiêu bản thực sự nhận tin?

Mỗi partition chỉ được một consumer trong nhóm đọc. Muốn 10 bản song song thì cần ít nhất 10 partition.

Câu hỏi nhanh. Mọi sự kiện của một đơn hàng phải xử lý đúng thứ tự. Producer nên làm gì?

Một partition thì đúng thứ tự nhưng không mở rộng được. Key theo đơn hàng: thứ tự đúng cho từng đơn, các đơn khác nhau vẫn xử lý song song.

Câu hỏi nhanh. Consumer commit offset ngay khi nhận tin, rồi mới xử lý. Server sập giữa lúc xử lý. Chuyện gì xảy ra?

Đây là at-most-once. Muốn không mất tin: xử lý xong mới commit, và làm xử lý idempotent để chịu được tin trùng.

#Bài tập

Consumer cập nhật thống kê, chịu được tin trùng

Viết consumer Kafka (nhóm stats) đọc topic submissions, tăng bộ đếm số bài đã nộp của mỗi bài tập trong Postgres. Chạy producer gửi cùng một sự kiện 2 lần: bộ đếm chỉ được tăng 1.

Gợi ý từng bước

  1. Bảng processed_events(consumer text, event_id text, PRIMARY KEY (consumer, event_id)) và assignment_stats(assignment_id bigint PRIMARY KEY, submitted int NOT NULL DEFAULT 0).
  2. Dùng hàm handle ở phần "Giao ít nhất một lần": INSERT event_id trước, trùng thì bỏ qua.
  3. Bộ đếm chưa có dòng: INSERT ... ON CONFLICT (assignment_id) DO UPDATE SET submitted = assignment_stats.submitted + 1.
  4. Xử lý xong cả lô mới CommitUncommittedOffsets.

package main

import (
    "context"
    "encoding/json"
    "log/slog"
    "os"
    "os/signal"
    "syscall"

    "github.com/jackc/pgx/v5/pgxpool"
    "github.com/twmb/franz-go/pkg/kgo"
)

type Event struct {
    EventID      string `json:"eventId"`
    AssignmentID int64  `json:"assignmentId"`
}

func handle(ctx context.Context, pool *pgxpool.Pool, ev Event) (bool, error) {
    tx, err := pool.Begin(ctx)
    if err != nil {
        return false, err
    }
    defer tx.Rollback(ctx)

    tag, err := tx.Exec(ctx,
        `INSERT INTO processed_events (consumer, event_id) VALUES ('stats', $1) ON CONFLICT DO NOTHING`, ev.EventID)
    if err != nil {
        return false, err
    }
    if tag.RowsAffected() == 0 {
        return false, nil // trùng
    }
    _, err = tx.Exec(ctx, `
        INSERT INTO assignment_stats (assignment_id, submitted) VALUES ($1, 1)
        ON CONFLICT (assignment_id) DO UPDATE SET submitted = assignment_stats.submitted + 1`, ev.AssignmentID)
    if err != nil {
        return false, err
    }
    return true, tx.Commit(ctx)
}

func main() {
    ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
    defer stop()

    pool, err := pgxpool.New(ctx, os.Getenv("DATABASE_URL"))
    if err != nil {
        panic(err)
    }
    cl, err := kgo.NewClient(
        kgo.SeedBrokers("localhost:9092"),
        kgo.ConsumerGroup("stats"),
        kgo.ConsumeTopics("submissions"),
        kgo.DisableAutoCommit(),
    )
    if err != nil {
        panic(err)
    }
    defer cl.Close()

    for {
        fs := cl.PollFetches(ctx)
        if fs.IsClientClosed() || ctx.Err() != nil {
            return
        }
        ok := true
        fs.EachRecord(func(r *kgo.Record) {
            var ev Event
            if json.Unmarshal(r.Value, &ev) != nil {
                return
            }
            applied, err := handle(ctx, pool, ev)
            if err != nil {
                slog.Error("lỗi", "event", ev.EventID, "err", err)
                ok = false
                return
            }
            slog.Info("sự kiện", "event", ev.EventID, "applied", applied)
        })
        if ok { // có lỗi thì không commit: lần poll sau... thực tế nên chuyển sang retry/DLQ như phần trên
            cl.CommitUncommittedOffsets(ctx)
        }
    }
}

Thiết kế: sự kiện cho luồng thanh toán

Người dùng mua gói Plus. Luồng: tạo đơn → ngân hàng báo có tiền (webhook) → kích hoạt gói → gửi email biên lai → cập nhật doanh thu ở trang quản trị. Hãy thiết kế: tên các sự kiện, key, nội dung, consumer nào nghe sự kiện nào, chỗ nào cần idempotent.

Gợi ý từng bước

  1. Sự kiện là điều đã xảy ra: đơn đã tạo, tiền đã vào, gói đã kích hoạt.
  2. Key nào để mọi sự kiện của một đơn theo thứ tự?
  3. Webhook ngân hàng có thể gửi lại nhiều lần. Kích hoạt gói có thể bị gọi hai lần.
  4. Email không nằm trong transaction được.
