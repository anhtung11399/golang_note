Xử lý lỗi kiểu Go

Lỗi là giá trị: if err != nil, bọc lỗi với %w, errors.Is / errors.As, lỗi nghiệp vụ, panic và recover.

Học xong bài này bạn sẽ:
  • Trả và kiểm tra lỗi đúng cách
  • Bọc lỗi để giữ ngữ cảnh
  • Phân biệt lỗi người dùng và lỗi hệ thống

#Lỗi là giá trị

Go không có try / catch. Hàm có thể thất bại thì trả về một giá trị kiểu error ở vị trí cuối, và người gọi kiểm tra ngay:

Go
f, err := os.Open("data.csv")
if err != nil {
    return fmt.Errorf("mở file dữ liệu: %w", err)
}
defer f.Close()

error chỉ là một interface có sẵn:

Go
type error interface {
    Error() string
}
JavaScriptGo
throw new Error("x")return errors.New("x")
try { a() } catch (e) { ... }if err := a(); err != nil { ... }
Lỗi bay lên tự động qua nhiều tầngMỗi tầng tự quyết định: xử lý, hay bọc thêm ngữ cảnh rồi trả lên
Nhìn chữ ký hàm không biết hàm có thể ném lỗiChữ ký (T, error) nói rõ hàm có thể lỗi
e instanceof NotFoundErrorerrors.Is(err, ErrNotFound) / errors.As(err, &target)

Lúc đầu bạn sẽ thấy if err != nil lặp lại ở khắp nơi. Đây là chủ đích: đường đi của lỗi hiện rõ trên màn hình. Khi đọc một hàm Go, bạn thấy ngay mọi chỗ có thể hỏng và chuyện gì xảy ra lúc đó, điều mà await trong một khối try lớn không cho bạn thấy.

#Bọc lỗi để giữ ngữ cảnh

Một lỗi trần như connection refused không cho biết gì. Mỗi tầng nên thêm ngữ cảnh bằng fmt.Errorf với %w (wrap):

Go
func (r *Repo) GetClass(ctx context.Context, id int64) (Class, error) {
    var c Class
    err := r.db.QueryRow(ctx, `SELECT id, name FROM classes WHERE id = $1`, id).Scan(&c.ID, &c.Name)
    if err != nil {
        return Class{}, fmt.Errorf("lấy lớp %d: %w", id, err)
    }
    return c, nil
}

func (s *Service) ClassReport(ctx context.Context, id int64) (Report, error) {
    c, err := s.repo.GetClass(ctx, id)
    if err != nil {
        return Report{}, fmt.Errorf("tạo báo cáo lớp: %w", err)
    }
    // ...
}

Lỗi cuối cùng đọc như một câu chuyện, từ ngoài vào trong:

log
tạo báo cáo lớp: lấy lớp 42: failed to connect to `host=db`: dial tcp 10.0.0.5:5432: connect: connection refused

%w và %v khác nhau: %w giữ lỗi gốc bên trong để errors.Is / errors.As còn tìm thấy. %v chỉ chép chữ, lỗi gốc mất. Gần như luôn dùng %w.

#Lỗi định sẵn (sentinel) và errors.Is

Với các lỗi nghiệp vụ mà người gọi cần phân biệt, khai báo sẵn thành biến của package:

Go
var (
    ErrNotFound  = errors.New("không tìm thấy")
    ErrForbidden = errors.New("không có quyền")
    ErrConflict  = errors.New("dữ liệu đã thay đổi")
)

func (r *Repo) GetClass(ctx context.Context, id int64) (Class, error) {
    // ...
    if errors.Is(err, pgx.ErrNoRows) {
        return Class{}, ErrNotFound // đổi lỗi của thư viện thành lỗi của mình
    }
    // ...
}

// Ở tầng trên, dù lỗi đã bị bọc nhiều lớp, errors.Is vẫn tìm thấy:
if errors.Is(err, ErrNotFound) {
    // trả 404
}

Repository nên dịch lỗi của thư viện database (pgx.ErrNoRows, lỗi trùng khoá...) thành lỗi của chính ứng dụng (ErrNotFound, ErrConflict). Nhờ vậy tầng service và HTTP không phụ thuộc vào việc bạn dùng Postgres hay thứ khác.

#Kiểu lỗi riêng và errors.As

Khi lỗi cần mang thêm dữ liệu (trường nào sai, sai vì sao), tạo một kiểu lỗi riêng:

Go
type ValidationError struct {
    Field   string
    Message string
}

func (e *ValidationError) Error() string {
    return e.Field + ": " + e.Message
}

func validate(req CreateClassReq) error {
    if utf8.RuneCountInString(req.Name) > 60 {
        return &ValidationError{Field: "name", Message: "Tên lớp tối đa 60 ký tự"}
    }
    return nil
}

// Tầng HTTP lấy lại lỗi cụ thể để trả về cho client
var ve *ValidationError
if errors.As(err, &ve) {
    // trả 400 với ve.Field, ve.Message
}

#Biến lỗi thành response HTTP ở một chỗ

Ngoài thực tế, mỗi dự án có một hàm duy nhất quyết định lỗi nào thành status code nào và người dùng thấy câu gì. Không handler nào tự viết 500 lung tung.

internal/httpx/errors.go
func WriteError(w http.ResponseWriter, r *http.Request, err error) {
    var ve *ValidationError
    switch {
    case errors.As(err, &ve):
        writeJSON(w, http.StatusBadRequest, errBody("INVALID", ve.Message))
    case errors.Is(err, ErrNotFound):
        writeJSON(w, http.StatusNotFound, errBody("NOT_FOUND", "Không tìm thấy"))
    case errors.Is(err, ErrForbidden):
        writeJSON(w, http.StatusForbidden, errBody("FORBIDDEN", "Bạn không có quyền"))
    case errors.Is(err, context.DeadlineExceeded):
        writeJSON(w, http.StatusGatewayTimeout, errBody("TIMEOUT", "Máy chủ xử lý quá lâu"))
    default:
        // Lỗi không lường trước: ghi log đầy đủ, KHÔNG trả chi tiết cho client
        slog.ErrorContext(r.Context(), "lỗi không xử lý", "err", err, "path", r.URL.Path)
        writeJSON(w, http.StatusInternalServerError, errBody("INTERNAL", "Có lỗi xảy ra, vui lòng thử lại"))
    }
}

Đừng bao giờ trả nguyên err.Error() của lỗi hệ thống cho client. Chuỗi lỗi có thể chứa tên bảng, câu SQL, địa chỉ IP nội bộ, đường dẫn file: những thứ kẻ tấn công rất muốn biết. Lỗi nghiệp vụ (validation) thì được viết sẵn cho người dùng đọc nên trả được.

Xử lý lỗi một lần

GoSai / nguy hiểm
if err != nil {
    log.Printf("lỗi lấy lớp: %v", err) // ghi log ở đây
    return err                          // rồi trả lên, tầng trên lại ghi log lần nữa
}

Kết quả là một lỗi xuất hiện 4 lần trong log ở 4 tầng. Quy tắc: hoặc xử lý (ghi log, trả response), hoặc bọc và trả lên. Không làm cả hai. Thường chỉ tầng ngoài cùng (handler / middleware) ghi log.

#panic và recover

panic dừng hàm ngay lập tức và đi ngược lên chuỗi gọi hàm, chạy các defer trên đường đi. Nếu không ai recover, cả chương trình dừng.

Panic dành cho lỗi lập trình, những thứ "không thể xảy ra nếu code đúng": truy cập ngoài phạm vi slice, nil pointer, cấu hình bắt buộc bị thiếu lúc khởi động. Lỗi có thể đoán trước (người dùng nhập sai, không tìm thấy, mạng lỗi) luôn dùng error.

Go
func mustEnv(key string) string {
    v := os.Getenv(key)
    if v == "" {
        panic("thiếu biến môi trường " + key) // chấp nhận được: lúc khởi động, sai cấu hình thì nên dừng ngay
    }
    return v
}

recover chỉ có tác dụng bên trong một hàm defer. Ứng dụng phổ biến nhất: middleware chặn panic để một request lỗi không kéo sập cả server:

Go
func Recover(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if v := recover(); v != nil {
                slog.Error("panic", "value", v, "stack", string(debug.Stack()))
                http.Error(w, "Có lỗi xảy ra", http.StatusInternalServerError)
            }
        }()
        next.ServeHTTP(w, r)
    })
}

net/http của Go đã tự recover panic trong handler và chỉ đóng kết nối đó, nên server không sập. Nhưng nó không ghi log theo định dạng của bạn và client chỉ thấy kết nối bị cắt. Middleware như trên cho bạn log có cấu trúc và một response tử tế. Lưu ý: panic trong một goroutine bạn tự tạo ra (go func() {...}()) thì không middleware nào cứu được: nó làm dừng cả tiến trình. Goroutine chạy nền phải tự có recover.

Câu hỏi nhanh. Repository gọi DB và nhận pgx.ErrNoRows. Repository nên trả gì lên service?

Dịch lỗi thư viện thành lỗi miền nghiệp vụ giúp các tầng trên không phụ thuộc vào thư viện database. Trả nil, nil buộc người gọi kiểm tra thêm nil và rất dễ dẫn tới nil pointer panic.

Câu hỏi nhanh. err := fmt.Errorf("lưu đơn: %v", ErrConflict). Sau đó errors.Is(err, ErrConflict) trả về gì?

%v chỉ chèn chuỗi, không giữ lỗi gốc. Phải dùng %w thì errors.Is mới tìm thấy ErrConflict bên trong.

#Bài tập

Rút tiền

Viết Withdraw(balance, amount int64) (int64, error). Trả *ValidationError khi amount <= 0, trả lỗi định sẵn ErrInsufficientFunds khi không đủ tiền, bọc kèm số dư hiện tại. Viết hàm statusOf(err error) int trả 400 / 409 / 500 tương ứng.

Xem lời giải
Go
var ErrInsufficientFunds = errors.New("số dư không đủ")

func Withdraw(balance, amount int64) (int64, error) {
    if amount <= 0 {
        return balance, &ValidationError{Field: "amount", Message: "Số tiền phải lớn hơn 0"}
    }
    if amount > balance {
        return balance, fmt.Errorf("rút %d, còn %d: %w", amount, balance, ErrInsufficientFunds)
    }
    return balance - amount, nil
}

func statusOf(err error) int {
    var ve *ValidationError
    switch {
    case err == nil:
        return 200
    case errors.As(err, &ve):
        return 400
    case errors.Is(err, ErrInsufficientFunds):
        return 409
    default:
        return 500
    }
}

Ở bài 16 bạn sẽ thấy kiểm tra số dư ngay trong Go như thế này là chưa đủ khi có hai request rút tiền cùng lúc. Kiểm tra phải nằm trong câu SQL.
