Goroutine, channel và đồng thời

Sức mạnh lớn nhất của Go: chạy hàng nghìn việc cùng lúc. So sánh với event loop của JavaScript.

Học xong bài này bạn sẽ:
  • Chạy việc song song bằng goroutine + WaitGroup
  • Giao tiếp giữa goroutine bằng channel
  • Phát hiện và sửa data race

#JavaScript chờ, Go chạy song song

Ở frontend và Node.js, code của bạn chạy trên một luồng. await fetch() không chặn luồng vì event loop chuyển sang việc khác trong lúc chờ mạng. Nhưng một vòng lặp tính toán nặng 2 giây sẽ chặn mọi thứ khác.

Go dùng goroutine: những "luồng nhẹ" do runtime của Go quản lý. Bạn viết code tuần tự bình thường (không async, không await, không callback), còn runtime tự phân phối hàng nghìn goroutine lên tất cả các nhân CPU.

net/http của Go tạo một goroutine cho mỗi kết nối. Bạn viết handler như thể chỉ có một người dùng, gọi database, chờ, trả kết quả. Hàng nghìn người dùng cùng lúc là hàng nghìn goroutine, mỗi cái chỉ tốn vài KB bộ nhớ lúc đầu. Một luồng hệ điều hành thường tốn cỡ 1MB trở lên cho stack, nên mô hình "mỗi request một luồng" của các server đời cũ khó mở rộng hơn nhiều.

#Goroutine: thêm chữ go

Go
func sendEmail(to string) {
    time.Sleep(time.Second) // giả lập gửi chậm
    fmt.Println("đã gửi", to)
}

func main() {
    go sendEmail("an@x.vn")   // chạy ở goroutine mới, main không chờ
    go sendEmail("binh@x.vn")
    fmt.Println("main chạy tiếp ngay")
    time.Sleep(2 * time.Second) // tạm thời: chờ cho goroutine kịp chạy (cách đúng ở dưới)
}

Khi hàm main kết thúc, chương trình dừng ngay, mọi goroutine đang chạy dở bị bỏ. time.Sleep để chờ là cách sai. Phải đồng bộ bằng WaitGroup hoặc channel.

#sync.WaitGroup: chờ một nhóm việc xong

Giống await Promise.all([...]):

Go
func main() {
    emails := []string{"an@x.vn", "binh@x.vn", "chi@x.vn"}
    var wg sync.WaitGroup
    for _, e := range emails {
        wg.Add(1)
        go func() {
            defer wg.Done()
            sendEmail(e)
        }()
    }
    wg.Wait() // chờ tới khi cả 3 gọi Done
    fmt.Println("gửi xong tất cả")
}

Từ Go 1.25 có cách viết gọn wg.Go(func() { sendEmail(e) }), tự lo Add và Done.

errgroup: Promise.all có lỗi và huỷ

Trong thực tế bạn cần thêm hai thứ: lấy lỗi đầu tiên, và huỷ các việc còn lại khi một việc lỗi. Package golang.org/x/sync/errgroup làm đúng việc đó, và được dùng rất nhiều:

Go
// Trang tổng quan cần 3 nguồn dữ liệu độc lập: gọi song song thay vì lần lượt
func (s *Service) Dashboard(ctx context.Context, userID int64) (Dashboard, error) {
    var d Dashboard
    g, ctx := errgroup.WithContext(ctx)
    g.Go(func() error {
        var err error
        d.Classes, err = s.store.ClassesOf(ctx, userID)
        return err
    })
    g.Go(func() error {
        var err error
        d.DueToday, err = s.store.DueToday(ctx, userID)
        return err
    })
    g.Go(func() error {
        var err error
        d.Unread, err = s.store.UnreadCount(ctx, userID)
        return err
    })
    if err := g.Wait(); err != nil { // lỗi đầu tiên; ctx đã bị huỷ để các việc khác dừng sớm
        return Dashboard{}, err
    }
    return d, nil
}

Ba truy vấn mỗi cái 30ms chạy lần lượt mất 90ms, chạy song song mất khoảng 30ms. Mỗi goroutine ghi vào một trường khác nhau của d, nên không tranh chấp.

#Channel: đường ống giữa các goroutine

Channel là một hàng đợi có kiểu dữ liệu, an toàn khi dùng đồng thời. Goroutine này gửi vào, goroutine khác nhận ra.

Go
ch := make(chan int)      // channel không đệm: gửi chờ tới khi có người nhận
go func() {
    ch <- 42              // gửi
}()
v := <-ch                 // nhận: chờ tới khi có giá trị
fmt.Println(v)

buf := make(chan string, 100) // channel có đệm 100 chỗ: gửi chỉ chờ khi đầy

Câu châm ngôn của Go: "Đừng giao tiếp bằng cách chia sẻ bộ nhớ, hãy chia sẻ bộ nhớ bằng cách giao tiếp." Thay vì nhiều goroutine cùng sửa một biến (phải khoá), hãy để một goroutine sở hữu dữ liệu và những goroutine khác gửi yêu cầu qua channel.

Worker pool: giới hạn số việc chạy cùng lúc

Có 10.000 ảnh cần tạo ảnh thu nhỏ. Mở 10.000 goroutine cùng lúc sẽ ngốn hết RAM và làm nghẽn dịch vụ lưu trữ. Mẫu chuẩn là một nhóm cố định N "thợ" nhận việc từ một channel:

Go
func process(ctx context.Context, ids []int64, workers int) (ok, failed int) {
    jobs := make(chan int64)
    results := make(chan error)

    var wg sync.WaitGroup
    for range workers {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for id := range jobs { // nhận tới khi jobs bị đóng
                results <- makeThumbnail(ctx, id)
            }
        }()
    }

    go func() { // gửi việc rồi đóng jobs để các worker biết là hết
        defer close(jobs)
        for _, id := range ids {
            select {
            case jobs <- id:
            case <-ctx.Done():
                return
            }
        }
    }()

    go func() { wg.Wait(); close(results) }() // mọi worker xong → đóng results

    for err := range results {
        if err != nil {
            failed++
        } else {
            ok++
        }
    }
    return ok, failed
}

Quy tắc đóng channel: chỉ bên gửi được đóng, và chỉ đóng khi chắc chắn không còn ai gửi nữa. Gửi vào channel đã đóng gây panic. Nhận từ channel đã đóng thì nhận được zero value ngay lập tức, for range trên channel sẽ dừng.

Với trường hợp đơn giản, errgroup có sẵn g.SetLimit(8) để giới hạn số goroutine, ngắn hơn nhiều so với tự viết pool.

#select: chờ nhiều thứ cùng lúc

Go
select {
case res := <-resultCh:
    fmt.Println("có kết quả", res)
case <-time.After(2 * time.Second):
    fmt.Println("quá 2 giây, bỏ")
case <-ctx.Done():
    fmt.Println("request đã bị huỷ")
}

select chờ tới khi một trong các case sẵn sàng, rồi chạy đúng case đó. Giống Promise.race nhưng cho channel. Bài 10 nói về ctx.Done().

#Mutex: khi buộc phải dùng chung dữ liệu

Nhiều goroutine cùng đọc và ghi một biến mà không đồng bộ gọi là data race. Kết quả sai một cách ngẫu nhiên, và với map còn làm sập chương trình.

GoSai / nguy hiểm
var count int
var wg sync.WaitGroup
for range 1000 {
    wg.Add(1)
    go func() {
        defer wg.Done()
        count++ // đọc, cộng, ghi: 3 bước, các goroutine xen vào nhau
    }()
}
wg.Wait()
fmt.Println(count) // thường KHÔNG phải 1000
GoĐúng / nên làm
type Counter struct {
    mu sync.Mutex
    n  map[string]int
}

func (c *Counter) Inc(key string) {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.n[key]++
}

func (c *Counter) Get(key string) int {
    c.mu.Lock()
    defer c.mu.Unlock()
    return c.n[key]
}

Biến thể: sync.RWMutex cho nhiều người đọc cùng lúc, chỉ ghi mới khoá độc quyền. Với một bộ đếm số đơn giản, dùng sync/atomic: var n atomic.Int64; n.Add(1).

Bộ phát hiện race có sẵn

Terminal
go test -race ./...   # chạy test với bộ phát hiện race
go run -race .        # chạy chương trình với bộ phát hiện race
Kết quả khi có race
WARNING: DATA RACE
Write at 0x00c000012345 by goroutine 8:
  main.main.func1()
      /app/main.go:14 +0x44
Previous write at 0x00c000012345 by goroutine 7:
  ...

Luôn chạy go test -race trong CI. Bộ phát hiện chỉ tìm thấy race ở đoạn code thật sự chạy trong lúc test, nên test càng phủ nhiều nhánh càng tốt.

#Những lỗi đồng thời hay gặp

LỗiBiểu hiệnCách tránh
Rò rỉ goroutineBộ nhớ tăng dần theo thời gian, số goroutine (xem qua pprof) tăng mãiMọi goroutine phải có đường thoát: channel được đóng, hoặc ctx.Done()
Deadlockfatal error: all goroutines are asleep - deadlock!Không gửi vào channel không đệm khi không ai nhận. Khoá nhiều mutex luôn theo cùng một thứ tự
Data raceKết quả sai ngẫu nhiên, map panicMutex, atomic, hoặc chỉ một goroutine sở hữu dữ liệu

Câu hỏi nhanh. Handler HTTP chạy go sendWelcomeEmail(user) rồi trả response ngay. Rủi ro lớn nhất trong môi trường production là gì?

Việc nền quan trọng nên đưa vào hàng đợi bền vững có thử lại (bài 20). Goroutine "bắn rồi quên" chỉ hợp với việc không quan trọng, và phải có recover.

#Bài tập

Kiểm tra nhiều trang web song song

Cho danh sách 20 URL. Kiểm tra mỗi URL trả status gì, chạy tối đa 5 request cùng lúc, mỗi request tối đa 3 giây. In kết quả theo đúng thứ tự danh sách ban đầu.

Xem lời giải
Go
func checkAll(ctx context.Context, urls []string) []string {
    out := make([]string, len(urls)) // mỗi goroutine ghi vào ô riêng → không race, giữ thứ tự
    client := &http.Client{Timeout: 3 * time.Second}

    g, ctx := errgroup.WithContext(ctx)
    g.SetLimit(5)
    for i, u := range urls {
        g.Go(func() error {
            req, err := http.NewRequestWithContext(ctx, http.MethodGet, u, nil)
            if err != nil {
                out[i] = "URL sai: " + err.Error()
                return nil
            }
            resp, err := client.Do(req)
            if err != nil {
                out[i] = "lỗi: " + err.Error()
                return nil // không trả lỗi để các URL khác vẫn chạy
            }
            resp.Body.Close()
            out[i] = resp.Status
            return nil
        })
    }
    g.Wait()
    return out
}

Hai chi tiết thực tế: http.Client mặc định không có timeout (bài 11), nên luôn tự đặt. Và luôn Close() body của response, nếu không kết nối không được dùng lại và bị rò rỉ.

Tìm và sửa race

Chạy đoạn "đếm count++" ở trên với go run -race ., đọc báo cáo, rồi sửa bằng ba cách: sync.Mutex, atomic.Int64, và một goroutine duy nhất nhận số qua channel rồi cộng.

Gợi ý cách thứ ba
Go
ch := make(chan int)
done := make(chan int)
go func() { // goroutine duy nhất sở hữu biến tổng
    total := 0
    for n := range ch {
        total += n
    }
    done <- total
}()
var wg sync.WaitGroup
for range 1000 {
    wg.Add(1)
    go func() { defer wg.Done(); ch <- 1 }()
}
wg.Wait()
close(ch)
fmt.Println(<-done) // 1000
