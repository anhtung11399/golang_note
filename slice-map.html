Array, slice và map

Slice hoạt động bên trong ra sao, vì sao append có thể làm bạn mất dữ liệu, và map dùng thế nào cho đúng.

Học xong bài này bạn sẽ:
  • Hiểu slice = (con trỏ, len, cap)
  • Tránh lỗi chia sẻ mảng nền khi append
  • Dùng map an toàn (nil map, thứ tự duyệt)

#Array: độ dài cố định, ít khi dùng trực tiếp

Go
var days [7]string           // mảng 7 chuỗi, độ dài là một phần của kiểu
scores := [3]int{8, 9, 10}
fmt.Println(len(scores))     // 3

[3]int và [4]int là hai kiểu khác nhau. Gán mảng cho biến khác là sao chép toàn bộ. Vì cứng nhắc như vậy, code hằng ngày gần như chỉ dùng slice.

#Slice: "mảng" bạn sẽ dùng hằng ngày

Go
names := []string{"An", "Bình"}   // không ghi độ dài trong [] → slice
names = append(names, "Chi")      // thêm phần tử: PHẢI gán lại kết quả
fmt.Println(len(names))           // 3

nums := make([]int, 0, 100)       // slice rỗng, chuẩn bị sẵn chỗ cho 100 phần tử
sub := names[1:3]                 // cắt: phần tử 1 và 2 → ["Bình", "Chi"]
JavaScriptGo
const a = []var a []int (nil, dùng được ngay) hoặc a := []int{}
a.push(x)a = append(a, x)
a.lengthlen(a)
a.slice(1, 3)a[1:3] (nhưng dùng chung bộ nhớ, xem dưới)
a.includes(x)slices.Contains(a, x)

a.sort((x, y) => x - y)slices.Sort(a) hoặc slices.SortFunc(a, cmp)

#Bên trong một slice

Hiểu phần này là tránh được một loại lỗi rất khó tìm. Một slice thực chất là một struct nhỏ gồm 3 trường: con trỏ tới một mảng nền, len (số phần tử đang dùng) và cap (sức chứa của mảng nền tính từ vị trí con trỏ).

Cạm bẫy 1: hai slice dùng chung bộ nhớ

Go
a := []string{"A", "B", "C", "D", "E"}
s := a[1:3]       // ["B", "C"]
s[0] = "X"
fmt.Println(a)    // [A X C D E]  ← a cũng bị sửa!

Cạm bẫy 2: append ghi đè dữ liệu của slice khác

Khi còn chỗ trong cap, append ghi thẳng vào mảng nền. Khi hết chỗ, nó cấp mảng mới lớn hơn (thường gấp đôi khi slice còn nhỏ), sao chép sang và trả về slice trỏ vào mảng mới. Vì vậy bạn không đoán được kết quả của append có dùng chung bộ nhớ với slice cũ hay không.

GoSai / nguy hiểm
a := []string{"A", "B", "C", "D", "E"}
s := a[1:3]               // len 2, cap 4
s = append(s, "Z")        // còn chỗ → ghi vào a[3]
fmt.Println(a)            // [A B C Z E]  ← "D" bị ghi đè âm thầm
GoĐúng / nên làm
s := slices.Clone(a[1:3]) // sao chép ra mảng riêng
s = append(s, "Z")        // a không bị ảnh hưởng

Luôn viết s = append(s, x). Quên gán lại thì phần tử mới có thể "biến mất" vì nó nằm trong mảng mới mà biến s không trỏ tới. Trình biên dịch sẽ báo lỗi nếu bạn gọi append mà bỏ kết quả.

Chuẩn bị sẵn sức chứa

Khi biết trước số phần tử (ví dụ đổi 1.000 dòng database thành 1.000 DTO), cấp sẵn cap để tránh cấp phát và sao chép nhiều lần:

Go
out := make([]UserDTO, 0, len(users))
for _, u := range users {
    out = append(out, toDTO(u))
}

nil slice và slice rỗng trong JSON

Go
var a []int        // nil
b := []int{}       // rỗng, không nil
// len, append, range đều chạy bình thường với cả hai.
// Nhưng khi đổi sang JSON:
json.Marshal(a)    // null
json.Marshal(b)    // []

Đây là lý do frontend đôi khi nhận "items": null thay vì [] và vỡ ở dòng items.map(...). Backend Go nên khởi tạo slice rỗng cho các trường danh sách trong response. Bây giờ bạn biết lỗi đó đến từ đâu.

#Map: giống object / Map trong JavaScript

Go
ages := map[string]int{
    "An":   20,
    "Bình": 22,
}
ages["Chi"] = 19          // thêm hoặc sửa
delete(ages, "An")        // xoá
fmt.Println(len(ages))    // 2

age := ages["Không có"]   // trả về zero value: 0, không lỗi
age, ok := ages["Bình"]   // "comma ok": ok = true nếu khoá có tồn tại
if !ok {
    fmt.Println("không có")
}

counts := make(map[string]int) // map rỗng, ghi được ngay
counts["go"]++                 // khoá chưa có thì bắt đầu từ 0

Ba điều phải nhớ về map

  1. Ghi vào nil map gây panic. var m map[string]int; m["a"] = 1 làm chương trình dừng. Luôn tạo bằng make hoặc map[...]...{}.
  2. Thứ tự duyệt là ngẫu nhiên, và Go cố tình làm ngẫu nhiên khác nhau mỗi lần chạy để bạn không vô tình phụ thuộc vào nó. Cần thứ tự thì lấy danh sách khoá ra rồi sắp xếp:
    Go
    keys := slices.Sorted(maps.Keys(ages)) // Go 1.23+, import "maps", "slices"
for _, k := range keys {
    fmt.Println(k, ages[k])
}
  3. Map không an toàn khi nhiều goroutine cùng ghi. Runtime phát hiện được và dừng chương trình với lỗi fatal error: concurrent map writes. Trong HTTP server (mỗi request một goroutine), một map dùng chung phải được bảo vệ bằng mutex (bài 09).

Set: dùng map với giá trị rỗng

Go
seen := map[string]struct{}{}   // struct{} không tốn bộ nhớ
seen["lan@gmail.com"] = struct{}{}
if _, ok := seen[email]; ok {
    fmt.Println("trùng")
}

Map trong bộ nhớ là cache đơn giản nhất. Nhưng khi chạy 3 bản server sau load balancer, mỗi bản có map riêng: người dùng gọi lần một vào máy A, lần hai vào máy B và không thấy dữ liệu cũ. Đây là lý do các hệ thống thật dùng Redis cho cache dùng chung (bài 17).

#Gom nhóm: mẫu bạn sẽ viết rất nhiều

Ví dụ có danh sách bài nộp, cần gom theo học sinh để tính số bài đã nộp:

Go
type Submission struct {
    StudentID int64
    Score     float64
}

func countByStudent(subs []Submission) map[int64]int {
    out := make(map[int64]int, len(subs))
    for _, s := range subs {
        out[s.StudentID]++
    }
    return out
}

Ở bài 16, bạn sẽ dùng chính mẫu này để sửa lỗi N+1 truy vấn: lấy hết dữ liệu liên quan trong một câu SQL rồi gom bằng map trong Go.

Câu hỏi nhanh. a := []int{1, 2, 3, 4}; b := a[:2]; b = append(b, 99). Giá trị của a là gì?

b có len 2 nhưng cap 4, còn chỗ trong mảng nền chung nên append ghi thẳng vào a[2].

Câu hỏi nhanh. Hai request HTTP cùng lúc ghi vào một map[string]int dùng chung, không có khoá. Điều gì có thể xảy ra?

Map không an toàn cho ghi đồng thời. Đây là lỗi fatal (không recover được), làm sập cả server. Dùng sync.Mutex hoặc sync.Map.

#Bài tập

Đếm từ xuất hiện nhiều nhất

Viết topWords(text string, n int) []string trả về n từ xuất hiện nhiều nhất (không phân biệt hoa thường). Gợi ý: strings.Fields, strings.ToLower, map đếm, rồi slices.SortFunc.

Xem lời giải
Go
func topWords(text string, n int) []string {
    counts := map[string]int{}
    for _, w := range strings.Fields(strings.ToLower(text)) {
        counts[w]++
    }
    words := make([]string, 0, len(counts))
    for w := range counts {
        words = append(words, w)
    }
    slices.SortFunc(words, func(a, b string) int {
        if counts[a] != counts[b] {
            return counts[b] - counts[a] // nhiều hơn đứng trước
        }
        return strings.Compare(a, b)     // bằng nhau thì theo chữ cái, kết quả luôn ổn định
    })
    if len(words) > n {
        words = words[:n]
    }
    return words
}

Để ý dòng so sánh phụ theo chữ cái: vì map duyệt ngẫu nhiên, nếu không có nó thì các từ cùng số lần xuất hiện sẽ đổi chỗ giữa các lần chạy, làm test lúc đúng lúc sai.

Phân trang trên slice

Viết page[T any](items []T, page, size int) []T trả về phần tử của trang page (bắt đầu từ 1). Không được panic khi trang vượt quá dữ liệu hoặc tham số âm. (Chữ [T any] là generics, bài 06 sẽ giải thích. Tạm hiểu là "hàm dùng được cho slice kiểu bất kỳ".)

Xem lời giải
Go
func page[T any](items []T, page, size int) []T {
    if page < 1 || size < 1 {
        return []T{}
    }
    start := (page - 1) * size
    if start >= len(items) {
        return []T{}
    }
    end := min(start+size, len(items)) // min có sẵn từ Go 1.21
    return items[start:end]
}

Truy cập ngoài phạm vi slice (items[10] khi len là 5) gây panic, khác với JavaScript trả undefined. Mọi chỉ số tính từ dữ liệu người dùng gửi lên đều phải kiểm tra như trên.
