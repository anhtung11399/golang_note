Index, tối ưu truy vấn và tranh chấp dữ liệu

Index hoạt động ra sao, đọc EXPLAIN, lỗi N+1, phân trang keyset, lost update và cách khoá dữ liệu.

Học xong bài này bạn sẽ:
  • Đặt index đúng cho truy vấn
  • Đọc kế hoạch truy vấn
  • Chống bán quá số lượng tồn kho khi nhiều người mua cùng lúc

#Index: mục lục của bảng

Không có index, để tìm WHERE email = 'lan@x.vn' Postgres phải đọc từng dòng của bảng (sequential scan). 100 dòng thì không sao. 10 triệu dòng thì mỗi lần đăng nhập đọc cả bảng.

Index (mặc định là cây B-tree) giữ các giá trị của cột theo thứ tự, mỗi giá trị trỏ tới dòng chứa nó. Tìm trong cây chỉ cần đi qua vài tầng, giống tra từ điển theo chữ cái thay vì đọc từng trang.

SQL
CREATE INDEX idx_assignments_class_due ON assignments (class_id, due_date DESC);
CREATE INDEX idx_submissions_student ON submissions (student_id);

Khoá chính và cột UNIQUE tự có index. Khoá ngoại thì không (trong Postgres): bạn phải tự tạo index cho class_id, teacher_id... nếu không, mỗi lần lọc theo lớp hay xoá một lớp (CASCADE) là quét toàn bảng con.

Index nhiều cột: thứ tự quan trọng

Index (class_id, due_date) giống danh bạ sắp theo (họ, tên):

Truy vấnDùng được index?
WHERE class_id = 5Có (cột đầu)
WHERE class_id = 5 AND due_date >= '2026-11-01'Có, rất tốt
WHERE class_id = 5 ORDER BY due_date DESC LIMIT 20Có, và khỏi phải sắp xếp
WHERE due_date = '2026-11-10'Gần như không (thiếu cột đầu), giống tìm theo tên mà không biết họ

Quy tắc: cột lọc bằng = đứng trước, cột lọc theo khoảng hoặc sắp xếp đứng sau.

Index không miễn phí

  • Mỗi lần INSERT / UPDATE / DELETE phải cập nhật mọi index của bảng. Bảng ghi nhiều mà có 10 index thì ghi chậm.
  • Index chiếm ổ đĩa và bộ nhớ đệm.
  • Hàm trên cột làm index vô dụng: WHERE lower(email) = $1 không dùng index trên email. Hoặc lưu email chữ thường sẵn, hoặc tạo index trên biểu thức (lower(email)).

#EXPLAIN: hỏi database nó định làm gì

SQL
EXPLAIN ANALYZE
SELECT id, title FROM assignments
WHERE class_id = 42 ORDER BY due_date DESC LIMIT 20;
Trước khi có index
Limit  (actual time=180.2..180.3 rows=20)
  ->  Sort  (Sort Key: due_date DESC)
        ->  Seq Scan on assignments  (actual time=0.02..176.9 rows=412 loops=1)
              Filter: (class_id = 42)
              Rows Removed by Filter: 1999588
Execution Time: 180.4 ms
Sau khi CREATE INDEX (class_id, due_date DESC)
Limit  (actual time=0.03..0.06 rows=20)
  ->  Index Scan using idx_assignments_class_due on assignments  (rows=20)
        Index Cond: (class_id = 42)
Execution Time: 0.08 ms

Những thứ cần nhìn: Seq Scan trên bảng lớn, Rows Removed by Filter rất lớn (đọc nhiều bỏ nhiều), Sort trên nhiều dòng, và actual time. Từ 180ms xuống 0,08ms là chuyện bình thường khi thêm đúng index.

EXPLAIN ANALYZE chạy thật câu lệnh. Với UPDATE / DELETE, bọc trong BEGIN; ... ROLLBACK;. Và kế hoạch trên máy bạn (100 dòng) có thể khác hẳn production (10 triệu dòng): Postgres chọn cách chạy dựa trên thống kê dữ liệu thật.

Bật extension pg_stat_statements trên production: nó thống kê câu truy vấn nào tốn tổng thời gian nhiều nhất. Thường 5 câu truy vấn chiếm phần lớn tải, sửa chúng trước. Các dịch vụ Postgres có quản lý (AWS RDS, Google Cloud SQL, Supabase, Neon) đều có sẵn hoặc bật được.

#Lỗi N+1: kẻ giết hiệu năng số một

GoSai / nguy hiểm
classes, _ := store.ClassesOf(ctx, teacherID)          // 1 truy vấn
for i, c := range classes {
    n, _ := store.CountStudents(ctx, c.ID)            // + N truy vấn, mỗi lớp một lần
    classes[i].StudentCount = n
}
// 30 lớp = 31 truy vấn. Mỗi lần đi về database mất ~1ms → 31ms chỉ để chờ mạng
GoĐúng / nên làm
// Một truy vấn lấy hết, gom bằng map trong Go (mẫu ở bài 04)
rows, err := db.Query(ctx, `
    SELECT class_id, count(*) FROM enrollments
    WHERE class_id = ANY($1) GROUP BY class_id`, classIDs) // pgx đổi []int64 thành mảng Postgres
// ... đọc vào map[int64]int rồi gán cho từng lớp

// Hoặc gộp luôn vào truy vấn đầu bằng JOIN + GROUP BY (bài 14)

Giống lỗi gọi API trong vòng lặp ở frontend: mỗi item trong danh sách tự fetch chi tiết của nó. Ở frontend là 30 request HTTP, ở backend là 30 lần đi về database cho mỗi request của người dùng. Nhân với 1.000 người dùng mỗi phút là 30.000 truy vấn vô ích.

ORM là nơi N+1 hay xuất hiện nhất, vì truy cập class.Students trông như đọc một trường nhưng thật ra chạy một câu SQL. Vì vậy các ORM đều có cơ chế "preload / eager loading". Với SQL thuần, N+1 dễ thấy hơn: một câu Query nằm trong vòng for.

#Phân trang keyset (cursor) bằng SQL

SQLSai / nguy hiểm
-- Trang 5000: Postgres vẫn phải đọc qua 100.000 dòng rồi bỏ đi
SELECT * FROM notifications WHERE user_id = 7
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 100000;
SQLĐúng / nên làm
-- Nhớ dòng cuối của trang trước (created_at, id) rồi lấy tiếp "sau" nó
SELECT id, created_at, body FROM notifications
WHERE user_id = 7
  AND (created_at, id) < ($2, $3)        -- so sánh theo bộ: đúng cả khi trùng created_at
ORDER BY created_at DESC, id DESC
LIMIT 21;                                 -- lấy dư 1 dòng để biết còn trang sau không
-- Index tương ứng: (user_id, created_at DESC, id DESC)

Con trỏ gửi cho client là (created_at, id) của dòng cuối, mã hoá base64 để client coi nó là chuỗi mờ. Truy vấn luôn nhanh như trang đầu, dù sâu tới đâu.

#Tranh chấp: hai request cùng sửa một dòng

Đây là phần quan trọng nhất của bài và là chỗ backend khác frontend nhiều nhất. Ví dụ bán vé: còn 1 vé, hai người bấm mua cùng lúc.

GoSai / nguy hiểm
// Đọc → kiểm tra → ghi: ba bước rời nhau
var stock int
db.QueryRow(ctx, `SELECT stock FROM tickets WHERE id = $1`, id).Scan(&stock)
if stock < 1 {
    return ErrSoldOut
}
db.Exec(ctx, `UPDATE tickets SET stock = $1 WHERE id = $2`, stock-1, id)
db.Exec(ctx, `INSERT INTO orders ...`)

Cách 1: điều kiện nằm ngay trong câu UPDATE (nên dùng đầu tiên)

SQLĐúng / nên làm
UPDATE tickets SET stock = stock - 1
WHERE id = $1 AND stock >= 1
RETURNING stock;
-- 0 dòng bị sửa → hết vé. Một câu lệnh là nguyên tử: không ai chen vào giữa được

Ghép với tạo đơn trong cùng một transaction (bài 15): UPDATE không sửa được dòng nào thì rollback và trả "hết vé".

Cách 2: khoá dòng bằng SELECT ... FOR UPDATE

Khi logic kiểm tra phức tạp, không viết gọn trong một câu UPDATE được:

Go
err := pgx.BeginFunc(ctx, db, func(tx pgx.Tx) error {
    var balance int64
    // Khoá dòng ví này tới khi transaction kết thúc. Request khác muốn khoá cùng dòng phải CHỜ
    if err := tx.QueryRow(ctx, `SELECT balance FROM wallets WHERE user_id = $1 FOR UPDATE`, uid).Scan(&balance); err != nil {
        return err
    }
    if balance < amount {
        return ErrInsufficientFunds
    }
    // ... kiểm tra hạn mức trong ngày, trạng thái tài khoản, v.v.
    _, err := tx.Exec(ctx, `UPDATE wallets SET balance = balance - $1 WHERE user_id = $2`, amount, uid)
    return err
})

FOR UPDATE SKIP LOCKED bỏ qua những dòng đang bị khoá thay vì chờ. Đây là cách làm hàng đợi việc ngay trong Postgres: nhiều worker cùng lấy việc mà không giành nhau một việc (bài 20).

Cách 3: optimistic concurrency với cột version

Đã gặp ở bài 12: UPDATE ... WHERE id = $1 AND version = $2. Không khoá gì, chỉ phát hiện xung đột và báo 409. Hợp với dữ liệu ít khi bị sửa cùng lúc (người dùng sửa form).

Mức cô lập (isolation level)

MứcÝ nghĩa
Read Committed (mặc định của Postgres)Mỗi câu lệnh thấy dữ liệu đã commit tính tới lúc câu lệnh đó bắt đầu. Không chống được lost update kiểu đọc rồi ghi như ví dụ trên
Repeatable ReadCả transaction nhìn một ảnh chụp cố định. Hai transaction cùng sửa một dòng thì một cái bị lỗi, phải thử lại
SerializableKết quả như thể các transaction chạy lần lượt. An toàn nhất, nhưng phải xử lý lỗi 40001 bằng cách chạy lại cả transaction

Trong thực tế, đa số hệ thống chạy Read Committed và dùng cách 1 hoặc cách 2 ở những chỗ cần.

Lỗi "bán quá số lượng" xảy ra thật ở các đợt flash sale, bán vé concert, mở bán sản phẩm giới hạn. Ở tải rất cao, ngay cả khoá dòng trong database cũng thành nút cổ chai (mọi người xếp hàng trên một dòng). Các sàn lớn khi đó chia kho thành nhiều phần, hoặc trừ kho trong Redis bằng lệnh nguyên tử rồi ghi database sau qua hàng đợi. Bài 23 bàn về thiết kế này.

#Bài tập

Giới hạn số lớp an toàn khi chạy song song

Viết lại CreateClass sao cho một giáo viên không bao giờ có quá quota lớp, kể cả khi 10 request tới cùng lúc trên 3 bản server. Viết test chạy 10 goroutine cùng tạo lớp và kiểm tra chỉ đúng quota lớp được tạo.

Xem lời giải
Go
func (s *Store) CreateClassWithQuota(ctx context.Context, c Class, quota int) (Class, error) {
    return c, pgx.BeginFunc(ctx, s.db, func(tx pgx.Tx) error {
        // Khoá dòng giáo viên: mọi request tạo lớp của CÙNG giáo viên xếp hàng tại đây
        if _, err := tx.Exec(ctx, `SELECT 1 FROM users WHERE id = $1 FOR UPDATE`, c.TeacherID); err != nil {
            return err
        }
        var n int
        if err := tx.QueryRow(ctx, `SELECT count(*) FROM classes WHERE teacher_id = $1`, c.TeacherID).Scan(&n); err != nil {
            return err
        }
        if n >= quota {
            return domain.ErrQuotaExceeded
        }
        return tx.QueryRow(ctx,
            `INSERT INTO classes (teacher_id, name, capacity) VALUES ($1, $2, $3) RETURNING id, created_at`,
            c.TeacherID, c.Name, c.Capacity).Scan(&c.ID, &c.CreatedAt)
    })
}

Không thể khoá "những dòng chưa tồn tại", nên ta khoá một dòng chắc chắn tồn tại và đại diện cho giáo viên: chính dòng users. Các giáo viên khác nhau không chặn nhau. Test: tạo 10 goroutine cùng gọi, đếm số lần thành công phải bằng quota, số lần ErrQuotaExceeded bằng phần còn lại.

Đọc EXPLAIN

Tạo bảng assignments với 1 triệu dòng giả bằng INSERT ... SELECT ... FROM generate_series(1, 1000000) (chỉ làm trên Postgres chạy bằng Docker ở máy bạn). So sánh EXPLAIN ANALYZE của truy vấn danh sách theo lớp trước và sau khi tạo index. Thử thêm OFFSET 500000 để thấy offset chậm thế nào.

Gợi ý
SQL
INSERT INTO assignments (class_id, title, due_date)
SELECT (random() * 5000)::int + 1, 'Bài ' || g, date '2026-01-01' + (g % 300)
FROM generate_series(1, 1000000) g;   -- cần có sẵn các lớp id 1..5001 vì có khoá ngoại
ANALYZE assignments;                  -- cập nhật thống kê cho bộ lập kế hoạch
