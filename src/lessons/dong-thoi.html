JavaScript chờ, Go chạy song song

Ở frontend và Node.js, code của bạn chạy trên một luồng. await fetch() không chặn luồng vì event loop chuyển sang việc khác trong lúc chờ mạng. Nhưng một vòng lặp tính toán nặng 2 giây sẽ chặn mọi thứ khác.

Go dùng goroutine: những "luồng nhẹ" do runtime của Go quản lý. Bạn viết code tuần tự bình thường (không async, không await, không callback), còn runtime tự phân phối hàng nghìn goroutine lên tất cả các nhân CPU.

net/http của Go tạo một goroutine cho mỗi kết nối. Bạn viết handler như thể chỉ có một người dùng, gọi database, chờ, trả kết quả. Hàng nghìn người dùng cùng lúc là hàng nghìn goroutine, mỗi cái chỉ tốn vài KB bộ nhớ lúc đầu. Một luồng hệ điều hành thường tốn cỡ 1MB trở lên cho stack, nên mô hình "mỗi request một luồng" của các server đời cũ khó mở rộng hơn nhiều.

Goroutine: thêm chữ go

Đặt chữ go trước một lời gọi hàm thì hàm đó chạy song song, còn dòng code tiếp theo chạy ngay mà không chờ. Gần giống gọi một hàm async mà không await.

package main

import (
    "fmt"
    "time"
)

func sendEmail(to string) {
    time.Sleep(time.Second) // giả lập gửi chậm mất 1 giây
    fmt.Println("đã gửi", to)
}

func main() {
    go sendEmail("an@x.vn")   // chạy ở goroutine mới, main không chờ
    go sendEmail("binh@x.vn") // goroutine thứ hai, chạy cùng lúc với cái trên
    fmt.Println("main chạy tiếp ngay")

    time.Sleep(2 * time.Second) // TẠM: đợi 2 giây cho goroutine kịp chạy (cách đúng ở phần sau)
}

Dòng "main chạy tiếp ngay" in ra trước, vì main không chờ. Hai dòng "đã gửi" in ra sau khoảng 1 giây (không phải 2 giây: hai email gửi cùng lúc), và thứ tự giữa chúng có thể đảo giữa các lần chạy.

Thử xoá dòng time.Sleep(2 * time.Second) rồi chạy: chỉ in "main chạy tiếp ngay", không có email nào.

Khi hàm main kết thúc, chương trình dừng ngay, mọi goroutine đang chạy dở bị bỏ. Ngủ một khoảng để chờ là cách sai: không biết phải ngủ bao lâu. Phải đồng bộ bằng WaitGroup hoặc channel.

sync.WaitGroup: chờ một nhóm việc xong

WaitGroup là một bộ đếm: Add(1) tăng lên khi giao một việc, Done() giảm xuống khi việc xong, Wait() chờ tới khi bộ đếm về 0. Giống await Promise.all([...]):

package main

import (
    "fmt"
    "sync"
    "time"
)

func sendEmail(to string) {
    time.Sleep(500 * time.Millisecond)
    fmt.Println("đã gửi", to)
}

func main() {
    emails := []string{"an@x.vn", "binh@x.vn", "chi@x.vn"}
    start := time.Now()

    var wg sync.WaitGroup
    for _, e := range emails {
        wg.Add(1)     // còn 1 việc nữa phải chờ
        go func() {   // hàm ẩn danh chạy ở goroutine mới
            defer wg.Done() // việc này xong (defer: chạy kể cả khi sendEmail lỗi)
            sendEmail(e)
        }()           // () ở cuối: gọi luôn hàm vừa viết
    }
    wg.Wait() // đứng chờ tới khi cả 3 gọi Done

    fmt.Println("gửi xong tất cả sau", time.Since(start).Round(100*time.Millisecond))
}

đã gửi an@x.vn

Ba email, mỗi email 0,5 giây, nhưng tổng chỉ 0,5 giây vì chạy song song. Gửi lần lượt sẽ mất 1,5 giây. Thứ tự ba dòng "đã gửi" thay đổi mỗi lần chạy, còn dòng cuối luôn nằm cuối.

Từ Go 1.25 có cách viết gọn wg.Go(func() { sendEmail(e) }), tự lo Add và Done.

errgroup: Promise.all có lỗi và huỷ

Trong thực tế bạn cần thêm hai thứ: lấy lỗi đầu tiên, và huỷ các việc còn lại khi một việc lỗi. Package golang.org/x/sync/errgroup làm đúng việc đó, và được dùng rất nhiều. Đây là thư viện ngoài (do đội Go duy trì), cài trước khi chạy:

go get golang.org/x/sync

Ví dụ: trang tổng quan của phụ huynh cần 3 loại dữ liệu độc lập. Gọi song song thay vì lần lượt:

package main

import (
    "context"
    "fmt"
    "time"

    "golang.org/x/sync/errgroup"
)

type Dashboard struct {
    Classes  []string
    DueToday int
    Unread   int
}

// Giả lập 3 truy vấn database, mỗi cái mất 300ms
func classesOf(ctx context.Context) ([]string, error) {
    time.Sleep(300 * time.Millisecond)
    return []string{"5A", "Tiếng Anh tối thứ 3"}, nil
}
func dueToday(ctx context.Context) (int, error) { time.Sleep(300 * time.Millisecond); return 2, nil }
func unread(ctx context.Context) (int, error)   { time.Sleep(300 * time.Millisecond); return 5, nil }

func loadDashboard(ctx context.Context) (Dashboard, error) {
    var d Dashboard
    g, ctx := errgroup.WithContext(ctx) // một nhóm việc, ctx bị huỷ khi có việc lỗi

    g.Go(func() error { // g.Go = chạy hàm ở goroutine mới, giống go func()
        var err error
        d.Classes, err = classesOf(ctx)
        return err
    })
    g.Go(func() error {
        var err error
        d.DueToday, err = dueToday(ctx)
        return err
    })
    g.Go(func() error {
        var err error
        d.Unread, err = unread(ctx)
        return err
    })

    if err := g.Wait(); err != nil { // chờ cả 3. Có lỗi thì nhận lỗi ĐẦU TIÊN
        return Dashboard{}, err
    }
    return d, nil
}

func main() {
    start := time.Now()
    d, err := loadDashboard(context.Background())
    fmt.Printf("%+v %v\n", d, err)
    fmt.Println("mất", time.Since(start).Round(100*time.Millisecond)) // ~300ms, không phải 900ms
}

{Classes:[5A Tiếng Anh tối thứ 3] DueToday:2 Unread:5} 
mất 300ms

Mỗi goroutine ghi vào một trường khác nhau của d, nên không giẫm chân nhau. context (tham số ctx) là cách báo "dừng lại" cho các việc đang chạy, bài {{n:context-test}} giải thích kỹ. Tạm hiểu: context.Background() là "không có hạn chót, không ai huỷ".

Channel: đường ống giữa các goroutine

Channel là một hàng đợi có kiểu dữ liệu, an toàn khi dùng đồng thời. Goroutine này gửi vào, goroutine khác nhận ra. Mũi tên <- chỉ hướng dữ liệu đi:

  • ch <- 42: gửi 42 vào channel
  • v := <-ch: lấy một giá trị ra khỏi channel, gán vào v
package main

import (
    "fmt"
    "time"
)

func main() {
    ch := make(chan string) // channel chở string. Không đệm: người gửi chờ tới khi có người nhận

    go func() {
        time.Sleep(500 * time.Millisecond) // giả lập việc mất thời gian
        ch <- "kết quả từ goroutine"       // gửi vào channel
    }()

    fmt.Println("đang chờ...")
    v := <-ch // ĐỨNG CHỜ ở đây tới khi có giá trị, giống await
    fmt.Println("nhận được:", v)

    buf := make(chan int, 3) // channel có đệm 3 chỗ: gửi chỉ phải chờ khi đã đầy
    buf <- 1
    buf <- 2 // gửi được ngay dù chưa ai nhận, vì còn chỗ trong đệm
    fmt.Println(<-buf, <-buf, len(buf))
}

Câu châm ngôn của Go: "Đừng giao tiếp bằng cách chia sẻ bộ nhớ, hãy chia sẻ bộ nhớ bằng cách giao tiếp." Thay vì nhiều goroutine cùng sửa một biến (phải khoá), hãy để một goroutine sở hữu dữ liệu và những goroutine khác gửi yêu cầu qua channel.

Worker pool: giới hạn số việc chạy cùng lúc

Có 10.000 ảnh cần tạo ảnh thu nhỏ. Mở 10.000 goroutine cùng lúc sẽ ngốn hết RAM và làm nghẽn dịch vụ lưu trữ. Mẫu chuẩn là một nhóm cố định N "thợ" (worker) cùng nhận việc từ một channel:

[fe] Producer / gửi 10.000 việc -> jobs (chan) [go] N worker / mỗi cái lấy việc, xử lý -> results (chan) [db] Gom kết quả / đếm thành công, lỗi 
package main

import (
    "errors"
    "fmt"
    "sync"
    "time"
)

// Giả lập tạo ảnh thu nhỏ: mất 100ms, ảnh có id chia hết cho 7 thì lỗi
func makeThumbnail(id int) error {
    time.Sleep(100 * time.Millisecond)
    if id%7 == 0 {
        return errors.New("ảnh hỏng")
    }
    return nil
}

func process(ids []int, workers int) (ok, failed int) {
    jobs := make(chan int)      // đường ống chở việc
    results := make(chan error) // đường ống chở kết quả

    // 1. Mở đúng `workers` goroutine. Mỗi cái lặp: lấy việc, làm, gửi kết quả
    var wg sync.WaitGroup
    for range workers {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for id := range jobs { // nhận lần lượt, dừng khi jobs bị đóng và đã hết việc
                results <- makeThumbnail(id)
            }
        }()
    }

    // 2. Một goroutine bỏ việc vào jobs, xong thì đóng jobs để các worker biết là hết
    go func() {
        for _, id := range ids {
            jobs <- id
        }
        close(jobs)
    }()

    // 3. Khi mọi worker đã xong thì đóng results, để vòng for bên dưới dừng
    go func() {
        wg.Wait()
        close(results)
    }()

    // 4. main gom kết quả
    for err := range results {
        if err != nil {
            failed++
        } else {
            ok++
        }
    }
    return ok, failed
}

func main() {
    ids := make([]int, 40) // 40 ảnh, id từ 1 đến 40
    for i := range ids {
        ids[i] = i + 1
    }

    start := time.Now()
    ok, failed := process(ids, 8)
    fmt.Println("thành công:", ok, "lỗi:", failed)
    fmt.Println("mất", time.Since(start).Round(100*time.Millisecond)) // 40 việc / 8 thợ x 100ms
}

thành công: 35 lỗi: 5
mất 500ms

Giải thích: 40 ảnh, 8 worker, mỗi ảnh 100ms: mỗi worker làm khoảng 5 ảnh, tổng khoảng 500ms. Không bao giờ có quá 8 ảnh được xử lý cùng lúc. Có 5 id chia hết cho 7 (7, 14, 21, 28, 35) nên 5 lỗi. Thử đổi số worker thành 1 rồi 40 để thấy thời gian thay đổi.

Quy tắc đóng channel: chỉ bên gửi được đóng, và chỉ đóng khi chắc chắn không còn ai gửi nữa. Gửi vào channel đã đóng gây panic. Nhận từ channel đã đóng thì nhận được zero value ngay lập tức, for range trên channel sẽ dừng.

Với trường hợp đơn giản, errgroup có sẵn g.SetLimit(8) để giới hạn số goroutine, ngắn hơn nhiều so với tự viết pool (xem bài tập cuối bài).

select: chờ nhiều thứ cùng lúc

select giống switch, nhưng mỗi case là một thao tác với channel. Nó chờ tới khi một case sẵn sàng, rồi chạy đúng case đó. Giống Promise.race:

package main

import (
    "fmt"
    "time"
)

// Giả lập gọi dịch vụ ngoài mất `d` thời gian, trả kết quả qua channel
func callAPI(d time.Duration) chan string {
    ch := make(chan string, 1)
    go func() {
        time.Sleep(d)
        ch <- "dữ liệu"
    }()
    return ch
}

func main() {
    // Lần 1: dịch vụ trả lời sau 100ms, hạn chờ 1 giây
    select {
    case res := <-callAPI(100 * time.Millisecond):
        fmt.Println("có kết quả:", res)
    case <-time.After(time.Second): // time.After trả về channel, có giá trị sau 1 giây
        fmt.Println("quá 1 giây, bỏ")
    }

    // Lần 2: dịch vụ chậm 3 giây, hạn chờ 1 giây
    select {
    case res := <-callAPI(3 * time.Second):
        fmt.Println("có kết quả:", res)
    case <-time.After(time.Second):
        fmt.Println("quá 1 giây, bỏ")
    }
}

có kết quả: dữ liệu
quá 1 giây, bỏ

Trong code thật, case hay gặp nhất là case <-ctx.Done(): nghĩa là "request đã bị huỷ" (bài {{n:context-test}}).

Mutex: khi buộc phải dùng chung dữ liệu

Nhiều goroutine cùng đọc và ghi một biến mà không đồng bộ gọi là data race. Kết quả sai một cách ngẫu nhiên, và với map còn làm sập chương trình. Chạy chương trình này vài lần:

package main

import (
    "fmt"
    "sync"
)

func main() {
    count := 0
    var wg sync.WaitGroup
    for range 1000 {
        wg.Add(1)
        go func() {
            defer wg.Done()
            count++ // thật ra là 3 bước: đọc count, cộng 1, ghi lại. Các goroutine xen vào nhau
        }()
    }
    wg.Wait()
    fmt.Println(count) // mong 1000
}

$ go run .
947
$ go run .
982

Mỗi lần ra một số khác, hiếm khi đúng 1000 (trên máy nhiều nhân). Hai goroutine cùng đọc count = 5, cùng cộng thành 6, cùng ghi 6: mất một lần đếm.

Sửa bằng sync.Mutex (mutual exclusion, "khoá loại trừ"): chỉ một goroutine được vào đoạn giữa Lock() và Unlock() tại một thời điểm, những goroutine khác xếp hàng chờ:

package main

import (
    "fmt"
    "sync"
)

type Counter struct {
    mu sync.Mutex     // khoá bảo vệ map bên dưới
    n  map[string]int
}

func (c *Counter) Inc(key string) {
    c.mu.Lock()         // xin khoá, ai đang giữ thì chờ
    defer c.mu.Unlock() // trả khoá khi hàm kết thúc
    c.n[key]++
}

func (c *Counter) Get(key string) int {
    c.mu.Lock()
    defer c.mu.Unlock()
    return c.n[key]
}

func main() {
    c := &Counter{n: map[string]int{}}
    var wg sync.WaitGroup
    for range 1000 {
        wg.Add(1)
        go func() {
            defer wg.Done()
            c.Inc("lượt xem")
        }()
    }
    wg.Wait()
    fmt.Println(c.Get("lượt xem"))
}

1000

Biến thể: sync.RWMutex cho nhiều người đọc cùng lúc, chỉ ghi mới khoá độc quyền. Với một bộ đếm số đơn giản, dùng sync/atomic: var n atomic.Int64; n.Add(1).

Kiểm tra nhiều trang web song song

Cho danh sách URL. Với mỗi URL, gửi request GET và ghi lại status (200 OK, 404 Not Found...) hoặc lỗi. Yêu cầu:

  • chạy tối đa 3 request cùng lúc (không phải tất cả một lúc, không phải lần lượt từng cái).
  • mỗi request tối đa 3 giây.
  • in kết quả theo đúng thứ tự danh sách ban đầu, dù request nào xong trước.

https://ten-mien-khong-ton-tai.vn -> lỗi: Get "https://ten-mien-khong-ton-tai.vn": dial tcp: lookup ten-mien-khong-ton-tai.vn: no such host

Gợi ý từng bước

  1. Cài errgroup: go get golang.org/x/sync. Tạo nhóm: var g errgroup.Group, rồi g.SetLimit(3): từ giờ g.Go tự chờ khi đã có 3 việc đang chạy.
  2. Giữ thứ tự: tạo trước out := make([]string, len(urls)). Goroutine thứ i chỉ ghi vào out[i]. Không ai ghi chung ô với ai nên không có race, và thứ tự giữ nguyên.
  3. Gửi request: tạo client := &http.Client{Timeout: 3 * time.Second}, gọi resp, err := client.Get(u). Có lỗi (mạng, tên miền sai) thì ghi lỗi. Không lỗi thì ghi resp.Status, và nhớ resp.Body.Close().
  4. Trong g.Go, luôn return nil kể cả khi URL lỗi, để các URL khác vẫn được kiểm tra.
  5. g.Wait() rồi in out.
Xem lời giải

go mod init checkurl
go get golang.org/x/sync   # thêm errgroup vào go.mod

package main

import (
    "fmt"
    "net/http"
    "time"

    "golang.org/x/sync/errgroup"
)

func checkAll(urls []string) []string {
    out := make([]string, len(urls)) // ô thứ i dành cho url thứ i
    client := &http.Client{Timeout: 3 * time.Second}

    var g errgroup.Group
    g.SetLimit(3) // tối đa 3 goroutine chạy cùng lúc

    for i, u := range urls {
        g.Go(func() error {
            resp, err := client.Get(u)
            if err != nil {
                out[i] = "lỗi: " + err.Error()
                return nil // không trả lỗi, để các URL khác vẫn chạy
            }
            resp.Body.Close() // bắt buộc: trả kết nối lại để dùng lại
            out[i] = resp.Status
            return nil
        })
    }
    g.Wait() // chờ tất cả xong
    return out
}

func main() {
    urls := []string{
        "https://go.dev",
        "https://go.dev/khong-co-trang-nay",
        "https://pkg.go.dev",
        "https://ten-mien-khong-ton-tai.vn",
    }
    for i, status := range checkAll(urls) {
        fmt.Println(urls[i], "->", status)
    }
}

Giải thích: 404 không phải lỗi của client.Get: server vẫn trả lời, chỉ là trả "không có trang này". err chỉ khác nil khi không nói chuyện được với server (sai tên miền, mất mạng, quá 3 giây). Khác fetch của JS ở chỗ nào? Không khác gì: fetch cũng không throw khi gặp 404.

Hai chi tiết thực tế: http.Client mặc định không có timeout (bài {{n:http}}), nên luôn tự đặt. Và luôn Close() body của response, nếu không kết nối không được dùng lại và bị rò rỉ.

Tìm và sửa race

Chạy chương trình "đếm count++" sai ở trên với go run -race . và đọc báo cáo. Sau đó sửa theo ba cách, mỗi cách đều phải in đúng 1000:

  1. Dùng sync.Mutex khoá quanh count++.
  2. Dùng atomic.Int64 thay cho int: var count atomic.Int64, cộng bằng count.Add(1), đọc bằng count.Load().
  3. Không dùng chung biến: mọi goroutine gửi số 1 vào một channel, chỉ một goroutine nhận và cộng.
Xem lời giải 
package main

import (
    "fmt"
    "sync"
    "sync/atomic"
)

func withMutex() int {
    var mu sync.Mutex
    count := 0
    var wg sync.WaitGroup
    for range 1000 {
        wg.Add(1)
        go func() {
            defer wg.Done()
            mu.Lock()
            count++ // chỉ một goroutine ở đây tại một thời điểm
            mu.Unlock()
        }()
    }
    wg.Wait()
    return count
}

func withAtomic() int64 {
    var count atomic.Int64 // phép cộng là một bước duy nhất, không xen vào được
    var wg sync.WaitGroup
    for range 1000 {
        wg.Add(1)
        go func() {
            defer wg.Done()
            count.Add(1)
        }()
    }
    wg.Wait()
    return count.Load()
}

func withChannel() int {
    ch := make(chan int)
    done := make(chan int)

    go func() { // goroutine DUY NHẤT sở hữu biến total, không ai khác đụng vào
        total := 0
        for n := range ch { // nhận tới khi ch bị đóng
            total += n
        }
        done <- total // báo kết quả
    }()

    var wg sync.WaitGroup
    for range 1000 {
        wg.Add(1)
        go func() {
            defer wg.Done()
            ch <- 1 // không cộng, chỉ gửi
        }()
    }
    wg.Wait()     // mọi goroutine đã gửi xong
    close(ch)     // báo cho bên nhận: hết rồi
    return <-done // chờ tổng
}

func main() {
    fmt.Println("mutex:  ", withMutex())
    fmt.Println("atomic: ", withAtomic())
    fmt.Println("channel:", withChannel())
}

mutex:   1000
atomic:  1000
channel: 1000

Chạy go run -race . với lời giải này: không còn cảnh báo nào. Trong thực tế, bộ đếm đơn giản dùng atomic, dữ liệu phức tạp (map, nhiều trường) dùng Mutex, còn channel hợp khi dữ liệu chảy qua nhiều bước xử lý.
