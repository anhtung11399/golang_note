Kubernetes giải quyết việc gì

Bài {{n:trien-khai}} đóng gói API thành image Docker. Chạy một container thì dễ. Nhưng ở công ty có hàng chục dịch vụ, mỗi dịch vụ 3 đến 30 bản, chạy trên hàng chục máy. Ai lo:

  • bản nào chết thì bật lại, máy nào hỏng thì dời container sang máy khác?
  • deploy bản mới từ từ, lỗi thì quay về bản cũ?
  • đông người thì tự thêm bản, vắng thì bớt?
  • dịch vụ này tìm dịch vụ kia ở đâu khi IP liên tục đổi?

Đó là việc của Kubernetes (viết tắt K8s, viết bằng Go). Bạn khai báo trạng thái mong muốn ("luôn có 3 bản API phiên bản 1.4.2"), Kubernetes liên tục so sánh với thực tế và sửa cho khớp.

Giống React: bạn mô tả UI mong muốn (khai báo), React tự tính phải đổi DOM thế nào (reconcile). Kubernetes làm điều đó với container: bạn viết YAML mô tả, các "controller" chạy vòng lặp đưa cụm về đúng trạng thái đó.

Là lập trình viên backend, bạn thường không dựng cụm Kubernetes (đội hạ tầng hoặc dịch vụ quản lý như EKS, GKE, AKS lo). Bạn cần: viết / đọc YAML cho dịch vụ của mình, làm cho chương trình Go chạy đúng trong Kubernetes, và gỡ lỗi khi pod không chạy.

Deployment cho API Go

apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: sobaitap
  labels: { app: api }
spec:
  replicas: 3
  selector:
    matchLabels: { app: api }        # Deployment quản lý các pod có nhãn app=api
  strategy:
    rollingUpdate:
      maxUnavailable: 0              # khi deploy, không bao giờ để thiếu pod
      maxSurge: 1                    # thêm tối đa 1 pod mới mỗi lần
  template:                          # khuôn để tạo pod
    metadata:
      labels: { app: api }
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: api
          image: sobaitap-api:1.4.2  # luôn ghi phiên bản cụ thể, không dùng :latest
          ports:
            - containerPort: 8080
          env:
            - name: PORT
              value: "8080"
            - name: GOMEMLIMIT          # báo cho Go biết giới hạn bộ nhớ của container
              valueFrom:
                resourceFieldRef: { resource: limits.memory }
            - name: GOMAXPROCS          # Go 1.25+ tự đọc giới hạn CPU, dòng này cho bản Go cũ
              valueFrom:
                resourceFieldRef: { resource: limits.cpu }
          envFrom:
            - configMapRef: { name: api-config }
            - secretRef: { name: api-secrets }
          resources:
            requests: { cpu: 250m, memory: 128Mi }   # để xếp chỗ: cần ít nhất chừng này
            limits: { cpu: "1", memory: 256Mi }      # vượt memory → bị giết (OOMKilled)
          readinessProbe:               # sẵn sàng nhận request chưa?
            httpGet: { path: /readyz, port: 8080 }
            periodSeconds: 5
            failureThreshold: 2
          livenessProbe:                # còn sống không? lỗi liên tục → khởi động lại
            httpGet: { path: /healthz, port: 8080 }
            periodSeconds: 10
            failureThreshold: 3
          startupProbe:                 # cho thời gian khởi động, trước đó chưa xét liveness
            httpGet: { path: /healthz, port: 8080 }
            failureThreshold: 30
            periodSeconds: 1
          securityContext:
            runAsNonRoot: true
            readOnlyRootFilesystem: true
            allowPrivilegeEscalation: false

250m nghĩa là 250 mili-CPU, tức một phần tư lõi. 128Mi là 128 mebibyte.

Lỗi kinh điển: liveness kiểm tra database. Database chậm 30 giây → liveness của mọi pod lỗi → Kubernetes giết toàn bộ pod cùng lúc → khởi động lại → dồn kết nối vào database đang yếu → sập hẳn. Database lỗi chỉ nên làm readiness lỗi (ngừng nhận request), không làm pod bị giết.

var ready atomic.Bool

mux.HandleFunc("GET /healthz", func(w http.ResponseWriter, r *http.Request) {

})
mux.HandleFunc("GET /readyz", func(w http.ResponseWriter, r *http.Request) {
    ctx, cancel := context.WithTimeout(r.Context(), time.Second)
    defer cancel()
    if !ready.Load() || pool.Ping(ctx) != nil {
        w.WriteHeader(503)
        return
    }
    w.WriteHeader(200)
})

// main: sau khi kết nối xong mọi thứ
ready.Store(true)

Tắt êm trong Kubernetes

Khi deploy bản mới hoặc dời pod, Kubernetes gửi SIGTERM, chờ terminationGracePeriodSeconds (30 giây), rồi SIGKILL. Đồng thời, nó rút pod khỏi Service, nhưng việc rút này lan tới mọi nơi mất vài giây. Nếu server tắt ngay khi nhận SIGTERM, request đang trên đường tới sẽ lỗi.

Tổng thời gian (5 + 20 giây) phải nhỏ hơn terminationGracePeriodSeconds. Worker đọc hàng đợi cũng vậy: ngừng lấy việc mới, làm nốt việc đang làm.

GOMEMLIMIT: tránh bị OOMKilled

Bộ dọn rác của Go mặc định chạy khi heap tăng gấp đôi so với lần dọn trước. Với limit 256Mi, heap 140MB có thể vọt lên 280MB trước khi GC kịp chạy, container bị giết với trạng thái OOMKilled. Đặt GOMEMLIMIT (Go 1.19+) bằng khoảng 80 đến 90% limit, Go sẽ dọn rác tích cực hơn khi gần chạm ngưỡng. Ở YAML trên, resourceFieldRef đặt bằng đúng limit, an toàn hơn thì đặt tay GOMEMLIMIT: "220MiB".

Với maxSurge: 1, maxUnavailable: 0: tạo 1 pod mới, chờ nó ready, tắt 1 pod cũ, lặp lại. Nếu pod mới không bao giờ ready (bản lỗi), quá trình dừng ở đó, 3 pod cũ vẫn phục vụ. Quay lại:

kubectl -n sobaitap rollout undo deployment/api
kubectl -n sobaitap rollout history deployment/api

Ở công ty, hiếm ai chạy kubectl set image tay. Mẫu phổ biến là GitOps: YAML nằm trong repo git, CI sửa tag image và commit, công cụ (Argo CD, Flux) thấy git đổi thì áp vào cụm. Lịch sử deploy chính là lịch sử git.

Migration với Job

apiVersion: batch/v1
kind: Job
metadata:
  name: migrate-1-4-3
  namespace: sobaitap
spec:
  backoffLimit: 0               # lỗi thì dừng, không chạy lại migration tự động
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: sobaitap-api:1.4.3
          command: ["/app/api", "migrate"]   # cùng binary, lệnh con migrate (dùng goose nhúng, bài sqlc)
          envFrom:
            - secretRef: { name: api-secrets }

Thứ tự trong pipeline: chạy Job migration, chờ thành công (kubectl wait --for=condition=complete job/migrate-1-4-3), rồi mới cập nhật Deployment. Migration phải tương thích với code cũ (expand / contract, bài {{n:orm-sqlc}}), vì trong lúc rolling update, pod cũ và mới cùng chạy.

Tự co giãn với HPA

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: api, namespace: sobaitap }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: api }
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 70 }   # 70% của requests.cpu
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300   # chờ 5 phút ổn định mới giảm, tránh tăng giảm liên tục

HPA tính % CPU theo requests, không phải limits. Không đặt requests thì HPA không chạy. Với worker đọc hàng đợi, CPU không phản ánh đúng lượng việc: dùng KEDA để co giãn theo độ dài hàng đợi (số tin Kafka chưa đọc, số dòng jobs đang chờ).

Tăng pod không giải quyết được nghẽn ở database. 20 pod × pool 20 kết nối = 400 kết nối, vượt max_connections mặc định (100) của Postgres. Tính trước: maxReplicas × pool size phải nhỏ hơn giới hạn database, hoặc đặt PgBouncer ở giữa.

Helm và Kustomize

Có môi trường staging và production, khác nhau số replicas, tên miền, tài nguyên. Không chép YAML hai lần:

  • Kustomize (có sẵn trong kubectl apply -k): một thư mục base/ và các thư mục overlays/staging, overlays/prod chỉ ghi phần khác.
  • Helm: YAML có chỗ trống dạng template Go ({{ .Values.replicas }}), mỗi môi trường một file values.yaml. Cũng là cách cài phần mềm có sẵn (Postgres, Redis, Prometheus) bằng một lệnh.

Không phải lúc nào cũng cần Kubernetes. Một sản phẩm mới, vài dịch vụ, vài nghìn người dùng chạy rất tốt trên Cloud Run, Fly.io, Render, ECS Fargate hay một máy chủ với Docker Compose. Kubernetes đáng giá khi có nhiều dịch vụ, nhiều đội, và có người lo vận hành cụm. Nhưng vì phần lớn công ty vừa và lớn đã dùng, đọc được YAML và biết gỡ lỗi pod là kỹ năng gần như bắt buộc của backend.

- Pod ngừng nhận request cho tới khi Postgres ổn + Mọi pod bị coi là chết và bị khởi động lại cùng lúc, dồn thêm tải lên Postgres, có thể sập toàn bộ dịch vụ - Không có gì ? Kiểm tra phụ thuộc bên ngoài chỉ đặt ở readiness: pod ngừng nhận request nhưng không bị giết. Liveness chỉ kiểm tra tiến trình còn trả lời. - kubectl get pods + kubectl logs <pod> --previous (và kubectl describe pod để xem sự kiện) - kubectl delete pod ? Pod đang khởi động lại, log hiện tại có thể trống. --previous cho log của lần chạy vừa crash. Xoá pod chỉ tạo pod mới bị lỗi giống hệt. + Đặt GOMEMLIMIT khoảng 450MiB để GC dọn sớm hơn khi gần chạm giới hạn - Tăng CPU - Đặt GOGC=off ? GC mặc định cho heap tăng gấp đôi trước khi dọn. GOMEMLIMIT báo cho Go biết trần bộ nhớ thật. GOGC=off thì ngược lại, càng dễ OOM.

Bài tập

Deploy API lên kind, thử rolling update và rollback

Dùng API của bài {{n:trien-khai}} (có Dockerfile, /healthz, /readyz, graceful shutdown). Deploy 3 bản lên cụm kind, gọi thử qua port-forward. Build bản 2 cố tình lỗi (thoát ngay khi khởi động), deploy và quan sát: dịch vụ vẫn chạy bằng bản cũ. Rollback.

Gợi ý từng bước

  1. Image đặt imagePullPolicy: IfNotPresent để kind dùng image đã kind load, không cố tải từ Internet.
  2. Bản lỗi: thêm if os.Getenv("BROKEN") == "" { log.Fatal("thiếu BROKEN") } ở đầu main, build tag :2.
  3. Theo dõi bằng kubectl get pods -w ở một terminal trong khi deploy ở terminal khác.
  4. Trong lúc deploy bản lỗi, chạy vòng while true; do curl -s -o /dev/null -w "%{http_code} " localhost:8080/healthz; sleep 0.5; done: luôn thấy 200.

Giải thích: với maxUnavailable: 0 và maxSurge: 1, Kubernetes chỉ tạo 1 pod bản 2 và chờ nó ready. Pod đó crash liên tục nên không bao giờ ready, ba pod bản 1 không bị đụng tới. Vòng curl luôn trả 200. rollout undo quay Deployment về template trước, pod lỗi bị xoá. Bản thật nên đặt progressDeadlineSeconds để rollout bị đánh dấu thất bại sau một thời gian, CI thấy và báo động.

Đọc YAML và tìm 6 lỗi cấu hình

Deployment dưới đây chạy được nhưng có 6 vấn đề sẽ gây sự cố ở production. Tìm và sửa.

apiVersion: apps/v1
kind: Deployment
metadata: { name: api }
spec:
  replicas: 1
  selector: { matchLabels: { app: api } }
  template:
    metadata: { labels: { app: api } }
    spec:
      containers:
        - name: api
          image: registry.local/api:latest
          env:
            - name: DATABASE_URL
              value: postgres://app:Matkhau123@db:5432/app
          livenessProbe:
            httpGet: { path: /readyz, port: 8080 }
            initialDelaySeconds: 0
            periodSeconds: 2
            failureThreshold: 1

Gợi ý từng bước

  1. Bao nhiêu pod còn lại khi máy chứa pod đó bảo trì?
  2. :latest thì rollback về đâu?
  3. Mật khẩu nằm ở đâu?
  4. Probe nào, kiểm tra cái gì, chịu lỗi được mấy lần?
  5. Thiếu những phần nào so với Deployment mẫu trong bài?
Xem lời giải
  1. replicas: 1: một pod chết hoặc bị dời là dịch vụ ngừng. Ít nhất 2, thường 3, kèm PodDisruptionBudget.
  2. :latest: không biết đang chạy bản nào, rollback không có ý nghĩa, mỗi pod có thể chạy một bản khác. Dùng tag cố định (phiên bản hoặc mã commit).
  3. Mật khẩu viết thẳng trong YAML (commit vào git). Đưa vào Secret, lấy từ kho bí mật.
  4. Liveness gọi /readyz (kiểm tra database), failureThreshold: 1, periodSeconds: 2, không có startupProbe: một lần chậm 2 giây là pod bị giết, database chập chờn là mọi pod bị giết. Liveness gọi /healthz, thêm readinessProbe gọi /readyz, thêm startupProbe, failureThreshold 3.
  5. Không có resources: không có requests thì scheduler xếp bừa, HPA không chạy. Không có limits thì một pod rò bộ nhớ ảnh hưởng cả máy.
  6. Không có securityContext, strategy, terminationGracePeriodSeconds, GOMEMLIMIT: chạy bằng root, deploy có thể làm thiếu pod, không kiểm soát thời gian tắt.
spec:
  replicas: 3
  strategy: { rollingUpdate: { maxUnavailable: 0, maxSurge: 1 } }
  template:
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: api
          image: registry.local/api:1.4.3
          envFrom: [{ secretRef: { name: api-secrets } }]
          env: [{ name: GOMEMLIMIT, value: "220MiB" }]
          resources:
            requests: { cpu: 250m, memory: 128Mi }
            limits: { memory: 256Mi }
          startupProbe: { httpGet: { path: /healthz, port: 8080 }, failureThreshold: 30, periodSeconds: 1 }
          livenessProbe: { httpGet: { path: /healthz, port: 8080 }, periodSeconds: 10, failureThreshold: 3 }
          readinessProbe: { httpGet: { path: /readyz, port: 8080 }, periodSeconds: 5, failureThreshold: 2 }
          securityContext: { runAsNonRoot: true, readOnlyRootFilesystem: true, allowPrivilegeEscalation: false }

Ghi chú: nhiều đội cố ý không đặt limits.cpu (chỉ đặt requests), vì giới hạn CPU làm Go bị "bóp" (throttling) gây đuôi độ trễ cao, trong khi bộ nhớ thì luôn phải có limit.
