Lỗi là giá trị

Go không có try / catch. Hàm có thể thất bại thì trả về thêm một giá trị kiểu error ở vị trí cuối cùng, và người gọi kiểm tra ngay sau khi gọi:

package main

import (
    "fmt"
    "os"
)

func main() {
    f, err := os.Open("data.csv") // trả về 2 giá trị: file và lỗi
    if err != nil {               // có lỗi: xử lý rồi dừng
        fmt.Println("không mở được file:", err)
        return
    }
    defer f.Close() // tới được đây là mở thành công
    fmt.Println("đã mở file")
}

không mở được file: open data.csv: no such file or directory

Thư mục của bạn không có file data.csv nên ra nhánh lỗi. Tạo một file tên data.csv cạnh main.go rồi chạy lại sẽ thấy "đã mở file".

error không có gì bí ẩn, nó chỉ là một interface có sẵn (bài 06): kiểu nào có method Error() string là lỗi.

Lúc đầu bạn sẽ thấy if err != nil lặp lại ở khắp nơi. Đây là chủ đích: đường đi của lỗi hiện rõ trên màn hình. Khi đọc một hàm Go, bạn thấy ngay mọi chỗ có thể hỏng và chuyện gì xảy ra lúc đó, điều mà await trong một khối try lớn không cho bạn thấy.

Bọc lỗi để giữ ngữ cảnh

Một lỗi trần như connection refused không cho biết lỗi xảy ra khi đang làm gì. Mỗi tầng nên thêm ngữ cảnh bằng fmt.Errorf với %w (w = wrap, bọc):

package main

import (
    "errors"
    "fmt"
)

// Tầng trong cùng: giả lập database không kết nối được
func queryDB() error {
    return errors.New("connection refused")
}

// Tầng repository: bọc thêm "đang lấy lớp nào"
func getClass(id int64) error {
    if err := queryDB(); err != nil {
        return fmt.Errorf("lấy lớp %d: %w", id, err) // %w: chèn lỗi gốc vào, và GIỮ nó bên trong
    }
    return nil
}

// Tầng service: bọc thêm "đang làm nghiệp vụ gì"
func classReport(id int64) error {
    if err := getClass(id); err != nil {
        return fmt.Errorf("tạo báo cáo lớp: %w", err)
    }
    return nil
}

func main() {
    err := classReport(42)
    fmt.Println(err)
}

tạo báo cáo lớp: lấy lớp 42: connection refused

Lỗi cuối cùng đọc như một câu chuyện, từ ngoài vào trong: đang tạo báo cáo, lúc lấy lớp 42 thì database từ chối kết nối. Đọc log là biết ngay chỗ hỏng.

actors: [fe] Client, [go] Handler, [go] Service, [db] Repository Client -> Handler: GET /classes/42/report Handler -> Service: ClassReport(42) Service -> Repository: GetClass(42) Repository --> Service: "lấy lớp 42: connection refused" Service --> Handler: "tạo báo cáo lớp: lấy lớp 42: ..." note Handler: ghi log lỗi đầy đủ, một lần duy nhất Handler --> Client: 500 {"error": "Máy chủ đang bận, thử lại sau"}

%w và %v in ra giống hệt nhau, nhưng khác nhau ở bên trong: %w giữ lỗi gốc để errors.Is / errors.As còn tìm thấy. %v chỉ chép chữ, lỗi gốc mất. Gần như luôn dùng %w.

Lỗi định sẵn (sentinel) và errors.Is

Với các lỗi mà người gọi cần phân biệt để xử lý khác nhau (không tìm thấy thì trả 404, không có quyền thì trả 403), khai báo sẵn thành biến dùng chung. errors.Is kiểm tra "trong chuỗi lỗi bọc nhau này có lỗi X không", kể cả khi đã bọc nhiều lớp:

package main

import (
    "errors"
    "fmt"
)

// Lỗi định sẵn: tên bắt đầu bằng Err, khai báo một lần ở cấp package
var (
    ErrNotFound  = errors.New("không tìm thấy")
    ErrForbidden = errors.New("không có quyền")
)

func findClass(id int64) error {
    if id != 1 {
        return fmt.Errorf("lấy lớp %d: %w", id, ErrNotFound) // bọc lỗi định sẵn kèm ngữ cảnh
    }
    return nil
}

func main() {
    err := findClass(42)
    fmt.Println(err)

    // So sánh trực tiếp thất bại vì err là lỗi BỌC NGOÀI, không phải chính ErrNotFound
    fmt.Println(err == ErrNotFound)

    // errors.Is lột từng lớp bọc ra để tìm
    fmt.Println(errors.Is(err, ErrNotFound))
    fmt.Println(errors.Is(err, ErrForbidden))

    if errors.Is(err, ErrNotFound) {
        fmt.Println("-> trả về 404")
    }
}

Repository nên dịch lỗi của thư viện database (pgx.ErrNoRows, lỗi trùng khoá...) thành lỗi của chính ứng dụng (ErrNotFound, ErrConflict). Nhờ vậy tầng service và HTTP không phụ thuộc vào việc bạn dùng Postgres hay thứ khác. Trong code thật nó trông như sau (trích đoạn, bài 15 có đầy đủ):

if errors.Is(err, pgx.ErrNoRows) {
    return Class{}, ErrNotFound // đổi lỗi của thư viện thành lỗi của mình
}

Kiểu lỗi riêng và errors.As

Khi lỗi cần mang thêm dữ liệu (trường nào sai, sai vì sao), tạo một kiểu lỗi riêng: một struct có method Error(). errors.As tìm trong chuỗi lỗi một lỗi đúng kiểu đó và lấy nó ra cho bạn dùng các trường:

package main

import (
    "errors"
    "fmt"
    "unicode/utf8"
)

type ValidationError struct {
    Field   string
    Message string
}

// Có method Error() string, nên *ValidationError là một error
func (e *ValidationError) Error() string {
    return e.Field + ": " + e.Message
}

func validateClassName(name string) error {
    if utf8.RuneCountInString(name) > 10 {
        return &ValidationError{Field: "name", Message: "Tên lớp tối đa 10 ký tự"}
    }
    return nil
}

func createClass(name string) error {
    if err := validateClassName(name); err != nil {
        return fmt.Errorf("tạo lớp: %w", err)
    }
    return nil
}

func main() {
    err := createClass("Lớp chuyên Toán khối 10")

    var ve *ValidationError   // biến rỗng để errors.As đổ kết quả vào
    if errors.As(err, &ve) {  // "trong err có lỗi kiểu *ValidationError không? có thì gán vào ve"
        fmt.Println("trường sai:", ve.Field)
        fmt.Println("báo người dùng:", ve.Message)
    }
}

trường sai: name
báo người dùng: Tên lớp tối đa 10 ký tự

Nhớ nhanh: errors.Is hỏi "có phải lỗi này không" (so với một biến lỗi định sẵn). errors.As hỏi "có lỗi nào thuộc kiểu này không" (rồi lấy dữ liệu bên trong). Giống e instanceof ValidationError trong JS.

Biến lỗi thành response HTTP ở một chỗ

Ngoài thực tế, mỗi dự án có một hàm duy nhất quyết định lỗi nào thành status code nào và người dùng thấy câu gì. Không handler nào tự viết 500 lung tung. Đây là trích đoạn từ dự án thật, bạn sẽ dựng nó ở bài 12:

func WriteError(w http.ResponseWriter, r *http.Request, err error) {
    var ve *ValidationError
    switch {
    case errors.As(err, &ve): // lỗi dữ liệu đầu vào: báo rõ cho người dùng
        writeJSON(w, http.StatusBadRequest, errBody("INVALID", ve.Message))
    case errors.Is(err, ErrNotFound):
        writeJSON(w, http.StatusNotFound, errBody("NOT_FOUND", "Không tìm thấy"))
    case errors.Is(err, ErrForbidden):
        writeJSON(w, http.StatusForbidden, errBody("FORBIDDEN", "Bạn không có quyền"))
    case errors.Is(err, context.DeadlineExceeded): // quá thời gian (bài 10)
        writeJSON(w, http.StatusGatewayTimeout, errBody("TIMEOUT", "Máy chủ xử lý quá lâu"))
    default:
        // Lỗi không lường trước: ghi log đầy đủ, KHÔNG trả chi tiết cho client
        slog.ErrorContext(r.Context(), "lỗi không xử lý", "err", err, "path", r.URL.Path)
        writeJSON(w, http.StatusInternalServerError, errBody("INTERNAL", "Có lỗi xảy ra, vui lòng thử lại"))
    }
}

Đừng bao giờ trả nguyên err.Error() của lỗi hệ thống cho client. Chuỗi lỗi có thể chứa tên bảng, câu SQL, địa chỉ IP nội bộ, đường dẫn file: những thứ kẻ tấn công rất muốn biết. Lỗi nghiệp vụ (validation) thì được viết sẵn cho người dùng đọc nên trả được.

panic và recover

panic dừng hàm ngay lập tức và đi ngược lên chuỗi gọi hàm, chạy các defer trên đường đi. Nếu không ai recover, cả chương trình dừng. Gần giống throw mà không có catch.

Panic dành cho lỗi lập trình, những thứ "không thể xảy ra nếu code đúng": truy cập ngoài phạm vi slice, nil pointer, cấu hình bắt buộc bị thiếu lúc khởi động. Lỗi có thể đoán trước (người dùng nhập sai, không tìm thấy, mạng lỗi) luôn dùng error.

func mustEnv(key string) string {
    v := os.Getenv(key) // đọc biến môi trường, giống process.env[key]
    if v == "" {
        // chấp nhận được: lúc khởi động, sai cấu hình thì nên dừng ngay
        panic("thiếu biến môi trường " + key)
    }
    return v
}

recover() "bắt" panic, nhưng chỉ có tác dụng khi gọi bên trong một hàm defer. Xem nó chạy:

package main

import "fmt"

func safeDivide(a, b int) (result int, err error) {
    defer func() {
        if v := recover(); v != nil { // có panic: v là giá trị panic, chương trình KHÔNG dừng
            err = fmt.Errorf("đã chặn panic: %v", v)
        }
    }()
    return a / b, nil // b = 0 thì phép chia gây panic
}

func main() {
    fmt.Println(safeDivide(10, 2))
    fmt.Println(safeDivide(10, 0))
    fmt.Println("chương trình vẫn chạy tiếp")
}

(result int, err error) là giá trị trả về có tên: hàm defer gán được err trước khi hàm thật sự trả về. Đây là một trong số ít chỗ nên dùng cách viết này.

Ứng dụng phổ biến nhất của recover: middleware chặn panic để một request lỗi không làm hỏng cả server (trích đoạn, bài 13 dùng lại):

func Recover(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if v := recover(); v != nil {
                slog.Error("panic", "value", v, "stack", string(debug.Stack()))
                http.Error(w, "Có lỗi xảy ra", http.StatusInternalServerError)
            }
        }()
        next.ServeHTTP(w, r) // chạy handler thật, panic ở trong sẽ bị defer phía trên bắt
    })
}

net/http của Go đã tự recover panic trong handler và chỉ đóng kết nối đó, nên server không sập. Nhưng nó không ghi log theo định dạng của bạn và client chỉ thấy kết nối bị cắt. Middleware như trên cho bạn log có cấu trúc và một response tử tế. Lưu ý: panic trong một goroutine bạn tự tạo ra (go func() {...}()) thì không middleware nào cứu được: nó làm dừng cả tiến trình. Goroutine chạy nền phải tự có recover.

Bài tập

Rút tiền

Viết hàm Withdraw(balance, amount int64) (int64, error): rút amount từ số dư balance, trả về số dư mới.

  • amount <= 0: trả *ValidationError (kiểu lỗi ở trên) với thông báo "Số tiền phải lớn hơn 0".
  • không đủ tiền: trả lỗi định sẵn ErrInsufficientFunds, bọc kèm số tiền muốn rút và số dư hiện tại.

Viết thêm statusOf(err error) int đổi lỗi thành mã HTTP: không lỗi 200, validation 400, không đủ tiền 409, còn lại 500. Kết quả mong muốn:

rút 30000: số dư 70000, lỗi , mã 200
rút 0: số dư 100000, lỗi amount: Số tiền phải lớn hơn 0, mã 400
rút 500000: số dư 100000, lỗi rút 500000, còn 100000: số dư không đủ, mã 409

Gợi ý từng bước

  1. Khai báo var ErrInsufficientFunds = errors.New("số dư không đủ") ở ngoài hàm.
  2. Trong Withdraw, kiểm tra theo kiểu guard clause (bài 03): sai thì return luôn. Khi lỗi, trả lại balance cũ.
  3. Bọc lỗi: fmt.Errorf("rút %d, còn %d: %w", amount, balance, ErrInsufficientFunds).
  4. Trong statusOf, dùng switch không biểu thức với errors.As và errors.Is, giống hàm WriteError ở trên.
Xem lời giải 
package main

import (
    "errors"
    "fmt"
)

type ValidationError struct {
    Field   string
    Message string
}

func (e *ValidationError) Error() string { return e.Field + ": " + e.Message }

var ErrInsufficientFunds = errors.New("số dư không đủ")

func Withdraw(balance, amount int64) (int64, error) {
    if amount <= 0 {
        return balance, &ValidationError{Field: "amount", Message: "Số tiền phải lớn hơn 0"}
    }
    if amount > balance {
        return balance, fmt.Errorf("rút %d, còn %d: %w", amount, balance, ErrInsufficientFunds)
    }
    return balance - amount, nil
}

func statusOf(err error) int {
    var ve *ValidationError
    switch {
    case err == nil:
        return 200
    case errors.As(err, &ve):
        return 400
    case errors.Is(err, ErrInsufficientFunds):
        return 409 // Conflict: yêu cầu hợp lệ nhưng mâu thuẫn với trạng thái hiện tại
    default:
        return 500
    }
}

func main() {
    for _, amount := range []int64{30000, 0, 500000} {
        newBalance, err := Withdraw(100000, amount)
        fmt.Printf("rút %d: số dư %d, lỗi %v, mã %d\n", amount, newBalance, err, statusOf(err))
    }
}

Giải thích: lỗi thứ ba đã bị bọc (có thêm "rút 500000, còn 100000"), nhưng errors.Is vẫn tìm thấy ErrInsufficientFunds bên trong nên ra 409. Thử đổi %w thành %v trong Withdraw: chữ in ra y hệt, nhưng mã thành 500.
