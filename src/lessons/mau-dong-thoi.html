Vì sao cần "mẫu"

Bài {{n:dong-thoi}} dạy các viên gạch: goroutine, channel, sync.WaitGroup, sync.Mutex, select. Bài {{n:context-test}} thêm context. Nhưng khi đọc code ở công ty, bạn sẽ thấy người ta ghép các viên gạch đó theo vài kiểu lặp đi lặp lại. Thuộc các kiểu này thì vừa đọc code nhanh, vừa tránh được ba lỗi kinh điển:

  • Chạy quá nhiều việc cùng lúc: 10.000 goroutine cùng gọi một API bên ngoài, API đó chặn bạn, hoặc database hết kết nối.
  • Rò rỉ goroutine (goroutine leak): goroutine bị kẹt mãi ở một channel không ai đọc, bộ nhớ tăng dần cho tới khi server bị khởi động lại.
  • Mất lỗi: 1 trong 50 việc chạy song song bị lỗi nhưng không ai biết.

Bài này đi qua 9 mẫu. Mỗi mẫu có: bài toán, code chạy được, kết quả, và bẫy hay gặp.

Mẫu 1: Worker pool

Bài toán: có 1.000 ảnh cần tạo thumbnail. Mỗi ảnh tốn khoảng 50ms CPU. Máy có 8 lõi. Tạo 1.000 goroutine cùng lúc thì chúng tranh nhau CPU, tốn RAM, và không nhanh hơn 8 goroutine. Cách làm chuẩn: tạo N worker cố định, mỗi worker lấy việc từ một channel chung.

package main

import (
    "fmt"
    "sync"
    "time"
)

type Job struct{ ID int }
type Result struct {
    JobID  int
    Worker int
}

func worker(id int, jobs <-chan Job, results chan<- Result, wg *sync.WaitGroup) {
    defer wg.Done()
    for j := range jobs { // chạy tới khi jobs bị đóng VÀ đã đọc hết
        time.Sleep(10 * time.Millisecond) // giả lập việc nặng
        results <- Result{JobID: j.ID, Worker: id}
    }
}

func main() {
    const numJobs, numWorkers = 12, 3
    jobs := make(chan Job)
    results := make(chan Result)

    var wg sync.WaitGroup
    for w := 1; w <= numWorkers; w++ {
        wg.Add(1)
        go worker(w, jobs, results, &wg)
    }

    // Gửi việc ở goroutine riêng, xong thì đóng jobs để worker biết là hết
    go func() {
        for i := 1; i <= numJobs; i++ {
            jobs <- Job{ID: i}
        }
        close(jobs)
    }()

    // Khi mọi worker xong thì đóng results, để vòng range bên dưới kết thúc
    go func() {
        wg.Wait()
        close(results)
    }()

    start := time.Now()
    count := map[int]int{}
    for r := range results {
        count[r.Worker]++
    }
    fmt.Println("số việc mỗi worker:", count)
    fmt.Println("thời gian ~", time.Since(start).Round(10*time.Millisecond))
}

$ go run .
số việc mỗi worker: map[1:4 2:4 3:4]
thời gian ~ 40ms

Giải thích: 12 việc, mỗi việc 10ms, 3 worker chạy song song nên mất khoảng 12 × 10 / 3 = 40ms. Mỗi lần chạy, số việc của từng worker có thể lệch đi một chút (ví dụ map[1:5 2:4 3:3]) vì worker nào rảnh trước thì lấy việc trước.

Ba chi tiết bắt buộc phải đúng, sai một cái là chương trình treo:

  1. Ai đóng jobs? Bên gửi, sau khi gửi xong. Không đóng thì for j := range jobs của worker chờ mãi.
  2. Ai đóng results? Một goroutine riêng chờ wg.Wait(). Không thể để worker đóng (worker 1 đóng trong khi worker 2 còn gửi → panic "send on closed channel").
  3. Gửi việc phải ở goroutine riêng. Nếu main tự gửi 12 việc rồi mới đọc kết quả, cả hai channel đều không có bộ đệm: worker kẹt ở results <- vì chưa ai đọc, main kẹt ở jobs <- vì worker không rảnh. Go báo fatal error: all goroutines are asleep - deadlock!.

Chọn số worker thế nào? Việc nặng CPU: bằng số lõi, runtime.NumCPU(). Việc chủ yếu chờ mạng / database: nhiều hơn (20 đến 100), nhưng không vượt số kết nối tối đa của database pool (bài {{n:go-postgres}}) hoặc giới hạn của API bên ngoài.

Mẫu 2: errgroup, cách viết gọn hơn và có lỗi

Worker pool tự viết dài và dễ sai. Trong code thật, 90% trường hợp người ta dùng golang.org/x/sync/errgroup. Nó gộp WaitGroup + giữ lỗi đầu tiên + huỷ context của các việc còn lại + giới hạn số việc chạy cùng lúc.

go get golang.org/x/sync

package main

import (
    "context"
    "errors"
    "fmt"
    "time"

    "golang.org/x/sync/errgroup"
)

func fetchUser(ctx context.Context, id int) (string, error) {
    select {
    case <-time.After(time.Duration(id*10) * time.Millisecond):
        if id == 4 {
            return "", errors.New("user 4: không tìm thấy")
        }
        return fmt.Sprintf("user-%d", id), nil
    case <-ctx.Done(): // việc khác đã lỗi → dừng sớm
        return "", ctx.Err()
    }
}

func main() {
    g, ctx := errgroup.WithContext(context.Background())
    g.SetLimit(3) // tối đa 3 việc chạy cùng lúc: đây chính là semaphore

    ids := []int{1, 2, 3, 4, 5, 6, 7, 8}
    names := make([]string, len(ids)) // mỗi goroutine ghi vào ô riêng → không cần mutex

    for i, id := range ids {
        g.Go(func() error { // Go 1.22+: i, id là biến riêng của mỗi vòng lặp
            name, err := fetchUser(ctx, id)
            if err != nil {
                return err
            }
            names[i] = name
            return nil
        })
    }

    if err := g.Wait(); err != nil { // chờ tất cả, trả lỗi ĐẦU TIÊN
        fmt.Println("lỗi:", err)
    }
    fmt.Printf("%q\n", names)
}

$ go run .
lỗi: user 4: không tìm thấy
["user-1" "user-2" "user-3" "" "" "" "" ""]

Giải thích: việc 1, 2, 3 chạy trước (giới hạn 3). Việc 1 xong ở 10ms thì việc 4 bắt đầu, việc 4 lỗi ở khoảng 50ms. Lỗi đó huỷ ctx, nên các việc 5, 6, 7 đang chạy nhận ctx.Done() và dừng, việc 8 không còn được chạy. g.Wait() trả lỗi đầu tiên, các lỗi context canceled phía sau bị bỏ qua.

g.Go với SetLimit sẽ chặn (block) khi đã đủ số việc đang chạy. Vì vậy vòng for bên ngoài cũng chạy chậm theo. Đó là điều mình muốn: không bao giờ có hơn 3 goroutine tồn tại.

Khi nào không muốn huỷ khi một việc lỗi? Ví dụ gửi email cho 500 phụ huynh: một email lỗi không nên chặn 499 email còn lại. Khi đó dùng errgroup.Group thường (không WithContext), mỗi việc tự ghi lỗi của mình vào một slice, và luôn trả nil:

var g errgroup.Group
g.SetLimit(10)
errs := make([]error, len(parents))
for i, p := range parents {
    g.Go(func() error {
        errs[i] = sendEmail(ctx, p)
        return nil // không để một lỗi làm dừng cả nhóm
    })
}
g.Wait()
err := errors.Join(errs...) // gộp mọi lỗi (nil bị bỏ qua), Go 1.20+

Mẫu 3: Pipeline

Bài toán: đọc 1 triệu dòng log, lọc dòng lỗi, tách trường, ghi vào database theo lô. Mỗi bước là một giai đoạn (stage), nối nhau bằng channel. Lợi ích: các giai đoạn chạy song song với nhau (đọc dòng 1.000 trong khi đang ghi lô dòng 1 đến 500), và bộ nhớ dùng ít vì không giữ cả 1 triệu dòng.

node a 70 80 file "Đọc file" "hàm gen" node b 260 80 goroutine "Lọc" "chỉ dòng ERROR" node c 450 80 goroutine "Tách trường" "parse" node d 640 80 store "Ghi lô" "500 dòng / lần" edge a b "chan string" edge b c "chan string" edge c d "chan Entry" 
package main

import (
    "context"
    "fmt"
    "strings"
)

// Mỗi giai đoạn: nhận channel vào, trả channel ra, tự đóng channel ra khi xong.
// Luôn có select với ctx.Done() để có thể dừng giữa chừng mà không rò rỉ goroutine.

func gen(ctx context.Context, lines ...string) <-chan string {
    out := make(chan string)
    go func() {
        defer close(out)
        for _, l := range lines {
            select {
            case out <- l:
            case <-ctx.Done():
                return
            }
        }
    }()
    return out
}

func filter(ctx context.Context, in <-chan string, keep func(string) bool) <-chan string {
    out := make(chan string)
    go func() {
        defer close(out)
        for l := range in {
            if !keep(l) {
                continue
            }
            select {
            case out <- l:
            case <-ctx.Done():
                return
            }
        }
    }()
    return out
}

type Entry struct{ Level, Msg string }

func parse(ctx context.Context, in <-chan string) <-chan Entry {
    out := make(chan Entry)
    go func() {
        defer close(out)
        for l := range in {
            level, msg, _ := strings.Cut(l, " ")
            select {
            case out <- Entry{level, msg}:
            case <-ctx.Done():
                return
            }
        }
    }()
    return out
}

func main() {
    ctx, cancel := context.WithCancel(context.Background())
    defer cancel() // main thoát sớm → mọi giai đoạn nhận Done và dừng

    src := gen(ctx,
        "INFO server started",
        "ERROR db timeout",
        "INFO request ok",
        "ERROR disk full",
    )
    errorsOnly := filter(ctx, src, func(l string) bool { return strings.HasPrefix(l, "ERROR") })

    for e := range parse(ctx, errorsOnly) {
        fmt.Printf("%-5s | %s\n", e.Level, e.Msg)
    }
}

$ go run .
ERROR | db timeout
ERROR | disk full

Giải thích: gen gửi 4 dòng, filter chỉ cho 2 dòng ERROR đi qua, parse tách "ERROR" và phần còn lại. Khi gen gửi xong, nó đóng channel, filter thoát vòng range và đóng channel của mình, parse cũng vậy, cuối cùng vòng range trong main kết thúc. "Đóng dây chuyền" từ đầu tới cuối.

Vì sao mỗi lần gửi đều phải có select ... ctx.Done()? Giả sử main chỉ lấy kết quả đầu tiên rồi return. Không có ctx.Done(), goroutine parse sẽ kẹt mãi ở out <- ... vì không còn ai đọc, kéo theo filter và gen kẹt theo. Trong server chạy hàng tháng, mỗi request rò 3 goroutine là đủ làm hết RAM.

Mẫu 4: Fan-out, fan-in

Nếu giai đoạn "Tách trường" chậm nhất, ta chạy nhiều bản của nó cùng đọc một channel vào (fan-out), rồi gộp các channel ra thành một (fan-in). Hàm gộp chuẩn:

// merge gộp nhiều channel thành một. Channel ra đóng khi MỌI channel vào đã đóng.
func merge[T any](ctx context.Context, ins ...<-chan T) <-chan T {
    out := make(chan T)
    var wg sync.WaitGroup
    wg.Add(len(ins))
    for _, in := range ins {
        go func() {
            defer wg.Done()
            for v := range in {
                select {
                case out <- v:
                case <-ctx.Done():
                    return
                }
            }
        }()
    }
    go func() { wg.Wait(); close(out) }()
    return out
}

// Dùng: 4 bản parse cùng đọc errorsOnly
p1, p2, p3, p4 := parse(ctx, errorsOnly), parse(ctx, errorsOnly), parse(ctx, errorsOnly), parse(ctx, errorsOnly)
for e := range merge(ctx, p1, p2, p3, p4) { ... }

Lưu ý: fan-out làm mất thứ tự. Dòng 2 có thể ra trước dòng 1. Nếu thứ tự quan trọng, gắn số thứ tự vào mỗi phần tử rồi sắp xếp lại ở cuối, hoặc đừng fan-out.

Mẫu 5: Semaphore bằng channel có bộ đệm

Đôi khi bạn không muốn dùng thư viện, hoặc cần giới hạn số việc cùng lúc ở một đoạn code dùng chung cho cả server (ví dụ: cả server chỉ được gọi tối đa 5 request tới dịch vụ AI cùng lúc, bất kể bao nhiêu người dùng). Channel có bộ đệm N là một semaphore:

var aiSlots = make(chan struct{}, 5) // tối đa 5 lượt cùng lúc trên toàn server

func callAI(ctx context.Context, prompt string) (string, error) {
    select {
    case aiSlots <- struct{}{}: // lấy một lượt (đầy 5 thì chờ)
    case <-ctx.Done():          // chờ lâu quá, người dùng đã huỷ
        return "", ctx.Err()
    }
    defer func() { <-aiSlots }() // trả lượt

    return doCallAI(ctx, prompt)
}

struct{} là kiểu rỗng, chiếm 0 byte: ta chỉ cần "chỗ", không cần giá trị. Thư viện golang.org/x/sync/semaphore có thêm trọng số (một việc lớn chiếm 3 lượt), nhưng bản channel đủ cho hầu hết trường hợp.

Mẫu 6: sync.Once, khởi tạo một lần

Đọc file cấu hình, nạp mẫu email, kết nối tới dịch vụ ít dùng: chỉ làm khi cần lần đầu, và chỉ làm đúng một lần dù 100 goroutine gọi cùng lúc.

package main

import (
    "fmt"
    "sync"
)

var loadTemplates = sync.OnceValue(func() map[string]string {
    fmt.Println("đang nạp mẫu email...") // chỉ in MỘT lần
    return map[string]string{"welcome": "Chào {name}!"}
})

func main() {
    var wg sync.WaitGroup
    for range 5 {
        wg.Add(1)
        go func() {
            defer wg.Done()
            _ = loadTemplates()["welcome"]
        }()
    }
    wg.Wait()
    fmt.Println("mẫu:", loadTemplates()["welcome"])
}

$ go run .
đang nạp mẫu email...
mẫu: Chào {name}!

sync.OnceValue (Go 1.21+) trả về một hàm: gọi lần đầu thì chạy hàm bên trong, các lần sau trả lại kết quả đã có. Có cả sync.OnceValues cho hàm trả (T, error). Bản cũ là var once sync.Once; once.Do(func(){...}), bạn sẽ gặp nhiều trong code cũ.

Nếu hàm khởi tạo lỗi (ví dụ mạng chập chờn), Once vẫn coi là "đã làm", lần sau không thử lại. Với việc có thể lỗi tạm thời, đừng dùng Once, dùng mutex + biến kiểm tra.

Mẫu 7: atomic và sync.Pool, khi cần nhanh

Đếm số request từ nhiều goroutine: dùng mutex được, nhưng sync/atomic nhanh hơn nhiều lần và gọn hơn.

var requests atomic.Int64 // Go 1.19+: kiểu có sẵn, không cần con trỏ

func handler(w http.ResponseWriter, r *http.Request) {
    requests.Add(1)
    // ...
}

// ở chỗ khác, đọc an toàn từ goroutine bất kỳ:
fmt.Println(requests.Load())

Chỉ dùng atomic cho một biến đơn lẻ. Cần cập nhật hai biến cùng lúc cho khớp nhau (ví dụ sum và count để tính trung bình) thì phải dùng mutex, vì atomic không bảo đảm hai lệnh đi liền nhau.

sync.Pool giữ lại các đối tượng tạm (bộ đệm byte, encoder) để dùng lại, giảm việc cấp phát bộ nhớ và công việc của bộ dọn rác (GC). Thư viện chuẩn dùng nó trong fmt và encoding/json.

var bufPool = sync.Pool{New: func() any { return new(bytes.Buffer) }}

func render(data any) []byte {
    buf := bufPool.Get().(*bytes.Buffer)
    buf.Reset()             // QUAN TRỌNG: xoá dữ liệu của lần dùng trước
    defer bufPool.Put(buf)  // trả về pool

    json.NewEncoder(buf).Encode(data)
    return bytes.Clone(buf.Bytes()) // sao chép ra, vì buf sẽ được người khác dùng lại
}

Đừng dùng sync.Pool khi chưa đo (bài {{n:quan-sat}}, pprof). Với API bình thường, chỗ chậm là database, không phải cấp phát bộ nhớ. Pool chỉ đáng khi profile cho thấy GC chiếm phần lớn CPU.

Mẫu 8: Ticker, việc lặp lại định kỳ

Mỗi 30 giây dọn phiên hết hạn, mỗi phút đẩy số liệu đi. Dùng time.Ticker trong một goroutine, luôn có đường thoát bằng context:

func runCleanup(ctx context.Context, every time.Duration) {
    t := time.NewTicker(every)
    defer t.Stop()
    for {
        select {
        case <-t.C:
            if err := deleteExpiredSessions(ctx); err != nil {
                slog.Error("dọn phiên", "err", err) // lỗi một lần, lần sau thử tiếp
            }
        case <-ctx.Done():
            return // server tắt
        }
    }
}

// trong main:
go runCleanup(ctx, 30*time.Second)

Nếu một lần dọn mất lâu hơn 30 giây, ticker bỏ qua các nhịp bị lỡ (channel t.C chỉ chứa 1 nhịp), không dồn lại chạy liên tục. Khi chạy nhiều bản server, cả 3 bản cùng dọn: với việc như xoá phiên hết hạn thì vô hại, với việc như "gửi email tổng kết hằng ngày" thì cần khoá phân tán hoặc một bản riêng chạy cron (bài {{n:bat-dong-bo}}).

Mẫu 9: Rate limit và debounce

Giới hạn tần suất phía bạn gọi đi: API bên ngoài chỉ cho 10 request mỗi giây. Dùng golang.org/x/time/rate (thuật toán token bucket):

import "golang.org/x/time/rate"

lim := rate.NewLimiter(10, 20) // 10 request/giây, cho dồn tối đa 20 (burst)

for _, item := range items {
    if err := lim.Wait(ctx); err != nil { // chờ tới lượt, hoặc ctx bị huỷ
        return err
    }
    callExternalAPI(ctx, item)
}

Debounce: người dùng sửa sơ đồ lớp liên tục, mỗi thay đổi đều muốn "lưu", nhưng chỉ cần lưu khi họ ngừng tay 2 giây. Bạn đã làm việc này ở frontend với setTimeout, Go dùng time.AfterFunc:

type Debouncer struct {
    mu sync.Mutex
    t  *time.Timer
}

func (d *Debouncer) Call(wait time.Duration, fn func()) {
    d.mu.Lock()
    defer d.mu.Unlock()
    if d.t != nil {
        d.t.Stop() // huỷ lần hẹn trước
    }
    d.t = time.AfterFunc(wait, fn) // hẹn lại từ đầu
}

Giống hệt clearTimeout(t); t = setTimeout(fn, 2000). Khác biệt: fn chạy ở một goroutine khác, nên nếu nó đụng tới dữ liệu dùng chung thì phải có mutex.

Phát hiện rò rỉ goroutine

Ba cách, từ dễ tới chuyên:

  1. Đếm: runtime.NumGoroutine(). In ra định kỳ hoặc đưa lên số liệu (bài {{n:quan-sat}}). Số này tăng mãi không giảm khi tải ổn định = rò rỉ.
  2. Xem chúng đang kẹt ở đâu: bật net/http/pprof, mở /debug/pprof/goroutine?debug=1. Bạn sẽ thấy kiểu "1.204 goroutine đang ở main.parse dòng 54, chan send". Đó là chỗ thiếu ctx.Done().
  3. Trong test: thư viện go.uber.org/goleak báo lỗi nếu test kết thúc mà còn goroutine chạy.
package main

Tải nhiều trang web song song, có giới hạn và timeout

Viết chương trình nhận một danh sách URL, tải song song tối đa 3 URL cùng lúc, mỗi URL có timeout 2 giây, cả chương trình có timeout 5 giây. In ra mã trạng thái và thời gian của từng URL, theo đúng thứ tự của danh sách. Một URL lỗi không được làm dừng các URL khác.

Gợi ý từng bước

  1. Kết quả theo thứ tự: tạo slice results := make([]string, len(urls)), goroutine thứ i ghi vào results[i].
  2. Không dừng khi lỗi: dùng errgroup.Group (không WithContext), SetLimit(3), mỗi việc trả nil và ghi lỗi vào ô của mình.
  3. Timeout tổng: ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second).
  4. Timeout từng URL: trong mỗi việc, reqCtx, cancel := context.WithTimeout(ctx, 2*time.Second), rồi http.NewRequestWithContext(reqCtx, "GET", u, nil).
  5. Nhớ resp.Body.Close(), và đọc hết body bằng io.Copy(io.Discard, resp.Body) để kết nối được dùng lại.

package main

import (
    "context"
    "fmt"
    "io"
    "net/http"
    "os"
    "time"

    "golang.org/x/sync/errgroup"
)

func fetch(ctx context.Context, url string) string {
    reqCtx, cancel := context.WithTimeout(ctx, 2*time.Second)
    defer cancel()

    start := time.Now()
    req, err := http.NewRequestWithContext(reqCtx, http.MethodGet, url, nil)
    if err != nil {
        return "lỗi URL: " + err.Error()
    }
    resp, err := http.DefaultClient.Do(req)
    if err != nil {
        return fmt.Sprintf("lỗi sau %v: %v", time.Since(start).Round(time.Millisecond), err)
    }
    defer resp.Body.Close()
    n, _ := io.Copy(io.Discard, resp.Body)
    return fmt.Sprintf("%d, %d byte, %v", resp.StatusCode, n, time.Since(start).Round(time.Millisecond))
}

func main() {
    urls := os.Args[1:]
    ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
    defer cancel()

    results := make([]string, len(urls))
    var g errgroup.Group
    g.SetLimit(3)
    for i, u := range urls {
        g.Go(func() error {
            results[i] = fetch(ctx, u)
            return nil // không để một URL lỗi làm dừng cả nhóm
        })
    }
    g.Wait()

    for i, u := range urls {
        fmt.Printf("%-28s %s\n", u, results[i])
    }
}

Pipeline đếm từ, có fan-out

Cho một slice các câu. Giai đoạn 1 gửi từng câu. Giai đoạn 2 (chạy 4 bản song song) tách câu thành từ, đổi về chữ thường, gửi từng từ. Giai đoạn cuối đếm số lần xuất hiện mỗi từ và in 3 từ nhiều nhất.

Gợi ý từng bước

  1. Dùng lại gen và merge ở trên.
  2. Giai đoạn tách: strings.Fields(strings.ToLower(câu)) cho các từ.
  3. Giai đoạn đếm chạy ở main (chỉ một goroutine) nên dùng map thường, không cần mutex.
  4. Sắp xếp: chuyển map thành slice cặp (từ, số lần) rồi slices.SortFunc, số lần giảm dần, bằng nhau thì theo chữ cái để kết quả cố định.

package main

import (
    "cmp"
    "context"
    "fmt"
    "slices"
    "strings"
    "sync"
)

func gen(ctx context.Context, items ...string) <-chan string {
    out := make(chan string)
    go func() {
        defer close(out)
        for _, it := range items {
            select {
            case out <- it:
            case <-ctx.Done():
                return
            }
        }
    }()
    return out
}

func words(ctx context.Context, in <-chan string) <-chan string {
    out := make(chan string)
    go func() {
        defer close(out)
        for s := range in {
            for _, w := range strings.Fields(strings.ToLower(s)) {
                select {
                case out <- w:
                case <-ctx.Done():
                    return
                }
            }
        }
    }()
    return out
}

func merge[T any](ctx context.Context, ins ...<-chan T) <-chan T {
    out := make(chan T)
    var wg sync.WaitGroup
    wg.Add(len(ins))
    for _, in := range ins {
        go func() {
            defer wg.Done()
            for v := range in {
                select {
                case out <- v:
                case <-ctx.Done():
                    return
                }
            }
        }()
    }
    go func() { wg.Wait(); close(out) }()
    return out
}

func main() {
    ctx, cancel := context.WithCancel(context.Background())
    defer cancel()

    src := gen(ctx,
        "Go chạy nhanh",
        "Go dễ học",
        "Học Go để viết backend",
        "backend Go chạy ổn định",
    )
    // fan-out: 4 bản words cùng đọc src
    var outs []<-chan string
    for range 4 {
        outs = append(outs, words(ctx, src))
    }

    count := map[string]int{}
    for w := range merge(ctx, outs...) { // fan-in
        count[w]++
    }

    type kv struct {
        w string
        n int
    }
    var list []kv
    for w, n := range count {
        list = append(list, kv{w, n})
    }
    slices.SortFunc(list, func(a, b kv) int {
        return cmp.Or(cmp.Compare(b.n, a.n), cmp.Compare(a.w, b.w))
    })
    for _, x := range list[:3] {
        fmt.Printf("%-8s %d\n", x.w, x.n)
    }
}

Tìm và sửa chỗ rò rỉ goroutine

Hàm dưới đây hỏi 3 máy chủ cùng lúc và lấy câu trả lời nhanh nhất. Nó có lỗi rò rỉ goroutine. Tìm và sửa.

func fastest(ctx context.Context, servers []string) string {
    ch := make(chan string)
    for _, s := range servers {
        go func() { ch <- query(ctx, s) }()
    }
    return <-ch
}

Gợi ý từng bước

  1. return <-ch chỉ đọc một lần. Hai goroutine còn lại gửi vào ch thì sao?
  2. Có hai cách sửa: cho channel đủ chỗ chứa, hoặc huỷ các truy vấn còn lại.
  3. Làm cả hai là tốt nhất: đủ chỗ để không ai kẹt, và huỷ context để các truy vấn chậm dừng sớm, không tốn tài nguyên.
Xem lời giải

Channel không có bộ đệm, chỉ một lần đọc, nên 2 goroutine chậm hơn kẹt mãi ở ch <-. Mỗi lần gọi fastest rò 2 goroutine.

func fastest(ctx context.Context, servers []string) string {
    ctx, cancel := context.WithCancel(ctx)
    defer cancel() // có kết quả rồi → huỷ các truy vấn còn lại

    ch := make(chan string, len(servers)) // đủ chỗ: không goroutine nào phải chờ người đọc
    for _, s := range servers {
        go func() { ch <- query(ctx, s) }()
    }
    return <-ch
}

Bộ đệm bằng số server bảo đảm mọi goroutine gửi được và thoát. cancel() khi hàm trả về giúp các truy vấn chưa xong dừng sớm (nếu query truyền ctx xuống HTTP / database). Kết quả của chúng nằm trong channel rồi bị bộ dọn rác thu hồi cùng channel.
