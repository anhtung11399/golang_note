Vì sao vẫn là SQL

Có rất nhiều loại database (MongoDB, DynamoDB, Cassandra...), nhưng với đa số ứng dụng nghiệp vụ, cơ sở dữ liệu quan hệ (PostgreSQL, MySQL) vẫn là lựa chọn mặc định: dữ liệu có cấu trúc rõ, có quan hệ với nhau, cần giao dịch đúng tuyệt đối. Lộ trình này dùng PostgreSQL, database mã nguồn mở được dùng rộng rãi nhất cho backend hiện nay.

Cài Postgres để chạy thử

Mọi câu SQL trong bài này đều chạy được, và kết quả in ngay bên dưới để bạn so. Chọn một trong hai cách:

Cách 1: Docker (cần cài Docker Desktop và mở nó lên trước):

docker run -d --name pg -e POSTGRES_PASSWORD=dev -p 5432:5432 postgres:17   # tải và chạy Postgres ở nền
docker exec -it pg psql -U postgres                                         # mở cửa sổ gõ SQL

Cách 2: Homebrew trên macOS, không cần Docker:

brew install postgresql@17
brew services start postgresql@17   # chạy Postgres ở nền, tự bật lại khi mở máy
psql postgres                       # mở cửa sổ gõ SQL

Khi thấy dấu nhắc postgres=# là bạn đang ở trong psql, công cụ gõ SQL của Postgres. Dán câu SQL vào, kết thúc bằng dấu ; rồi Enter. Gõ \q để thoát, \dt để xem danh sách bảng, \d users để xem cấu trúc bảng users.

Thích giao diện bấm chuột hơn: cài TablePlus, DBeaver hoặc pgAdmin, kết nối tới localhost:5432, người dùng postgres, mật khẩu dev (cách 1) hoặc để trống (cách 2).

Hãy nghĩ một bảng như một mảng object cùng kiểu, mỗi dòng là một object, mỗi cột là một thuộc tính có kiểu cố định. Khác với state ở frontend: dữ liệu này dùng chung cho mọi người, sống nhiều năm, và database sẽ từ chối dữ liệu sai ràng buộc thay vì để bạn tự kiểm tra.

Thiết kế bảng cho "Sổ bài tập"

Nghiệp vụ: giáo viên có nhiều lớp. Lớp có nhiều học sinh, một học sinh có thể học nhiều lớp (học thêm). Lớp có nhiều bài tập. Mỗi học sinh nộp mỗi bài tập một lần, có điểm.

Năm bảng dưới đây được dùng xuyên suốt bài {{n:sql}}, {{n:go-postgres}}, {{n:toi-uu-query}}. Đọc sơ đồ trước: mũi tên đi từ bảng "một" tới bảng "nhiều" (một giáo viên có nhiều lớp).

CREATE TABLE users (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email       text NOT NULL UNIQUE,
    name        text NOT NULL CHECK (char_length(name) BETWEEN 1 AND 80),
    role        text NOT NULL CHECK (role IN ('teacher', 'student')),
    created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE classes (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    teacher_id  bigint NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    name        text NOT NULL CHECK (char_length(name) BETWEEN 1 AND 60),
    capacity    int NOT NULL CHECK (capacity BETWEEN 1 AND 80),
    created_at  timestamptz NOT NULL DEFAULT now()
);

-- Bảng nối cho quan hệ nhiều - nhiều
CREATE TABLE enrollments (
    class_id    bigint NOT NULL REFERENCES classes(id) ON DELETE CASCADE,
    student_id  bigint NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    joined_at   timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (class_id, student_id)        -- một học sinh vào một lớp đúng một lần
);

CREATE TABLE assignments (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    class_id    bigint NOT NULL REFERENCES classes(id) ON DELETE CASCADE,
    title       text NOT NULL,
    due_date    date NOT NULL,
    created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE submissions (
    assignment_id bigint NOT NULL REFERENCES assignments(id) ON DELETE CASCADE,
    student_id    bigint NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    score         numeric(4,2) CHECK (score BETWEEN 0 AND 10),  -- NULL = chưa chấm
    submitted_at  timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (assignment_id, student_id)
);

Đọc lược đồ:

  • bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY: cột id là số nguyên 64 bit, database tự đánh số 1, 2, 3... khi thêm dòng. Giống AUTO_INCREMENT của MySQL.
  • text NOT NULL UNIQUE: chuỗi, không được để trống, không được trùng với dòng khác.
  • REFERENCES users(id): khoá ngoại. Giá trị cột này phải là một id có thật trong bảng users.
  • timestamptz NOT NULL DEFAULT now(): thời điểm, không gửi thì lấy giờ hiện tại.
  • numeric(4,2): số thập phân chính xác, tối đa 4 chữ số, 2 chữ số sau dấu chấm (từ 0.00 đến 99.99). Không dùng số thực cho điểm, cùng lý do như tiền ở bài {{n:bien-kieu}}.

Dán toàn bộ khối trên vào psql. Mỗi bảng tạo xong, psql in CREATE TABLE.

Dữ liệu mẫu

Dán tiếp khối này để có dữ liệu cho mọi ví dụ trong bài. Id được ghi cố định (OVERRIDING SYSTEM VALUE cho phép tự chọn id thay vì để database đánh số) để kết quả trên máy bạn giống hệt trong bài:

INSERT INTO users (id, email, name, role) OVERRIDING SYSTEM VALUE VALUES
  (7,   'hoa@truong.vn',  'Cô Hoa',  'teacher'),
  (8,   'nam@truong.vn',  'Thầy Nam', 'teacher'),
  (101, 'an@hs.vn',       'An',      'student'),
  (102, 'binh@hs.vn',     'Bình',    'student'),
  (103, 'chi@hs.vn',      'Chi',     'student'),
  (104, 'dung@hs.vn',     'Dũng',    'student');

INSERT INTO classes (id, teacher_id, name, capacity) OVERRIDING SYSTEM VALUE VALUES
  (42, 7, 'Lớp 5A', 35),
  (43, 7, 'Tiếng Anh tối thứ 3', 20),
  (50, 8, 'Lớp 6B', 40);

INSERT INTO enrollments (class_id, student_id) VALUES
  (42, 101), (42, 102), (42, 103), (42, 104),
  (43, 101), (43, 103);

INSERT INTO assignments (id, class_id, title, due_date) OVERRIDING SYSTEM VALUE VALUES
  (9,  42, 'Toán trang 12', '2026-11-03'),
  (10, 42, 'Văn: tả cây',   '2026-11-05'),
  (11, 43, 'Unit 3',        '2026-11-04');

INSERT INTO submissions (assignment_id, student_id, score, submitted_at) VALUES
  (9,  101, 9.00, '2026-11-02 19:05+07'),
  (9,  103, 7.50, '2026-11-02 20:41+07'),
  (9,  104, 4.00, '2026-11-03 06:30+07'),
  (10, 101, 8.00, '2026-11-04 18:00+07'),
  (10, 104, 3.50, '2026-11-04 21:10+07'),
  (10, 103, NULL, '2026-11-04 21:30+07');

Tóm tắt dữ liệu: Cô Hoa (id 7) dạy hai lớp 42 (Lớp 5A, 4 học sinh An, Bình, Chi, Dũng) và 43. Lớp 42 có bài tập 9 và 10. Bình chưa nộp bài nào, Chi nộp bài {{n:context-test}} nhưng chưa được chấm (score là NULL).

Thử phá ràng buộc để thấy database từ chối:

INSERT INTO users (email, name, role) VALUES ('an@hs.vn', 'An khác', 'student');

ERROR:  duplicate key value violates unique constraint "users_email_key"
DETAIL:  Key (email)=(an@hs.vn) already exists.

INSERT INTO submissions (assignment_id, student_id, score) VALUES (9, 102, 11);

ERROR:  new row for relation "submissions" violates check constraint "submissions_score_check"
DETAIL:  Failing row contains (9, 102, 11.00, 2026-11-03 15:43:45.781+07).

INSERT INTO classes (teacher_id, name, capacity) VALUES (999, 'Lớp ma', 10);

ERROR:  insert or update on table "classes" violates foreign key constraint "classes_teacher_id_fkey"
DETAIL:  Key (teacher_id)=(999) is not present in table "users".

Ba lỗi lần lượt là: email đã có người dùng (UNIQUE), điểm 11 ngoài khoảng 0 đến 10 (CHECK), giáo viên 999 không tồn tại (khoá ngoại). Ở bài {{n:go-postgres}} bạn sẽ bắt các lỗi này trong Go và đổi thành response 409 / 400.

Kiểm tra ở Go là tốt, nhưng ràng buộc trong database là lớp phòng thủ cuối cùng: nó vẫn đúng khi có bug trong code, khi hai request chạy song song, khi ai đó sửa dữ liệu bằng tay hay viết script nhập liệu. Code bạn viết hôm nay sẽ được người khác sửa trong 3 năm tới, còn ràng buộc thì vẫn ở đó.

CRUD cơ bản

CRUD = Create, Read, Update, Delete: bốn việc cơ bản với dữ liệu. Trong SQL là INSERT, SELECT, UPDATE, DELETE.

Đọc: lấy các lớp của giáo viên 7. Đọc câu SQL như tiếng Anh: "chọn cột id, name, capacity từ bảng classes, ở những dòng có teacher_id bằng 7, sắp theo id".

SELECT id, name, capacity FROM classes WHERE teacher_id = 7 ORDER BY id;

 id |        name         | capacity
----+---------------------+----------
 42 | Lớp 5A              |       35
 43 | Tiếng Anh tối thứ 3 |       20
(2 rows)

Tạo, và lấy lại dữ liệu vừa tạo bằng RETURNING (không cần chạy thêm câu SELECT):

INSERT INTO classes (teacher_id, name, capacity) VALUES (7, 'Lớp 5B', 35)
RETURNING id, name;

 id |  name
----+--------
  1 | Lớp 5B
(1 row)

INSERT 0 1

Lớp mới có id 1 vì dữ liệu mẫu tự chọn id 42, 43, 50, còn bộ đếm tự tăng của database vẫn bắt đầu từ 1.

Sửa và xoá. Luôn có WHERE:

UPDATE classes SET name = 'Lớp 5A1' WHERE id = 42 AND teacher_id = 7;

UPDATE 1

UPDATE classes SET name = 'Lớp của tôi' WHERE id = 50 AND teacher_id = 7;

UPDATE 0

UPDATE 1 nghĩa là một dòng bị sửa. UPDATE 0: không dòng nào, vì lớp 50 là của Thầy Nam (id 8), không phải của giáo viên 7. Câu SQL không báo lỗi, chỉ là không sửa gì. Trong Go, bạn đọc con số này để trả 404 (bài {{n:go-postgres}}).

DELETE FROM classes WHERE id = 1 AND teacher_id = 7;   -- xoá lớp 5B vừa tạo

UPDATE classes SET name = 'x' quên WHERE là sửa mọi dòng của bảng. Khi sửa dữ liệu bằng tay trên production: mở transaction (BEGIN), chạy, xem số dòng bị ảnh hưởng, đúng rồi mới COMMIT.

Để ý điều kiện AND teacher_id = 7: không chỉ sửa lớp 42, mà sửa lớp 42 nếu nó thuộc giáo viên 7. Gộp kiểm quyền vào câu SQL là thói quen tốt nhất bạn có thể tập từ bây giờ.

JOIN: ghép dữ liệu từ nhiều bảng

Bảng assignments chỉ có class_id, không có tên lớp. Muốn hiện tên lớp cạnh bài tập thì phải ghép hai bảng: với mỗi bài tập, tìm dòng lớp có id bằng class_id của nó. Giống assignments.map(a => ({ ...a, class: classes.find(c => c.id === a.classId) })), nhưng database làm nhanh hơn nhiều nhờ index.

SELECT a.id, a.title, a.due_date, c.name AS class_name
FROM assignments a                    -- "a" là tên gọi tắt của bảng
JOIN classes c ON c.id = a.class_id   -- ghép: dòng nào của classes khớp với bài tập này
WHERE c.teacher_id = 7;

 id |     title     |  due_date  |     class_name
----+---------------+------------+---------------------
  9 | Toán trang 12 | 2026-11-03 | Lớp 5A
 10 | Văn: tả cây   | 2026-11-05 | Lớp 5A
 11 | Unit 3        | 2026-11-04 | Tiếng Anh tối thứ 3
(3 rows)

AS class_name đặt tên cho cột kết quả. JOIN (đầy đủ là INNER JOIN) chỉ giữ những dòng khớp được ở cả hai bên.

Bài toán khó hơn: mọi học sinh của lớp 42 kèm điểm bài {{n:dong-thoi}}, kể cả em chưa nộp. Dùng LEFT JOIN: giữ mọi dòng của bảng bên trái, bên phải không có thì điền NULL.

SELECT u.id, u.name, s.score, s.submitted_at
FROM enrollments e                                    -- bắt đầu từ danh sách học sinh của lớp
JOIN users u ON u.id = e.student_id                   -- lấy tên học sinh
LEFT JOIN submissions s ON s.student_id = e.student_id AND s.assignment_id = 9  -- bài nộp, nếu có
WHERE e.class_id = 42
ORDER BY u.name;

 id  | name | score |      submitted_at
-----+------+-------+------------------------
 101 | An   |  9.00 | 2026-11-02 19:05:00+07
 102 | Bình |       |
 103 | Chi  |  7.50 | 2026-11-02 20:41:00+07
 104 | Dũng |  4.00 | 2026-11-03 06:30:00+07
(4 rows)

Bình chưa nộp: LEFT JOIN vẫn giữ dòng của Bình với các cột của submissions để trống (NULL, psql in ra ô trống). Nếu dùng JOIN thường, Bình biến mất khỏi danh sách, và giáo viên không biết ai chưa nộp. Thời gian hiện theo giờ Việt Nam (+07) vì phiên psql đang đặt múi giờ đó (xem mục "Thời gian trong database").

Để ý: điều kiện s.assignment_id = 9 nằm trong ON, không phải trong WHERE. Đặt vào WHERE thì dòng NULL của Bình bị lọc mất, LEFT JOIN thành JOIN thường. Đây là lỗi SQL kinh điển. Thử đặt sai chỗ:

SELECT u.id, u.name, s.score
FROM enrollments e
JOIN users u ON u.id = e.student_id
LEFT JOIN submissions s ON s.student_id = e.student_id
WHERE e.class_id = 42 AND s.assignment_id = 9   -- SAI: điều kiện của bảng bên phải nằm ở WHERE
ORDER BY u.name;

 id  | name | score
-----+------+-------
 101 | An   |  9.00
 103 | Chi  |  7.50
 104 | Dũng |  4.00
(3 rows)

Bình đã biến mất. Câu SQL vẫn chạy, không báo lỗi gì, nên lỗi này rất khó phát hiện.

Gom nhóm: GROUP BY

GROUP BY gom các dòng có cùng giá trị thành một nhóm, rồi các hàm count, avg, sum, max tính trên từng nhóm. Giống lodash.groupBy rồi tính trên mỗi nhóm.

-- Mỗi lớp của giáo viên 7: số học sinh, số bài tập
SELECT c.id, c.name,
       count(DISTINCT e.student_id) AS students,     -- DISTINCT: đếm mỗi học sinh một lần
       count(DISTINCT a.id)         AS assignments
FROM classes c
LEFT JOIN enrollments e ON e.class_id = c.id
LEFT JOIN assignments a ON a.class_id = c.id
WHERE c.teacher_id = 7
GROUP BY c.id, c.name;                               -- mỗi lớp một dòng kết quả

 id |        name         | students | assignments
----+---------------------+----------+-------------
 42 | Lớp 5A              |        4 |           2
 43 | Tiếng Anh tối thứ 3 |        2 |           1
(2 rows)

Vì sao cần DISTINCT? Ghép một lớp với 4 học sinh và 2 bài tập tạo ra 4 × 2 = 8 dòng trung gian. Đếm không có DISTINCT sẽ ra 8 học sinh, 8 bài tập.

-- Điểm trung bình theo học sinh trong lớp 42, chỉ lấy em dưới 5
SELECT s.student_id, round(avg(s.score), 2) AS avg_score, count(s.score) AS graded
FROM submissions s
JOIN assignments a ON a.id = s.assignment_id
WHERE a.class_id = 42 AND s.score IS NOT NULL   -- WHERE lọc dòng TRƯỚC khi gom
GROUP BY s.student_id
HAVING avg(s.score) < 5;                        -- HAVING lọc nhóm SAU khi gom

 student_id | avg_score | graded
------------+-----------+--------
        104 |      3.75 |      2
(1 row)

Dũng (104) được 4 và 3.5, trung bình 3.75. An và Chi trung bình trên 5 nên bị HAVING loại.

NULL: không phải 0, không phải chuỗi rỗng

  • NULL nghĩa là "không biết / không có". score = NULL luôn ra "không biết", không bao giờ đúng. Phải viết score IS NULL.
  • avg, sum, count(cột) bỏ qua NULL. count(*) đếm mọi dòng. Bài 10 có 3 bài nộp, một bài chưa chấm: 
    SELECT count(*) AS dong, count(score) AS da_cham, round(avg(score), 2) AS trung_binh
FROM submissions WHERE assignment_id = 10;

     dong | da_cham | trung_binh
------+---------+------------
    3 |       2 |       5.75
(1 row)
    Trung bình là (8 + 3.5) / 2 = 5.75, bài chưa chấm của Chi không bị tính là 0.
  • Trong Go, đọc cột có thể NULL vào kiểu con trỏ (*float64) hoặc kiểu riêng của driver (pgtype.Numeric). Đọc NULL vào float64 thường sẽ báo lỗi.

Chuẩn hoá: mỗi thông tin nằm một chỗ

submissions: student_id | student_name | student_email | class_name | score

Học sinh đổi tên: phải sửa hàng trăm dòng, sót một dòng là dữ liệu mâu thuẫn. Chuẩn hoá nghĩa là tách thông tin về đúng bảng của nó (tên học sinh ở users), các bảng khác chỉ giữ khoá ngoại.

Ngoài thực tế đôi khi người ta cố tình chép dữ liệu (phi chuẩn hoá) để đọc nhanh, ví dụ lưu sẵn submission_count trong assignments thay vì đếm mỗi lần. Đổi lại phải giữ nó đồng bộ. Hãy bắt đầu bằng thiết kế chuẩn hoá, chỉ phi chuẩn hoá khi đo được là chậm.

Một ví dụ phi chuẩn hoá có chủ đích: đơn hàng lưu lại giá tại thời điểm mua (order_items.unit_price), dù bảng sản phẩm đã có giá. Vì giá sản phẩm sẽ đổi, nhưng hoá đơn đã thanh toán thì không được đổi theo. Ghi nhận lịch sử khác với chép trùng.

Thời gian trong database

  • Thời điểm (lúc tạo, lúc nộp): timestamptz. Postgres lưu dạng UTC và đổi theo múi giờ của phiên kết nối khi hiển thị.
  • Ngày theo lịch (hạn nộp, ngày điểm danh): date. Nhớ quy đổi "hôm nay" theo giờ Việt Nam (Asia/Ho_Chi_Minh) chứ không theo UTC: từ 0 giờ tới 7 giờ sáng ở Việt Nam, ngày UTC vẫn là hôm qua.
  • Muốn psql hiện giờ Việt Nam như các kết quả trong bài: SET TIME ZONE 'Asia/Ho_Chi_Minh'; (chỉ đổi cách hiển thị, dữ liệu lưu vẫn là một thời điểm duy nhất).

Bài tập

Viết các truy vấn báo cáo

Với 5 bảng ở trên, viết SQL cho:

  1. Danh sách học sinh lớp 42 chưa nộp bài tập 9. (Với dữ liệu mẫu: chỉ có Bình.)
  2. Với mỗi bài tập của lớp 42: tiêu đề, số em đã nộp, sĩ số lớp. (Bài 9: 3/4, bài 10: 3/4.)
  3. Năm học sinh có điểm trung bình cao nhất lớp 42 (chỉ tính bài đã chấm). (An đứng đầu với 8.50.)

Gợi ý

  1. Câu 1: bắt đầu từ câu LEFT JOIN "mọi học sinh kèm điểm bài {{n:dong-thoi}}" ở trên. Em chưa nộp là em có cột của submissions bị NULL. Thêm điều kiện s.student_id IS NULL.
  2. Câu 2: mỗi bài tập một dòng. Có thể đếm bằng truy vấn con: viết một câu SELECT count(*) nhỏ trong ngoặc ngay ở danh sách cột.
  3. Câu 3: giống ví dụ HAVING, bỏ HAVING, thêm ORDER BY avg_score DESC LIMIT 5, và JOIN thêm users để có tên.
Xem lời giải 
-- 1. Chưa nộp: LEFT JOIN rồi lấy dòng không khớp
SELECT u.id, u.name
FROM enrollments e
JOIN users u ON u.id = e.student_id
LEFT JOIN submissions s ON s.student_id = e.student_id AND s.assignment_id = 9
WHERE e.class_id = 42 AND s.student_id IS NULL;

-- Cách khác, thường dễ đọc hơn: NOT EXISTS
SELECT u.id, u.name
FROM enrollments e
JOIN users u ON u.id = e.student_id
WHERE e.class_id = 42
  AND NOT EXISTS (SELECT 1 FROM submissions s WHERE s.assignment_id = 9 AND s.student_id = e.student_id);

-- 2. Số bài nộp mỗi bài tập + sĩ số
SELECT a.id, a.title,
       (SELECT count(*) FROM submissions s WHERE s.assignment_id = a.id) AS submitted,
       (SELECT count(*) FROM enrollments e WHERE e.class_id = a.class_id) AS total
FROM assignments a
WHERE a.class_id = 42
ORDER BY a.due_date DESC;

-- 3. Top 5 điểm trung bình
SELECT u.id, u.name, round(avg(s.score), 2) AS avg_score
FROM submissions s
JOIN assignments a ON a.id = s.assignment_id
JOIN users u ON u.id = s.student_id
WHERE a.class_id = 42 AND s.score IS NOT NULL
GROUP BY u.id, u.name
ORDER BY avg_score DESC
LIMIT 5;

Thêm tính năng vào lược đồ

Thêm: giáo viên đính kèm nhiều file vào bài tập (tên file, kích thước, đường dẫn lưu trữ), và mỗi lớp có nhiều môn học, bài tập thuộc một môn. Viết CREATE TABLE / ALTER TABLE với đủ ràng buộc.

Gợi ý

  1. "Một lớp có nhiều môn" = bảng mới subjects có cột class_id trỏ về classes.
  2. "Bài tập thuộc một môn" = bảng assignments thêm cột subject_id: ALTER TABLE assignments ADD COLUMN ....
  3. "Một bài tập có nhiều file" = bảng mới assignment_files có assignment_id.
  4. Với mỗi cột, tự hỏi: được để trống không (NOT NULL)? được trùng không (UNIQUE)? giới hạn giá trị (CHECK)? xoá cha thì con ra sao (ON DELETE)?
Xem lời giải 
CREATE TABLE subjects (
    id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    class_id  bigint NOT NULL REFERENCES classes(id) ON DELETE CASCADE,
    name      text NOT NULL CHECK (char_length(name) BETWEEN 1 AND 40),
    UNIQUE (class_id, name)                 -- một lớp không có hai môn trùng tên
);

ALTER TABLE assignments ADD COLUMN subject_id bigint REFERENCES subjects(id) ON DELETE RESTRICT;

CREATE TABLE assignment_files (
    id             bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    assignment_id  bigint NOT NULL REFERENCES assignments(id) ON DELETE CASCADE,
    file_name      text NOT NULL,
    size_bytes     bigint NOT NULL CHECK (size_bytes BETWEEN 1 AND 26214400), -- tối đa 25 MB
    storage_key    text NOT NULL UNIQUE
);

Thử kiểm tra: tạo môn, gán bài tập 9 vào môn Toán, rồi xoá môn Toán:

INSERT INTO subjects (class_id, name) VALUES (42, 'Toán'), (42, 'Tiếng Việt');
UPDATE assignments SET subject_id = 1 WHERE id = 9;
DELETE FROM subjects WHERE id = 1;

ON DELETE RESTRICT ở subject_id: không cho xoá môn khi còn bài tập thuộc môn đó, buộc giáo viên xử lý bài tập trước. Chọn CASCADE hay RESTRICT là quyết định nghiệp vụ, hãy hỏi người làm sản phẩm. Thêm cột vào bảng đã có dữ liệu thì cột mới phải cho phép NULL hoặc có DEFAULT.
