Tài nguyên và đường dẫn

REST xoay quanh tài nguyên (danh từ) và dùng method HTTP làm động từ. Đường dẫn nói "cái gì", method nói "làm gì".

ViệcEndpointThành công
Danh sách lớp của tôiGET /v1/classes200 + danh sách
Tạo lớpPOST /v1/classes201 + lớp mới + header Location
Xem một lớpGET /v1/classes/{id}200
Sửa vài trườngPATCH /v1/classes/{id}200 + lớp sau khi sửa
Thay toàn bộPUT /v1/classes/{id}200
XoáDELETE /v1/classes/{id}204, không có body
Bài tập của một lớpGET /v1/classes/{id}/assignments200
Hành động không phải CRUDPOST /v1/assignments/{id}/submit200 / 201
  • Danh từ số nhiều, chữ thường, gạch ngang: /payment-issues, không phải /getPaymentIssue.
  • Lồng tối đa một, hai tầng. /classes/5/assignments được, /schools/1/classes/5/assignments/9/files/3 thì quá sâu: dùng /files/3.
  • Hành động không khớp CRUD (duyệt, nộp, huỷ, gửi lại) dùng POST với động từ ở cuối: POST /orders/9/cancel. Đây là cách các API lớn như Stripe vẫn làm.

Method: an toàn và idempotent

MethodAn toàn (không đổi dữ liệu)Idempotent (gọi nhiều lần = gọi một lần)Ghi chú
GET, HEADCóCóKhông bao giờ được đổi dữ liệu. Trình duyệt, CDN, crawler có thể tự gọi lại bất cứ lúc nào
PUTKhôngCóGửi lại bản đầy đủ, kết quả vẫn thế
DELETEKhôngCóXoá lần hai: dữ liệu vẫn là "đã xoá" (status có thể là 404)
PATCHKhôngTuỳ{"name":"5A"} idempotent, {"op":"increment"} thì không
POSTKhôngKhôngGửi hai lần = tạo hai bản ghi, trừ khi có idempotency key

Đừng bao giờ làm endpoint kiểu GET /delete?id=5. Thư viện prefetch link, trình kiểm tra link trong Slack/Zalo, hay bot tìm kiếm có thể tự gọi GET và xoá dữ liệu của bạn.

Hãy nghĩ tới code frontend sẽ viết: 401 thì chuyển về trang đăng nhập, 403 hiện "không có quyền", 409 hiện thông báo cụ thể, 429 chờ rồi thử lại, 5xx hiện "thử lại sau". Status đúng giúp frontend xử lý chung ở một chỗ (interceptor) thay vì đọc nội dung từng lỗi.

Một định dạng lỗi cho toàn bộ API

{
  "error": {
    "code": "CLASS_FULL",
    "message": "Lớp đã đủ sĩ số",
    "fields": { "joinCode": "Lớp đã đủ 40 học sinh" }
  }
}
  • code: hằng số ổn định cho máy đọc. Frontend switch theo nó. Không bao giờ đổi.
  • message: câu cho người đọc, có thể hiện thẳng lên giao diện.
  • fields: lỗi theo từng ô nhập, để form tô đỏ đúng ô.

Có một chuẩn chính thức cho việc này là Problem Details for HTTP APIs (RFC 9457, Content-Type: application/problem+json). Dùng chuẩn hay tự định nghĩa đều được, quan trọng nhất là mọi endpoint trả cùng một dạng.

Validate: không tin dữ liệu nào

type CreateAssignmentReq struct {
    Title    string `json:"title"`
    DueDate  string `json:"dueDate"`  // "2026-11-10"
    Count    int    `json:"count"`
}

func (r *CreateAssignmentReq) Validate() error {
    r.Title = strings.TrimSpace(r.Title)
    fields := map[string]string{}
    if n := utf8.RuneCountInString(r.Title); n == 0 || n > 200 {
        fields["title"] = "Nội dung từ 1 đến 200 ký tự"
    }
    if _, err := time.Parse(time.DateOnly, r.DueDate); err != nil {
        fields["dueDate"] = "Ngày không hợp lệ (YYYY-MM-DD)"
    }
    if r.Count < 1 || r.Count > 50 {
        fields["count"] = "Số bài từ 1 đến 50"
    }
    if len(fields) > 0 {
        return &FieldsError{Fields: fields}
    }
    return nil
}

Mọi giới hạn validate ở backend phải khớp với maxlength, min, max ở form frontend. Frontend validate để trải nghiệm tốt, backend validate để dữ liệu đúng. Thư viện go-playground/validator cho phép viết luật bằng tag (validate:"required,max=200"), rất phổ biến khi struct nhiều trường.

Phân trang, lọc, sắp xếp

Không bao giờ trả toàn bộ một bảng. Bảng có 10 dòng lúc ra mắt sẽ có 10 triệu dòng sau hai năm.

Phân trang theo số trang (offset)

GET /v1/classes/5/assignments?page=2&size=20&sort=-dueDate&subject=toan

{ "items": [ ... ], "page": 2, "size": 20, "total": 137 }

Dễ làm, có số trang để nhảy. Nhược điểm: OFFSET 100000 chậm (database vẫn phải đi qua 100.000 dòng), và nếu có dòng mới chen vào lúc người dùng đang lật trang thì bị trùng hoặc sót.

Phân trang theo con trỏ (cursor)

GET /v1/notifications?limit=20&after=eyJpZCI6OTAwMX0

{ "items": [ ... ], "nextCursor": "eyJpZCI6ODk4MX0", "hasMore": true }

Nhanh với mọi độ sâu và không trùng / sót, hợp với cuộn vô hạn và feed. Không nhảy thẳng tới trang 50 được. Cách cài đặt bằng SQL ở bài 16.

Stripe dùng cursor: tham số starting_after và trường has_more. GitHub API trả link trang sau trong header Link. Twitter / X, Facebook Graph API đều dùng cursor cho feed.

Luôn đặt giới hạn trên cho size (ví dụ tối đa 100), và chỉ cho sắp xếp / lọc theo danh sách cột cho phép. Tuyệt đối không ghép thẳng tham số sort vào câu SQL (bài 19: SQL injection).

var sortable = map[string]string{
    "dueDate":   "due_date",
    "createdAt": "created_at",
}
col, ok := sortable[strings.TrimPrefix(sortParam, "-")]
if !ok {
    col = "created_at"
}

Ngày giờ, id, tiền trong JSON

  • Thời điểm: chuỗi ISO 8601 / RFC 3339 có múi giờ, nên dùng UTC: "2026-11-03T08:30:00Z". Go mặc định đổi time.Time sang dạng này.
  • Ngày không có giờ (hạn nộp, ngày sinh): "2026-11-10". Đừng biến nó thành thời điểm nửa đêm UTC, sẽ lệch ngày ở múi giờ Việt Nam (UTC+7).
  • Id 64 bit: cân nhắc trả dạng chuỗi (JavaScript chỉ chính xác tới 253, bài 02).
  • Tiền: số nguyên theo đơn vị nhỏ nhất kèm mã tiền tệ: {"amount": 49000, "currency": "VND"}.

Idempotency key: bấm hai lần không trả tiền hai lần

Người dùng bấm "Thanh toán", mạng chập chờn, app tự gửi lại. POST không idempotent nên có thể tạo hai giao dịch. Giải pháp là client tạo một khoá ngẫu nhiên cho mỗi thao tác và gửi kèm:

POST /v1/payments
Idempotency-Key: 8b1f3c3e-6a2c-4c1e-9a77-2f1b1c0d9e11
actors: [fe] App, [go] API, [db] Database App -> API: POST /payments (key K) API -> Database: chưa có K → xử lý, lưu kết quả kèm K API --> App: 201 {id: 77} (mạng rớt, app không nhận được) App -> API: gửi lại POST /payments (key K) API -> Database: đã có K Database --> API: kết quả cũ {id: 77} API --> App: 201 {id: 77}, không tạo giao dịch thứ hai

Đây đúng là cách Stripe làm với header Idempotency-Key, và là một trong những thiết kế API được nhắc tới nhiều nhất. Phần cài đặt (bảng lưu khoá, UNIQUE, xử lý hai request cùng khoá tới cùng lúc) ở bài 20.

Chống ghi đè khi hai người cùng sửa

Giáo viên A và B cùng mở form sửa một bài tập. A lưu, rồi B lưu đè mất thay đổi của A. Cách chuẩn là optimistic concurrency: mỗi bản ghi có số phiên bản, client gửi lại phiên bản nó đã đọc.

UPDATE assignments
SET title = $1, version = version + 1
WHERE id = $2 AND version = $3;   -- 0 dòng bị sửa → đã có người sửa trước → trả 409

Trong HTTP, phiên bản thường đi qua header ETag (server trả) và If-Match (client gửi lại), hoặc đơn giản là trường version trong JSON.

Version và tài liệu

  • Đặt /v1 ngay từ đầu. Khi phải thay đổi phá vỡ tương thích (đổi tên trường, đổi kiểu), mở /v2 và giữ /v1 chạy một thời gian cho app di động cũ.
  • Thêm trường mới không phá tương thích. Xoá, đổi tên, đổi kiểu thì có. App di động không ép người dùng cập nhật được, nên một phiên bản API có thể phải sống nhiều năm.
  • Viết tài liệu bằng OpenAPI (Swagger). Từ file OpenAPI có thể sinh client TypeScript cho frontend, và công cụ oapi-codegen sinh khung server Go.
- 401 - 200 với dữ liệu rỗng + 404 (hoặc 403), và 404 tốt hơn vì không tiết lộ lớp 77 có tồn tại ? 401 là chưa đăng nhập, không đúng. Trả 404 giúp kẻ dò id không phân biệt được "không tồn tại" với "không phải của bạn". GitHub trả 404 cho repo riêng tư mà bạn không có quyền.

Thiết kế API cho tính năng điểm danh

Giáo viên điểm danh học sinh theo ngày (có mặt / vắng có phép / vắng không phép), phụ huynh xin nghỉ cho con. Viết ra: danh sách endpoint (method + đường dẫn), body request, response, status cho từng trường hợp lỗi.
