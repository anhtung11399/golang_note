Tài nguyên và đường dẫn

REST xoay quanh tài nguyên (danh từ) và dùng method HTTP làm động từ. Đường dẫn nói "cái gì", method nói "làm gì".

Một định dạng lỗi cho toàn bộ API

{
  "error": {
    "code": "CLASS_FULL",
    "message": "Lớp đã đủ sĩ số",
    "fields": { "joinCode": "Lớp đã đủ 40 học sinh" }
  }
}
  • code: hằng số ổn định cho máy đọc. Frontend switch theo nó. Không bao giờ đổi.
  • message: câu cho người đọc, có thể hiện thẳng lên giao diện.
  • fields: lỗi theo từng ô nhập, để form tô đỏ đúng ô.

Có một chuẩn chính thức cho việc này là Problem Details for HTTP APIs (RFC 9457, Content-Type: application/problem+json). Dùng chuẩn hay tự định nghĩa đều được, quan trọng nhất là mọi endpoint trả cùng một dạng.

Validate: không tin dữ liệu nào

Mỗi kiểu request có một method Validate(), kiểm tra hết các trường rồi trả về một lỗi chứa danh sách ô sai, để frontend tô đỏ đúng ô (không dừng ở ô sai đầu tiên). Chạy thử:

package main

import (
    "encoding/json"
    "fmt"
    "strings"
    "time"
    "unicode/utf8"
)

// Lỗi chứa nhiều ô sai: tên ô -> câu báo lỗi
type FieldsError struct {
    Fields map[string]string
}

func (e *FieldsError) Error() string { return "dữ liệu không hợp lệ" }

type CreateAssignmentReq struct {
    Title   string `json:"title"`
    DueDate string `json:"dueDate"` // "2026-11-10"
    Count   int    `json:"count"`
}

// Pointer receiver vì Validate còn chuẩn hoá dữ liệu (bỏ khoảng trắng thừa)
func (r *CreateAssignmentReq) Validate() error {
    r.Title = strings.TrimSpace(r.Title)
    fields := map[string]string{}
    if n := utf8.RuneCountInString(r.Title); n == 0 || n > 200 {
        fields["title"] = "Nội dung từ 1 đến 200 ký tự"
    }
    if _, err := time.Parse(time.DateOnly, r.DueDate); err != nil {
        fields["dueDate"] = "Ngày không hợp lệ (YYYY-MM-DD)"
    }
    if r.Count < 1 || r.Count > 50 {
        fields["count"] = "Số bài từ 1 đến 50"
    }
    if len(fields) > 0 {
        return &FieldsError{Fields: fields}
    }
    return nil
}

func main() {
    body := `{"title": "   ", "dueDate": "10/11/2026", "count": 3}` // client gửi lên
    var req CreateAssignmentReq
    json.Unmarshal([]byte(body), &req)

    if err := req.Validate(); err != nil {
        fe := err.(*FieldsError) // ở đây biết chắc kiểu nên ép thẳng. Code thật dùng errors.As
        // Đây chính là phần "fields" trong response lỗi ở mục trên
        out, _ := json.MarshalIndent(map[string]any{
            "error": map[string]any{"code": "INVALID", "message": "Kiểm tra lại các ô được đánh dấu", "fields": fe.Fields},
        }, "", "  ")
        fmt.Println(string(out))
    }
}

{
  "error": {
    "code": "INVALID",
    "fields": {
      "dueDate": "Ngày không hợp lệ (YYYY-MM-DD)",
      "title": "Nội dung từ 1 đến 200 ký tự"
    },
    "message": "Kiểm tra lại các ô được đánh dấu"
  }
}

count = 3 hợp lệ nên không có trong danh sách lỗi. time.DateOnly là mẫu ngày "2006-01-02" có sẵn: ngày gửi lên dạng 10/11/2026 không khớp mẫu nên bị báo sai. json.MarshalIndent in JSON có thụt lề cho dễ đọc, và luôn xếp khoá theo chữ cái.

Mọi giới hạn validate ở backend phải khớp với maxlength, min, max ở form frontend. Frontend validate để trải nghiệm tốt, backend validate để dữ liệu đúng. Thư viện go-playground/validator cho phép viết luật bằng tag (validate:"required,max=200"), rất phổ biến khi struct nhiều trường.

Phân trang, lọc, sắp xếp

Không bao giờ trả toàn bộ một bảng. Bảng có 10 dòng lúc ra mắt sẽ có 10 triệu dòng sau hai năm.

Phân trang theo số trang (offset)

GET /v1/classes/5/assignments?page=2&size=20&sort=-dueDate&subject=toan

{ "items": [ ... ], "page": 2, "size": 20, "total": 137 }

Dễ làm, có số trang để nhảy. Nhược điểm: OFFSET 100000 chậm (database vẫn phải đi qua 100.000 dòng), và nếu có dòng mới chen vào lúc người dùng đang lật trang thì bị trùng hoặc sót.

Phân trang theo con trỏ (cursor)

GET /v1/notifications?limit=20&after=eyJpZCI6OTAwMX0

{ "items": [ ... ], "nextCursor": "eyJpZCI6ODk4MX0", "hasMore": true }

Nhanh với mọi độ sâu và không trùng / sót, hợp với cuộn vô hạn và feed. Không nhảy thẳng tới trang 50 được. Cách cài đặt bằng SQL ở bài {{n:toi-uu-query}}.

Stripe dùng cursor: tham số starting_after và trường has_more. GitHub API trả link trang sau trong header Link. Twitter / X, Facebook Graph API đều dùng cursor cho feed.

Luôn đặt giới hạn trên cho size (ví dụ tối đa 100), và chỉ cho sắp xếp / lọc theo danh sách cột cho phép. Tuyệt đối không ghép thẳng tham số sort vào câu SQL (bài {{n:bao-mat-api}}: SQL injection).

var sortable = map[string]string{
    "dueDate":   "due_date",
    "createdAt": "created_at",
}
col, ok := sortable[strings.TrimPrefix(sortParam, "-")]
if !ok {
    col = "created_at"
}

Ngày giờ, id, tiền trong JSON

  • Thời điểm: chuỗi ISO 8601 / RFC 3339 có múi giờ, nên dùng UTC: "2026-11-03T08:30:00Z". Go mặc định đổi time.Time sang dạng này.
  • Ngày không có giờ (hạn nộp, ngày sinh): "2026-11-10". Đừng biến nó thành thời điểm nửa đêm UTC, sẽ lệch ngày ở múi giờ Việt Nam (UTC+7).
  • Id 64 bit: cân nhắc trả dạng chuỗi (JavaScript chỉ chính xác tới 253, bài {{n:bien-kieu}}).
  • Tiền: số nguyên theo đơn vị nhỏ nhất kèm mã tiền tệ: {"amount": 49000, "currency": "VND"}.

Idempotency key: bấm hai lần không trả tiền hai lần

Người dùng bấm "Thanh toán", mạng chập chờn, app tự gửi lại. POST không idempotent nên có thể tạo hai giao dịch. Giải pháp là client tạo một khoá ngẫu nhiên cho mỗi thao tác và gửi kèm:

POST /v1/payments
Idempotency-Key: 8b1f3c3e-6a2c-4c1e-9a77-2f1b1c0d9e11
actors: [fe] App, [go] API, [db] Database App -> API: POST /payments (key K) API -> Database: chưa có K → xử lý, lưu kết quả kèm K API --> App: 201 {id: 77} (mạng rớt, app không nhận được) App -> API: gửi lại POST /payments (key K) API -> Database: đã có K Database --> API: kết quả cũ {id: 77} API --> App: 201 {id: 77}, không tạo giao dịch thứ hai

Đây đúng là cách Stripe làm với header Idempotency-Key, và là một trong những thiết kế API được nhắc tới nhiều nhất. Phần cài đặt (bảng lưu khoá, UNIQUE, xử lý hai request cùng khoá tới cùng lúc) ở bài {{n:bat-dong-bo}}.

Chống ghi đè khi hai người cùng sửa

Giáo viên A và B cùng mở form sửa một bài tập. A lưu, rồi B lưu đè mất thay đổi của A. Cách chuẩn là optimistic concurrency: mỗi bản ghi có số phiên bản, client gửi lại phiên bản nó đã đọc.

UPDATE assignments
SET title = $1, version = version + 1
WHERE id = $2 AND version = $3;   -- 0 dòng bị sửa → đã có người sửa trước → trả 409

Trong HTTP, phiên bản thường đi qua header ETag (server trả) và If-Match (client gửi lại), hoặc đơn giản là trường version trong JSON.

PATCH: phân biệt "không gửi" với "gửi null"

Form sửa lớp chỉ gửi trường người dùng đổi. Ba trường hợp phải phân biệt được:

{ "name": "Lớp 5A1" }              // chỉ đổi tên, ghi chú giữ nguyên
{ "note": null }                   // XOÁ ghi chú
{ "name": "Lớp 5A1", "note": "" }  // đổi tên, ghi chú thành chuỗi rỗng

Dùng struct thường với string thì không phân biệt được: thiếu trường và "" đều ra chuỗi rỗng. Con trỏ *string phân biệt được "có / không" nhưng không phân biệt được "không gửi" với "gửi null" (cả hai ra nil). Cách chuẩn: một kiểu nhỏ tự ghi nhớ "đã có trong JSON chưa".

package main

import (
    "encoding/json"
    "fmt"
)

// Opt ghi nhớ trường có xuất hiện trong JSON hay không, và có phải null không
type Opt[T any] struct {
    Set   bool // có xuất hiện
    Null  bool // xuất hiện với giá trị null
    Value T
}

func (o *Opt[T]) UnmarshalJSON(b []byte) error {
    o.Set = true // chỉ được gọi khi khoá có trong JSON
    if string(b) == "null" {
        o.Null = true
        return nil
    }
    return json.Unmarshal(b, &o.Value)
}

type PatchClass struct {
    Name     Opt[string] `json:"name"`
    Note     Opt[string] `json:"note"`
    Capacity Opt[int]    `json:"capacity"`
}

func main() {
    for _, body := range []string{
        `{"name":"Lớp 5A1"}`,
        `{"note":null}`,
        `{"name":"Lớp 5A1","note":""}`,
    } {
        var p PatchClass
        json.Unmarshal([]byte(body), &p)
        fmt.Printf("%-30s name=%+v note=%+v\n", body, p.Name, p.Note)
    }
}

$ go run .
{"name":"Lớp 5A1"}             name={Set:true Null:false Value:Lớp 5A1} note={Set:false Null:false Value:}
{"note":null}                  name={Set:false Null:false Value:} note={Set:true Null:true Value:}
{"name":"Lớp 5A1","note":""}   name={Set:true Null:false Value:Lớp 5A1} note={Set:true Null:false Value:}

Giải thích: encoding/json chỉ gọi UnmarshalJSON của trường nào có trong JSON, nên Set cho biết "đã gửi". Giá trị null được truyền vào dưới dạng 4 byte null. Ba body giờ cho ra ba trạng thái khác nhau.

Ghép câu UPDATE chỉ với các trường đã gửi, mỗi trường đi kèm một cờ "có gửi" ($2, $4, $6):

UPDATE classes SET
    name     = CASE WHEN $2 THEN $3 ELSE name END,
    note     = CASE WHEN $4 THEN $5 ELSE note END,   -- $5 là NULL khi client gửi null
    capacity = CASE WHEN $6 THEN $7 ELSE capacity END
WHERE id = $1 AND teacher_id = $8;

Validate cũng theo cờ: chỉ kiểm tra độ dài name khi Name.Set, và từ chối name: null vì tên là bắt buộc.

Hành động không phải CRUD

Không phải việc gì cũng là "sửa một trường". Giao bài, khoá lớp, duyệt phụ huynh vào lớp là hành động có luật riêng (kiểm tra trạng thái, gửi thông báo). Hai cách đặt tên phổ biến:

POST /v1/classes/42/lock                    # động từ là tài nguyên con: dễ đọc, dễ phân quyền riêng
POST /v1/classes/42/roster/7/approve
POST /v1/assignments/9:publish              # kiểu của Google API (AIP-136)

Tránh PATCH /classes/42 {"locked": true} cho việc có hậu quả: client có thể gửi kèm các trường khác, và logic "khoá lớp thì làm gì" bị lẫn vào handler sửa chung.

Việc chạy lâu: 202 Accepted

"Xuất báo cáo cả năm ra PDF" mất 40 giây. Không giữ request chờ 40 giây (proxy cắt ở 30 giây, người dùng tưởng treo). Trả ngay 202 kèm địa chỉ để hỏi trạng thái:

actors: [fe] Client, [go] API, [q] Worker Client -> API: POST /v1/classes/42/reports API -> Worker: xếp việc vào hàng đợi API --> Client: 202, Location: /v1/jobs/j_81 Client -> API: GET /v1/jobs/j_81 API --> Client: 200 {status: "running", progress: 40} Worker -> API: xong, lưu file Client -> API: GET /v1/jobs/j_81 API --> Client: 200 {status: "done", resultUrl: "..."} 
{ "id": "j_81", "status": "failed", "error": { "code": "NO_DATA", "message": "Lớp chưa có bài tập nào" } }

Trạng thái nên là một tập cố định: queued, running, done, failed. Thay vì hỏi liên tục, client có thể nghe SSE / WebSocket (bài {{n:realtime-file}}) để biết khi xong.

Thao tác hàng loạt

Giáo viên tích 30 bài rồi bấm "Đã chấm". Gửi 30 request thì chậm và dễ dở dang. Một endpoint hàng loạt:

POST /v1/submissions:batchGrade
{ "items": [ {"id": 1, "score": 9}, {"id": 2, "score": 10}, {"id": 99, "score": 8} ] }

Phải quyết định trước một trong hai kiểu, và ghi rõ trong tài liệu:

  • Tất cả hoặc không gì: một transaction, một mục lỗi thì không mục nào được lưu, trả 422 chỉ rõ mục nào. Đơn giản cho client.
  • Từng mục độc lập: trả 200 với kết quả từng mục.
{ "results": [
    { "id": 1, "ok": true },
    { "id": 2, "ok": true },
    { "id": 99, "ok": false, "error": { "code": "NOT_FOUND", "message": "Không tìm thấy bài nộp" } }
] }

Luôn giới hạn số mục (ví dụ tối đa 100) và kiểm tra quyền cho từng mục: id 99 có thể là bài của lớp khác.

Cache HTTP và request có điều kiện

Danh sách môn học của lớp ít khi đổi, nhưng app gọi mỗi lần mở màn hình. ETag cho phép trả 304 Not Modified không kèm dữ liệu khi client đã có bản mới nhất:

func subjects(w http.ResponseWriter, r *http.Request) {
    list, version := loadSubjects(r.Context(), classID) // version: số tăng mỗi lần sửa môn, hoặc updated_at
    etag := fmt.Sprintf(`"s-%d-%d"`, classID, version)

    w.Header().Set("ETag", etag)
    w.Header().Set("Cache-Control", "private, no-cache") // được giữ bản sao, nhưng phải hỏi lại server mỗi lần
    if r.Header.Get("If-None-Match") == etag {
        w.WriteHeader(http.StatusNotModified) // không gửi body
        return
    }
    writeJSON(w, 200, list)
}

Định dạng lỗi theo chuẩn: Problem Details

Định dạng {error:{code,message}} ở trên là cách tự đặt, rất phổ biến. Nếu muốn theo chuẩn, RFC 9457 (Problem Details) định nghĩa kiểu application/problem+json, nhiều framework và cổng API hiểu sẵn:

{
  "type": "https://sobaitap.vn/errors/class-full",
  "title": "Lớp đã đủ sĩ số",
  "status": 409,
  "detail": "Lớp 5A đã có 30/30 em.",
  "instance": "/v1/classes/42/join",
  "code": "CLASS_FULL"
}

Chọn kiểu nào cũng được, quan trọng là một kiểu cho mọi endpoint, có mã lỗi ổn định cho code xử lý, và câu cho người đọc.

Giới hạn tần suất: báo cho client biết

Khi giới hạn tần suất (bài {{n:cache}}), trả 429 kèm header để client biết khi nào thử lại:

HTTP/1.1 429 Too Many Requests
Retry-After: 30
RateLimit-Limit: 100
RateLimit-Remaining: 0
RateLimit-Reset: 30

Client (và thư viện retry) nên đọc Retry-After thay vì thử lại ngay. Retry tự động chỉ áp dụng cho lỗi tạm thời (429, 502, 503, 504) và thao tác idempotent (GET, PUT, DELETE, hoặc POST có Idempotency-Key), kèm thời gian chờ tăng dần có ngẫu nhiên.

Version và tài liệu

  • Đặt /v1 ngay từ đầu. Khi phải thay đổi phá vỡ tương thích (đổi tên trường, đổi kiểu), mở /v2 và giữ /v1 chạy một thời gian cho app di động cũ.
  • Thêm trường mới không phá tương thích. Xoá, đổi tên, đổi kiểu thì có. App di động không ép người dùng cập nhật được, nên một phiên bản API có thể phải sống nhiều năm.
  • Viết tài liệu bằng OpenAPI (Swagger). Từ file OpenAPI có thể sinh client TypeScript cho frontend, và công cụ oapi-codegen sinh khung server Go.
- 401 - 200 với dữ liệu rỗng + 404 (hoặc 403), và 404 tốt hơn vì không tiết lộ lớp 77 có tồn tại ? 401 là chưa đăng nhập, không đúng. Trả 404 giúp kẻ dò id không phân biệt được "không tồn tại" với "không phải của bạn". GitHub trả 404 cho repo riêng tư mà bạn không có quyền.

Bài tập

Thiết kế API cho tính năng điểm danh

Bài này không viết code, chỉ thiết kế trên giấy (hoặc file ghi chú), giống việc bạn làm trước khi bắt tay vào một tính năng ở công ty. Tính năng: giáo viên điểm danh học sinh theo ngày (có mặt / vắng có phép / vắng không phép), phụ huynh xin nghỉ cho con. Viết ra: danh sách endpoint (method + đường dẫn), body request, response, status cho từng trường hợp lỗi.

Gợi ý từng bước

  1. Liệt kê danh từ (tài nguyên): lớp, học sinh, ngày điểm danh, đơn xin nghỉ. Mỗi danh từ thường thành một đường dẫn.
  2. Liệt kê ai làm gì: giáo viên xem danh sách ngày hôm nay, giáo viên lưu điểm danh, phụ huynh gửi đơn, giáo viên duyệt đơn. Mỗi việc thành một endpoint, chọn method theo bảng ở đầu bài.
  3. Với mỗi endpoint, hỏi: ai được gọi (kiểm quyền thế nào), gửi sai thì trả gì (400), không có quyền thì trả gì (404 hay 403), gọi hai lần thì sao (idempotent không).
