Index: mục lục của bảng

Không có index, để tìm WHERE email = 'lan@x.vn' Postgres phải đọc từng dòng của bảng (sequential scan). 100 dòng thì không sao. 10 triệu dòng thì mỗi lần đăng nhập đọc cả bảng.

Index (mặc định là cây B-tree) giữ các giá trị của cột theo thứ tự, mỗi giá trị trỏ tới dòng chứa nó. Tìm trong cây chỉ cần đi qua vài tầng, giống tra từ điển theo chữ cái thay vì đọc từng trang.

CREATE INDEX idx_assignments_class_due ON assignments (class_id, due_date DESC);
CREATE INDEX idx_submissions_student ON submissions (student_id);

Khoá chính và cột UNIQUE tự có index. Khoá ngoại thì không (trong Postgres): bạn phải tự tạo index cho class_id, teacher_id... nếu không, mỗi lần lọc theo lớp hay xoá một lớp (CASCADE) là quét toàn bảng con.

Index nhiều cột: thứ tự quan trọng

Index (class_id, due_date) giống danh bạ sắp theo (họ, tên):

Truy vấnDùng được index?
WHERE class_id = 5Có (cột đầu)
WHERE class_id = 5 AND due_date >= '2026-11-01'Có, rất tốt
WHERE class_id = 5 ORDER BY due_date DESC LIMIT 20Có, và khỏi phải sắp xếp
WHERE due_date = '2026-11-10'Gần như không (thiếu cột đầu), giống tìm theo tên mà không biết họ

Quy tắc: cột lọc bằng = đứng trước, cột lọc theo khoảng hoặc sắp xếp đứng sau.

Index không miễn phí

  • Mỗi lần INSERT / UPDATE / DELETE phải cập nhật mọi index của bảng. Bảng ghi nhiều mà có 10 index thì ghi chậm.
  • Index chiếm ổ đĩa và bộ nhớ đệm.
  • Hàm trên cột làm index vô dụng: WHERE lower(email) = $1 không dùng index trên email. Hoặc lưu email chữ thường sẵn, hoặc tạo index trên biểu thức (lower(email)).

Từ 10ms xuống 0,05ms (nhanh hơn 200 lần) là chuyện bình thường khi thêm đúng index. 10ms nghe nhỏ, nhưng bảng to gấp 10 lần thì thành 100ms, và nhân với hàng nghìn request mỗi giây thì database quá tải.

EXPLAIN ANALYZE chạy thật câu lệnh. Với UPDATE / DELETE, bọc trong BEGIN; ... ROLLBACK;. Và kế hoạch trên máy bạn (100 dòng) có thể khác hẳn production (10 triệu dòng): Postgres chọn cách chạy dựa trên thống kê dữ liệu thật.

Bật extension pg_stat_statements trên production: nó thống kê câu truy vấn nào tốn tổng thời gian nhiều nhất. Thường 5 câu truy vấn chiếm phần lớn tải, sửa chúng trước. Các dịch vụ Postgres có quản lý (AWS RDS, Google Cloud SQL, Supabase, Neon) đều có sẵn hoặc bật được.

Giống lỗi gọi API trong vòng lặp ở frontend: mỗi item trong danh sách tự fetch chi tiết của nó. Ở frontend là 30 request HTTP, ở backend là 30 lần đi về database cho mỗi request của người dùng. Nhân với 1.000 người dùng mỗi phút là 30.000 truy vấn vô ích.

ORM là nơi N+1 hay xuất hiện nhất, vì truy cập class.Students trông như đọc một trường nhưng thật ra chạy một câu SQL. Vì vậy các ORM đều có cơ chế "preload / eager loading". Với SQL thuần, N+1 dễ thấy hơn: một câu Query nằm trong vòng for.

Tranh chấp: hai request cùng sửa một dòng

Đây là phần quan trọng nhất của bài và là chỗ backend khác frontend nhiều nhất. Ví dụ bán vé: còn 1 vé, hai người bấm mua cùng lúc.

Tận mắt thấy lỗi. Chương trình dưới cho 50 goroutine (50 người) cùng mua khi kho còn 10 vé, lần đầu bằng cách "đọc, kiểm tra, ghi", lần sau bằng cách đúng (cách 1 ngay bên dưới). Chạy với database của bài 14 (chương trình tự tạo bảng tickets), cách chạy giống phần "Chạy thử" bài 15:

package main

import (
    "context"
    "fmt"
    "os"
    "sync"

    "github.com/jackc/pgx/v5/pgxpool"
)

// SAI: đọc, kiểm tra, rồi mới ghi. Ba bước rời nhau
func buyNaive(ctx context.Context, db *pgxpool.Pool) bool {
    var stock int
    db.QueryRow(ctx, `SELECT stock FROM tickets WHERE id = 1`).Scan(&stock)
    if stock < 1 {
        return false // hết vé
    }
    db.Exec(ctx, `UPDATE tickets SET stock = $1 WHERE id = 1`, stock-1)
    return true
}

// ĐÚNG: điều kiện nằm trong chính câu UPDATE. Một câu lệnh là nguyên tử
func buySafe(ctx context.Context, db *pgxpool.Pool) bool {
    tag, err := db.Exec(ctx, `UPDATE tickets SET stock = stock - 1 WHERE id = 1 AND stock >= 1`)
    return err == nil && tag.RowsAffected() == 1
}

// 50 người cùng mua khi chỉ còn 10 vé
func rush(ctx context.Context, db *pgxpool.Pool, buy func(context.Context, *pgxpool.Pool) bool) int {
    db.Exec(ctx, `UPDATE tickets SET stock = 10 WHERE id = 1`) // đặt lại kho: 10 vé
    var mu sync.Mutex
    sold := 0
    var wg sync.WaitGroup
    for range 50 {
        wg.Add(1)
        go func() {
            defer wg.Done()
            if buy(ctx, db) {
                mu.Lock()
                sold++
                mu.Unlock()
            }
        }()
    }
    wg.Wait()
    return sold
}

func main() {
    ctx := context.Background()
    db, err := pgxpool.New(ctx, os.Getenv("DATABASE_URL"))
    if err != nil {
        fmt.Println(err)
        os.Exit(1)
    }
    defer db.Close()

    db.Exec(ctx, `CREATE TABLE IF NOT EXISTS tickets (id int PRIMARY KEY, stock int NOT NULL)`)
    db.Exec(ctx, `INSERT INTO tickets VALUES (1, 10) ON CONFLICT DO NOTHING`)

    fmt.Println("cách sai: bán được", rush(ctx, db, buyNaive), "vé (kho chỉ có 10)")
    fmt.Println("cách đúng: bán được", rush(ctx, db, buySafe), "vé")
}

Cách 1: điều kiện nằm ngay trong câu UPDATE (nên dùng đầu tiên)

UPDATE tickets SET stock = stock - 1
WHERE id = $1 AND stock >= 1
RETURNING stock;

Ghép với tạo đơn trong cùng một transaction (bài 15): UPDATE không sửa được dòng nào thì rollback và trả "hết vé".

Cách 2: khoá dòng bằng SELECT ... FOR UPDATE

Khi logic kiểm tra phức tạp, không viết gọn trong một câu UPDATE được:

err := pgx.BeginFunc(ctx, db, func(tx pgx.Tx) error {
    var balance int64
    // Khoá dòng ví này tới khi transaction kết thúc. Request khác muốn khoá cùng dòng phải CHỜ
    if err := tx.QueryRow(ctx, `SELECT balance FROM wallets WHERE user_id = $1 FOR UPDATE`, uid).Scan(&balance); err != nil {
        return err
    }
    if balance < amount {
        return ErrInsufficientFunds
    }
    // ... kiểm tra hạn mức trong ngày, trạng thái tài khoản, v.v.
    _, err := tx.Exec(ctx, `UPDATE wallets SET balance = balance - $1 WHERE user_id = $2`, amount, uid)
    return err
})

FOR UPDATE SKIP LOCKED bỏ qua những dòng đang bị khoá thay vì chờ. Đây là cách làm hàng đợi việc ngay trong Postgres: nhiều worker cùng lấy việc mà không giành nhau một việc (bài 20).

Cách 3: optimistic concurrency với cột version

Đã gặp ở bài 12: UPDATE ... WHERE id = $1 AND version = $2. Không khoá gì, chỉ phát hiện xung đột và báo 409. Hợp với dữ liệu ít khi bị sửa cùng lúc (người dùng sửa form).

MứcÝ nghĩa

Gợi ý từng bước

  1. Cách "đếm rồi mới thêm" bị đúng lỗi bán vé ở trên: 10 request cùng đếm được 0. Phải làm sao để các request của cùng một giáo viên xếp hàng, từng cái một đếm và thêm.
  2. Không khoá được "những lớp chưa tồn tại". Nhưng khoá được một dòng chắc chắn có thật và đại diện cho giáo viên: dòng của họ trong bảng users, bằng SELECT ... FOR UPDATE trong một transaction.
  3. Trong cùng transaction: khoá, đếm, nếu chưa đủ thì INSERT. Dùng pgx.BeginFunc (bài 15) để khỏi tự viết commit / rollback.
  4. Test: sync.WaitGroup và 10 goroutine (bài 09), đếm số lần thành công và số lần nhận ErrQuotaExceeded, rồi đếm lại trong database. Test cần database thật, đọc địa chỉ từ DATABASE_URL, không có thì t.Skip.

package main

import (
    "context"
    "errors"

    "github.com/jackc/pgx/v5"
    "github.com/jackc/pgx/v5/pgxpool"
)

var ErrQuotaExceeded = errors.New("đã đủ số lớp của gói")

type Store struct {
    db *pgxpool.Pool
}

// CreateClassWithQuota tạo lớp, nhưng không bao giờ để giáo viên có quá `quota` lớp,
// kể cả khi nhiều request tới cùng lúc trên nhiều bản server
func (s *Store) CreateClassWithQuota(ctx context.Context, teacherID int64, name string, quota int) (int64, error) {
    var id int64
    err := pgx.BeginFunc(ctx, s.db, func(tx pgx.Tx) error {
        // 1. Khoá dòng của giáo viên. Request thứ hai của CÙNG giáo viên đứng chờ ở đây
        //    tới khi transaction của request thứ nhất commit hoặc rollback
        if _, err := tx.Exec(ctx, `SELECT 1 FROM users WHERE id = $1 FOR UPDATE`, teacherID); err != nil {
            return err
        }
        // 2. Đếm: lúc này không ai khác đang tạo lớp cho giáo viên này
        var n int
        if err := tx.QueryRow(ctx, `SELECT count(*) FROM classes WHERE teacher_id = $1`, teacherID).Scan(&n); err != nil {
            return err
        }
        if n >= quota {
            return ErrQuotaExceeded // BeginFunc thấy lỗi thì tự rollback
        }
        // 3. Tạo
        return tx.QueryRow(ctx,
            `INSERT INTO classes (teacher_id, name, capacity) VALUES ($1, $2, 30) RETURNING id`,
            teacherID, name).Scan(&id)
    }) // hàm trả nil thì BeginFunc tự commit, mở khoá cho request đang chờ
    return id, err
}

package main

import (

    "errors"
    "fmt"

func TestQuotaUnderConcurrency(t *testing.T) {
    url := os.Getenv("DATABASE_URL")
    if url == "" {
        t.Skip("cần DATABASE_URL trỏ tới database có dữ liệu bài 14")
    }
    ctx := context.Background()
    db, err := pgxpool.New(ctx, url)
    if err != nil {
        t.Fatal(err)
    }
    defer db.Close()
    s := &Store{db: db}

    // Dọn: Thầy Nam (id 8) bắt đầu với 0 lớp
    if _, err := db.Exec(ctx, `DELETE FROM classes WHERE teacher_id = 8`); err != nil {
        t.Fatal(err)
    }

    const quota = 3
    var mu sync.Mutex
    ok, rejected := 0, 0
    var wg sync.WaitGroup
    for i := range 10 { // 10 request cùng lúc
        wg.Add(1)
        go func() {
            defer wg.Done()
            _, err := s.CreateClassWithQuota(ctx, 8, fmt.Sprintf("Lớp thử %d", i), quota)
            mu.Lock()
            defer mu.Unlock()
            switch {
            case err == nil:
                ok++
            case errors.Is(err, ErrQuotaExceeded):
                rejected++
            default:
                t.Errorf("lỗi lạ: %v", err)
            }
        }()
    }
    wg.Wait()

    var inDB int
    db.QueryRow(ctx, `SELECT count(*) FROM classes WHERE teacher_id = 8`).Scan(&inDB)
    t.Logf("thành công %d, bị từ chối %d, trong database có %d lớp", ok, rejected, inDB)
    if ok != quota || rejected != 10-quota || inDB != quota {
        t.Errorf("muốn đúng %d lớp được tạo", quota)
    }
}

Giải thích: không có khoá, nhiều transaction cùng đếm được 0, 1 hoặc 2 lớp rồi cùng thêm, ra 9 lớp. Có khoá, transaction thứ hai đứng chờ ở dòng FOR UPDATE tới khi transaction thứ nhất commit, lúc đó nó mới đếm và thấy lớp vừa được thêm. Giáo viên khác nhau khoá dòng khác nhau, nên không chặn nhau. Test để t.Skip khi thiếu DATABASE_URL, nhờ vậy go test ./... trên máy không có database vẫn chạy được.

Đây chính là lỗi đã được nhắc ở bài 13 (service tạo lớp "đếm rồi mới tạo"), giờ bạn đã biết cách sửa.

Đọc EXPLAIN trên bảng 1 triệu dòng

Tạo một database riêng có bảng assignments với 1 triệu dòng giả, rồi so sánh EXPLAIN ANALYZE của truy vấn "20 bài mới nhất của lớp 42" trước và sau khi tạo index. Thử thêm phân trang OFFSET 500000 để thấy offset chậm thế nào, so với phân trang keyset.

Làm trên Postgres ở máy bạn (không làm trên database thật của công ty). Bảng chiếm khoảng 70MB.

Xem lời giải

Mở psql rồi dán lần lượt. \c bench là lệnh của psql để chuyển sang database bench, \timing on in thời gian của mỗi câu.

CREATE DATABASE bench;
\c bench
CREATE TABLE classes (
    id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name text NOT NULL
);
CREATE TABLE assignments (
    id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    class_id  bigint NOT NULL REFERENCES classes(id),
    title     text NOT NULL,
    due_date  date NOT NULL
);

-- 5.000 lớp, rồi 1 triệu bài tập chia đều cho các lớp
-- generate_series(1, 5000) sinh ra các số 1, 2, ..., 5000, giống một vòng for
INSERT INTO classes (name) SELECT 'Lớp ' || g FROM generate_series(1, 5000) g;
INSERT INTO assignments (class_id, title, due_date)
SELECT (g % 5000) + 1, 'Bài ' || g, date '2026-01-01' + (g % 300)
FROM generate_series(1, 1000000) g;
ANALYZE assignments;   -- cập nhật thống kê cho bộ lập kế hoạch
\timing on

EXPLAIN ANALYZE
SELECT id, title FROM assignments
WHERE class_id = 42 ORDER BY due_date DESC LIMIT 20;

Kết quả là kế hoạch "Trước khi có index" ở mục EXPLAIN đầu bài (khoảng 10ms, Seq Scan). Tạo index rồi chạy lại đúng câu đó:

CREATE INDEX idx_assignments_class_due ON assignments (class_id, due_date DESC);

EXPLAIN ANALYZE
SELECT id, title FROM assignments
WHERE class_id = 42 ORDER BY due_date DESC LIMIT 20;

Ra kế hoạch "Sau khi CREATE INDEX" (khoảng 0,05ms, Index Scan). Tiếp theo, so sánh hai cách lấy "trang thứ 25.000":

-- OFFSET: bỏ qua 500.000 dòng đầu
EXPLAIN ANALYZE
SELECT id, title FROM assignments ORDER BY id LIMIT 20 OFFSET 500000;

-- Keyset: "lấy 20 dòng sau id 500000"
EXPLAIN ANALYZE
SELECT id, title FROM assignments WHERE id > 500000 ORDER BY id LIMIT 20;

 Limit  (actual time=36.588..36.590 rows=20 loops=1)
   ->  Index Scan using assignments_pkey on assignments  (actual time=0.007..28.386 rows=500020 loops=1)
 Execution Time: 36.596 ms

 Limit  (actual time=0.010..0.012 rows=20 loops=1)
   ->  Index Scan using assignments_pkey on assignments  (actual time=0.009..0.011 rows=20 loops=1)
         Index Cond: (id > 500000)
 Execution Time: 0.018 ms

Giải thích: cả hai đều dùng index, nhưng OFFSET vẫn phải đi qua rows=500020 dòng rồi vứt 500.000 dòng đầu, mất 36ms. Keyset nhảy thẳng tới id > 500000 bằng index và chỉ đọc 20 dòng, mất 0,02ms: nhanh hơn khoảng 2.000 lần, và trang sâu đến đâu cũng nhanh như trang đầu. Số mili giây trên máy bạn sẽ khác, tỉ lệ thì tương tự.
