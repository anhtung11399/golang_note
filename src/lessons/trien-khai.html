Đóng gói bằng Docker

Docker đóng gói chương trình cùng mọi thứ nó cần thành một image, chạy giống hệt nhau ở máy bạn, CI và production. Với Go, image có thể rất nhỏ vì chương trình chỉ là một file.

# Giai đoạn 1: build (image có đủ công cụ Go, khá lớn).
# Phiên bản Go phải bằng hoặc mới hơn dòng "go" trong go.mod
FROM golang:1.27 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download                 # tách riêng bước này để Docker cache thư viện
COPY . .
RUN CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o /out/api ./cmd/api

# Giai đoạn 2: chạy (chỉ chứa file chạy, không có shell, không có trình biên dịch)
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/api /api
COPY migrations /migrations
USER nonroot:nonroot
EXPOSE 8080
ENTRYPOINT ["/api"]
  • Nhiều giai đoạn (multi-stage): công cụ build không lọt vào image chạy. Image cuối chỉ cỡ vài chục MB thay vì hơn 1GB.
  • CGO_ENABLED=0: build file chạy tĩnh hoàn toàn, không phụ thuộc thư viện C của hệ điều hành, chạy được trên image tối giản.
  • distroless (của Google): không có shell, không có trình quản lý gói. Kẻ tấn công lọt vào container cũng không có công cụ gì để dùng. Có thể dùng scratch (rỗng hoàn toàn) nhưng khi đó phải tự chép chứng chỉ CA để gọi HTTPS.
  • nonroot: không chạy bằng quyền root.

Giống build frontend: giai đoạn đầu cài node_modules và chạy vite build, giai đoạn sau chỉ chép thư mục dist vào nginx. Khác biệt: với Go, thứ được chép sang là một file chạy duy nhất.

Môi trường phát triển với Docker Compose

services:
  db:
    image: postgres:17
    environment:
      POSTGRES_PASSWORD: dev
      POSTGRES_DB: sobaitap
    ports: ["5432:5432"]
    volumes: [pgdata:/var/lib/postgresql/data]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 2s
  redis:
    image: redis:7
    ports: ["6379:6379"]
  api:
    build: .
    environment:
      DATABASE_URL: postgres://postgres:dev@db:5432/sobaitap?sslmode=disable
      REDIS_URL: redis://redis:6379
      SESSION_KEY: dev-only-key-at-least-32-characters!!
    ports: ["8080:8080"]
    depends_on:
      db: { condition: service_healthy }
volumes:
  pgdata:

docker compose up -d db redis   # chỉ chạy database, còn API chạy bằng go run để sửa code nhanh
docker compose up --build       # chạy cả hệ thống giống production

CI: mọi thay đổi đều được kiểm tra tự động

name: ci
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:17
        env: { POSTGRES_PASSWORD: test }
        ports: ["5432:5432"]
        options: --health-cmd "pg_isready -U postgres" --health-interval 2s
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with: { go-version-file: go.mod }
      - run: go vet ./...
      - run: go test -race -cover ./...
        env:
          TEST_DATABASE_URL: postgres://postgres:test@localhost:5432/postgres?sslmode=disable
      - run: go run golang.org/x/vuln/cmd/govulncheck@latest ./...
      - run: docker build -t sobaitap-api .

Bảo vệ nhánh main: chỉ gộp được khi CI xanh và có người review. Deploy production chỉ đi từ main, không bao giờ từ máy cá nhân của một ai đó.

Database: với production, ưu tiên dịch vụ có quản lý (Cloud SQL, RDS, Neon, Supabase...): tự sao lưu, tự vá lỗi, có bản sao. Tự chạy Postgres thì bạn phải tự lo tất cả những việc đó.

Sao lưu database và thử khôi phục. Bản sao lưu chưa từng được khôi phục thử thì chưa chắc dùng được. Năm 2017, GitLab mất khoảng 6 giờ dữ liệu production sau khi một kỹ sư xoá nhầm thư mục dữ liệu trên máy chủ database. Trong bài viết công khai sau sự cố, họ cho biết nhiều cơ chế sao lưu đã không hoạt động như mong đợi.

Deploy không gián đoạn

[ext] Gộp vào main / CI xanh -> build image, gắn tag theo commit [go] Image sobaitap-api:9f3c1a2 -> chạy migration (phải tương thích với code cũ, bài {{n:go-postgres}}) [db] Database đã có lược đồ mới -> rolling update: bật bản mới, chờ /readyz, tắt dần bản cũ (SIGTERM, bài {{n:kien-truc}}) [ok] Bản mới phục vụ 100% / theo dõi tỉ lệ lỗi, p99 -> có vấn đề: quay lại image trước (rollback) trong vài phút [warn] Rollback / vì vậy migration không được phá code cũ
  • Server không giữ trạng thái (stateless): phiên đăng nhập ở database / Redis, file ở dịch vụ lưu trữ, không lưu gì trên ổ đĩa của server. Nhờ vậy chạy 1 hay 20 bản đều như nhau, và tắt bất kỳ bản nào cũng không mất gì.
  • Mở rộng theo chiều ngang: tải tăng thì thêm bản server sau load balancer. Nút cổ chai tiếp theo thường là database, không phải Go.
  • Feature flag: deploy code mới nhưng tắt tính năng, bật dần cho một phần người dùng. Tách việc "deploy" khỏi việc "phát hành".

Biết đang chạy phiên bản nào

import "runtime/debug"

func version() string {
    if info, ok := debug.ReadBuildInfo(); ok {
        for _, s := range info.Settings {
            if s.Key == "vcs.revision" { // go build tự nhúng commit git (khi build trong repo git)
                return s.Value[:min(7, len(s.Value))]
            }
        }
    }
    return "dev"
}

// Ghi vào log lúc khởi động và trả ở /version: biết ngay lỗi xuất hiện từ bản nào

Checklist cấu hình production

  • HTTPS ở mọi nơi. Nền tảng thường lo sẵn, VPS thì Caddy tự lấy chứng chỉ Let's Encrypt.
  • Biến môi trường production không có cờ dev / debug. Bí mật lấy từ trình quản lý bí mật.
  • Server có timeout, có graceful shutdown, có /livez, /readyz.
  • Log JSON ra stdout, có nơi thu gom và tìm kiếm.
  • Metrics + cảnh báo cho tỉ lệ lỗi và độ trễ.
  • Database có sao lưu tự động, đã thử khôi phục. Pool kết nối không vượt giới hạn của database.
  • Giới hạn tài nguyên container (CPU, RAM). Từ Go 1.25, runtime tự đọc giới hạn CPU của container (cgroup) để đặt GOMAXPROCS. Có thể đặt GOMEMLIMIT để GC làm việc chăm hơn khi gần chạm giới hạn RAM.
- Không sao, load balancer tự đồng bộ thư mục + File nằm trên máy nào thì chỉ máy đó có. Request vào máy khác sẽ không thấy file, và file mất khi container được thay mới - Docker tự chia sẻ thư mục giữa các máy ? Server phải stateless. File để ở dịch vụ lưu trữ đối tượng dùng chung (S3, R2, GCS), database chỉ lưu đường dẫn.

Bài tập

Đóng gói và chạy API có đăng nhập

Lấy API ở lời giải bài {{n:xac-thuc}} (đăng ký, đăng nhập, ghi chú, Postgres). Viết:

  • Dockerfile nhiều giai đoạn.
  • compose.yaml chạy API + Postgres, database tự tạo bảng lần đầu.
  • workflow GitHub Actions: vet, test với Postgres thật, govulncheck, build image.
  • API tắt an toàn khi docker compose stop.

So sánh kích thước image cuối với image golang.

Gợi ý từng bước

  1. Dockerfile: chép mẫu ở đầu bài, sửa dòng build thành go build ... -o /out/api . (dự án bài {{n:xac-thuc}} có main ở thư mục gốc, không phải ./cmd/api).
  2. Postgres chính thức tự chạy mọi file .sql trong /docker-entrypoint-initdb.d/ khi database còn trống. Gắn schema.sql vào đó là có bảng.
  3. Trong compose, các container gọi nhau bằng tên service: API kết nối tới db:5432, không phải localhost (localhost bên trong container API là chính container API).
  4. docker stop gửi tín hiệu SIGTERM rồi chờ 10 giây. Thêm vào main phần signal.NotifyContext + srv.Shutdown như bài {{n:kien-truc}}, thời gian chờ ngắn hơn 10 giây.
Xem lời giải

Giữ nguyên auth.go, notes.go, schema.sql của bài {{n:xac-thuc}}. Thay hàm main trong main.go bằng bản có tắt an toàn (thêm import "errors", "os/signal", "syscall"), kèm hai route /livez và /slow để thử:

func main() {
    ctx := context.Background()
    db, err := pgxpool.New(ctx, os.Getenv("DATABASE_URL"))
    if err != nil {
        log.Fatal(err)
    }
    defer db.Close()
    if err := db.Ping(ctx); err != nil {
        log.Fatal("không kết nối được database: ", err)
    }

    a := &App{db: db, limiter: &loginLimiter{fails: map[string][]time.Time{}}}

    mux := http.NewServeMux()
    mux.HandleFunc("POST /register", a.register)
    mux.HandleFunc("POST /login", a.login)
    mux.HandleFunc("POST /logout", a.logout)
    mux.HandleFunc("GET /me", requireUser(a.me))
    mux.HandleFunc("GET /notes", requireUser(a.listNotes))
    mux.HandleFunc("POST /notes", requireUser(a.createNote))
    mux.HandleFunc("GET /notes/{id}", requireUser(a.getNote))
    mux.HandleFunc("DELETE /notes/{id}", requireUser(a.deleteNote))

    mux.HandleFunc("GET /livez", func(w http.ResponseWriter, r *http.Request) { w.Write([]byte("ok")) })
    mux.HandleFunc("GET /slow", func(w http.ResponseWriter, r *http.Request) {
        time.Sleep(5 * time.Second) // để thử tắt an toàn
        w.Write([]byte("xong việc chậm\n"))
    })

    srv := &http.Server{Addr: ":8080", Handler: a.authMiddleware(mux), ReadHeaderTimeout: 5 * time.Second}

    // docker stop gửi SIGTERM: ngừng nhận request mới, chờ request đang chạy xong rồi thoát
    sigCtx, stop := signal.NotifyContext(ctx, os.Interrupt, syscall.SIGTERM)
    defer stop()
    done := make(chan struct{})
    go func() {
        <-sigCtx.Done()
        log.Println("đang tắt, chờ các request dở dang")
        shutdownCtx, cancel := context.WithTimeout(context.Background(), 8*time.Second) // docker stop chờ 10 giây
        defer cancel()
        srv.Shutdown(shutdownCtx) // chờ request đang chạy xong mới trả về
        close(done)
    }()

    log.Println("http://localhost:8080")
    // Khi Shutdown bắt đầu, ListenAndServe trả về ErrServerClosed NGAY, chưa chờ gì cả
    if err := srv.ListenAndServe(); !errors.Is(err, http.ErrServerClosed) {
        log.Fatal(err)
    }
    <-done // nên phải đứng chờ Shutdown làm xong, nếu không main thoát và cắt ngang request
    log.Println("đã tắt")
}

Chạy cả hệ thống (máy chỉ cần Docker, không cần cài Go hay Postgres):

docker compose up --build -d   # lần đầu phải tải image Go và Postgres, có thể mất vài phút
docker compose ps              # hai dòng db và api, cột STATUS là "Up"
curl localhost:8080/livez      # ok
docker images                  # so cột SIZE của image api với image golang

Image API chỉ cỡ vài chục MB (file chạy khoảng 10 MB cộng image distroless), trong khi image golang hơn 800 MB. Sau đó thử lại các lệnh curl đăng ký, đăng nhập của bài {{n:xac-thuc}}: kết quả giống hệt.

Thử tắt an toàn: gọi request chậm rồi dừng container ngay khi nó đang chạy:

curl localhost:8080/slow &     # chạy nền, chờ 5 giây
docker compose stop api        # gửi SIGTERM trong lúc request đang chạy
docker compose logs api

Kết quả đúng: curl vẫn in ra xong việc chậm, và log của api có hai dòng đang tắt, chờ các request dở dang rồi vài giây sau mới tới đã tắt. Container chỉ dừng sau khi request xong.

Để ý dòng <-done trong main. Khi Shutdown bắt đầu, ListenAndServe trả về ngay lập tức. Nếu main kết thúc luôn ở đó, chương trình thoát và cắt ngang request đang chạy, dù đã gọi Shutdown. Đây là lỗi rất hay gặp, chính bản nháp đầu của lời giải này cũng mắc: curl nhận về rỗng. Phải đứng chờ Shutdown làm xong (ở đây bằng channel done, bài {{n:dong-thoi}}).

CI: đẩy dự án lên GitHub (có thư mục .github/workflows), mở tab Actions để xem. Thử sửa một test cho hỏng rồi push: job đỏ. Sửa lại: xanh.
